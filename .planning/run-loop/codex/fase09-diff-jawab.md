### HIGH

1. **Cleanup dapat menghapus berkas yang sudah di-commit.** **Terverifikasi di kode:** jika COMMIT berhasil tetapi balasannya hilang, `catch` pada [follow-up](src/app/api/public/status/[token]/follow-up/route.ts:149), [intake](src/app/api/public/intake/route.ts:120), [pesan tiket](src/app/api/tickets/[id]/messages/route.ts:163), dan [lampiran project](src/lib/projects/attachments.ts:292) langsung membuang file. Kondisi commit ambigu sudah tercatat sebagai b-WR-3 dan c-IN-03, tetapi saya menilainya **HIGH**: referensi live dapat menjadi rusak, dan cleanup ini melewati fence. Gunakan cleanup tertunda yang memastikan tidak ada referensi dan menghormati fence; saat hasil commit tidak pasti, pertahankan file. **Belum terverifikasi:** reproduksi dengan putusnya balasan COMMIT sungguhan.

2. **Rollback menghapus database sebelum set tujuan divalidasi penuh.** **Terverifikasi di kode:** [runbook](docs/OPERATIONS.md:254) menjalankan `dropdb --force` sebelum restore memeriksa arsip dan checksum-nya. Set rusak atau salah berarti database live sudah hilang sebelum penolakan. Backup pertama juga dilakukan saat penulis masih aktif; perubahan setelah snapshot hingga layanan berhenti tidak ada dalam set tersebut, sehingga klaim “everything … only in the set” tidak selalu benar. Hentikan penulis, buat dan pastikan backup berhasil, validasi serta uji restore set tujuan pada target terisolasi, baru lakukan pergantian dengan prosedur yang mempertahankan database lama sampai berhasil.

3. **K142 belum menegakkan kontrak schema.** **Terverifikasi di kode:** [check_schema](scripts/backup/aida-restore-set.sh:284) menganggap tidak adanya tabel migrasi sebagai database kosong dan hanya memeriksa `target − dump`. Database yang berisi tabel lain bisa lolos; target lebih tua juga bisa menyimpan objek lama yang tidak ada dalam dump karena `pg_restore --clean` hanya membersihkan objek dalam dump. Selain itu, set lebih baru dapat masuk ke database kosong atau lebih tua lalu [layanan lama dimulai](scripts/restore.sh:445), bertentangan dengan [kontrak](docs/OPERATIONS.md:175). Saya menilai ini **HIGH**, karena restore menulis database live dan dapat menjalankan kode terhadap schema yang tidak cocok.

   Perbaikan kecil yang konservatif: sebelum menghentikan layanan atau menulis, pastikan target benar-benar kosong **atau** riwayat migrasinya cocok persis dengan set; pastikan migrasi set tidak melampaui migrasi rilis target. Untuk target kosong dengan set lebih tua, jalankan migrasi target **sebelum** memulai app dan worker. Perbandingan nama saja tetap bukan bukti kesamaan schema bila migrasi gagal, diubah, atau schema dimodifikasi manual.

4. **Otorisasi dengan keanggotaan ganda tidak konservatif.** **Terverifikasi di kode:** [getActiveOrgAccess](src/lib/authz.ts:29) memakai `findFirst` tanpa urutan, sementara [schema](prisma/schema.prisma:160) tidak menjamin satu baris per user-organisasi. Bila ada baris `admin` dan `member`, hasilnya bisa mengizinkan write; [membership.ts](src/lib/membership.ts:56) sudah mendokumentasikan aturan konservatif untuk kondisi itu. Pakai pembacaan konservatif tersebut dan uji dengan database nyata. **Terverifikasi di kode:** pola satu sesi menutup perpindahan organisasi c-CR-01 pada 20 titik yang dilaporkan; pencarian helper tidak menemukan pemanggil pola lama untuk write. **Belum terverifikasi:** pembuktian menyeluruh semua jalur otorisasi di luar pola itu.

### MEDIUM

5. **Pemulihan server baru belum menyiapkan volume unggahan secara meyakinkan.** **Terverifikasi di kode:** [panduan](docs/OPERATIONS.md:230) hanya memulai `db` dan `backup-init`; wrapper [mewajibkan volume sudah ada](scripts/restore.sh:217), dan restore mensyaratkan [kepemilikan 1000:1000](scripts/backup/aida-restore-set.sh:443). Langkah penyalinan set menjalankan service backup, bukan app yang menyiapkan direktori unggahan. **Belum terverifikasi:** perilaku pembuatan dan kepemilikan volume pada Compose nyata. Jadikan ini skenario khusus SP-2.

6. **Jaminan log tanpa password belum lengkap.** **Terverifikasi di kode:** [demo boot](src/lib/demo/bootstrap-demo.ts:61) dan [seed CLI](prisma/seed.ts:62) mencetak pesan exception mentah. **Belum terverifikasi:** exception produksi yang benar-benar mengandung password. Gunakan pesan tetap atau kelas/kode yang dibatasi, serta injeksi exception berisi rahasia pada kedua jalur.

7. **Beberapa test tidak membuktikan klaimnya.** **Terverifikasi di kode:** test “[after commit]” [file inventory](tests/integration/file-delete-inventory.test.ts:12) melempar dari `NextResponse.json`, sesudah `catch` cleanup dilewati; ia tidak dapat menangkap hasil COMMIT ambigu pada temuan 1. Test [batas boot](tests/unit/boot-tenant-seed-lock.test.ts:98) hanya memeriksa opsi pada lock tiruan, bukan durasi pool dan lock sebenarnya.

**Terverifikasi di kode:** K144 membatasi satu koneksi per provider dan worker memakai satu provider; K145 memakai lock yang sama. K143 memiliki deadline dan retry, dengan batas yang sudah dicatat. Hook E2E memeriksa `NODE_ENV` produksi sebelum membaca cookie; input tag/repo installer dibatasi, tetapi integritas arsip tanpa checksum tetap batas yang diketahui. Tidak ditemukan jalur seed yang menghapus demo pada bagian yang diperiksa. **Belum terverifikasi:** perilaku stack nyata dan semua kemungkinan kebocoran atau injeksi.

Fase 9 **belum siap** ke gerbang ulang dan verifier sebagai kandidat selesai: tangani temuan HIGH dan tambahkan test yang dapat memicu kondisi tersebut dahulu. Sesudahnya, ulangi gerbang sesuai batas resource; SP-1–SP-3, integration penuh, dan E2E penuh pasca-F4 tetap harus dilaporkan sesuai bukti sebenarnya. Saya tidak menjalankan test, build, Docker, atau jaringan.
