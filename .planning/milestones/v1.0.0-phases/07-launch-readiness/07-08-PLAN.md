<!-- Proven infrastructure to copy, and the traps to avoid. -->

**`tests/e2e/global-setup.ts` is the template for booting a disposable, seeded instance.** Its proven sequence:
1. `new PostgreSqlContainer("pgvector/pgvector:pg16").withDatabase(...).withUsername(...).withPassword(...).start()` -> `container.getConnectionUri()`
2. `execSync("pnpm prisma migrate deploy && pnpm prisma generate", { env: { ...process.env, DATABASE_URL: uri } })`
3. `fs.mkdtempSync(path.join(os.tmpdir(), "aida-..."))` for `UPLOADS_DIR`
4. spawn the server with a bespoke env (`DATABASE_URL`, `PORT`, `BETTER_AUTH_URL`, `BETTER_AUTH_TRUSTED_ORIGINS`, `NEXT_PUBLIC_APP_URL`, `BETTER_AUTH_SECRET`, `RATE_LIMIT_PEPPER`, `UPLOADS_DIR`)
5. poll `${BASE_URL}/api/health` until ready (`waitForServer`)
6. `chromium.launch()` from `@playwright/test`, drive `/setup` then `/login`, persist `storageState`
7. a `teardown` that kills the process tree (`taskkill /pid <pid> /t /f` on win32) and stops the container
Copy `killTree` and `waitForServer` verbatim — they encode real cross-platform pain.

**Use a PRODUCTION server, not `next dev`.** `next dev` renders a development indicator overlay that would appear in every marketing asset. Build once (`pnpm build`) then serve with `pnpm start` (`next start`), pointed at the throwaway database via env. If `next start` refuses because `output: "standalone"` is configured, fall back to `node .next/standalone/server.js` after copying `public/` and `.next/static` into `.next/standalone/` — exactly what the Dockerfile does (see its `COPY --from=builder` lines). Record which path you used.

**Dark mode** is driven by `next-themes` reading `localStorage`. Force it deterministically per browser context:
```ts
const ctx = await browser.newContext({ storageState, viewport: { width: 1440, height: 900 }, deviceScaleFactor: 2, colorScheme: "dark" });
await ctx.addInitScript(() => window.localStorage.setItem("theme", "dark"));
```
and the light variant with `colorScheme: "light"` + `"light"` in storage. `deviceScaleFactor: 2` gives retina-sharp PNGs.

**Demo credentials** come from Plan 07-02/07-07: `admin@demo.aida.test` / `aida-demo-2026` by default. In this capture environment set `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` on the spawned server so the headless bootstrap creates the org+admin without the `/setup` wizard, then run the seed.

**AI is OFF in the demo dataset by design** (`Setting.aiEnabled` is never written). Triage chips, the AI Activity trail and `/insights` all render from STORED data. Live "Generate draft" / "Generate insights" buttons will not produce output without a provider — plan the recording around that fact (Task 2).

**Transient first-hit 404 under a freshly started server** is a documented flake in this project (see `gotoWarm` in `tests/e2e/phase6-insight.spec.ts`): poll `page.goto(...)` until the status is not 404 rather than treating the first 404 as a bug.

**Design system:** assets must show the shipped design. Do not add capture-only CSS, hide chrome, or edit the images afterwards.

**Asset budget:** the GIF must stay under 8 MB (GitHub renders larger files poorly and it bloats every clone). PNGs should each be under 500 KB.
