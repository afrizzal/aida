### Required properties for the replan

- **C1:** the per-link visibility boundary is a provenance marker assigned while the target row lock is held (for example a monotonic message sequence compared with a merge marker taken under the lock, or an explicit visibility field written by the writing transaction), never `createdAt` against `mergedAt`. Tests cover a reply whose transaction starts before the merge but writes after it, equal timestamps, the status page and the attachment route, each for both the source and the target token.
- **C2:** a follow-up completed on the source before the merge is visible only to the source token, together with its attachments; the test adds negative assertions that the target token sees neither the message nor its attachments. 12-04 Race 2 and the matching truth say the same thing.
- **C3:** the merge path calls `findActiveMembership` before it reads any ticket data; the pre-read is removed (or moved after the membership check). A removed member gets `MEMBERSHIP_ENDED` for both a merged and an unmerged source, and the test asserts both.
- **C4:** the cycle E2E uses three tickets: C child of B, B child of A, then A child of C, which is refused with the cycle error copy and leaves the database unchanged. The two-ticket case stays as a picker test that shows the row disabled with "Already linked".
- **C5:** 12-02 states one lock order for `CHILD_OF` inserts, used in Task 1 and Task 2 alike: advisory lock, then the ticket row locks in id order, then validation (parent check, ancestor walk). Reaching the traversal bound is an explicit refusal with a defined code, proven by a test with a chain at the bound. The same-pair truth says that when the first transaction rolls back, the second add succeeds.
- **C6:** wake reads the deadline under the row lock (`SELECT … FOR UPDATE`), then runs the conditional update, and audits the locked value as `before`. Tests check the WOKEN `before` value for the wake job and for both reply paths, including a re-snooze that races the wake.
- **C7:** a reply or follow-up that is rejected (409 `MERGED_SOURCE` or `TICKET_CHANGED`, or any rollback) leaves no stored attachment file: files are staged and removed on rollback, including a partial failure after some files were saved. Tests check the storage for files, not only the rows and jobs.
- **C8:** the migration check reads `pg_trigger` for both `aida_audit_event_no_update_delete` on `AuditEvent` and `aida_ticket_audit_event_no_update_delete` on `TicketAuditEvent`, asserting table, function and enabled state; update and delete tests run against both tables. The check also compares the generated `searchVector` column definitions and the GIN index definitions, not only their names.
- **C9:** a CLOSED ticket that is still snoozed can be woken from the UI: the snoozed chip still opens the popover with "Wake now", and only setting a new snooze is disabled. An E2E snoozes a ticket, closes it, and wakes it from the chip.
- **C10:** forced-order, PID-bound tests (recorded PIDs, `waitForBlockedBy`) cover two different merges into the same target racing a reply, the second-mismatch branch that returns 409 `TICKET_CHANGED` with nothing written, and a relation removal racing a merge's link replacement. `removeRelation` re-reads the relation after taking the locks. Each test asserts that a rollback leaves no stray audit rows.
