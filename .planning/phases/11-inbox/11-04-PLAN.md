Design note on D-17 for reviewers: a conditional UPDATE alone does not wait for a transaction that is changing the ticket from OPEN to RESOLVED, because the row fails the WHERE condition on the statement snapshot and is skipped without waiting. The reply paths therefore take the ticket row lock first (SELECT … FOR UPDATE on that one row) and then run the conditional UPDATE in the next statement, which reads the committed status. This is a row lock inside one path, not the shared lock protocol D-17 rejected; the auto-close job keeps a pure conditional UPDATE on the ticket.

Design note on Codex plan review cycle 1: D-16 is amended (C3), so neither the candidate query nor the conditional UPDATE reads messages: an agent's reply does not touch the ticket row and an uncommitted message is invisible to the job's snapshot, so a message-based rule could not be enforced without serialising every message write. A customer reply still wins because it reopens the ticket under the row lock. For C8 the close takes FOR SHARE on the days setting row before its UPDATE and the save holds FOR UPDATE on it; lock order is setting row then ticket row in the job, setting row only in the save and ticket row only in the reply paths, so no cycle exists. Every race test records the PID of each run inside that run's transaction (hooks: opts.onCloseTransaction, saveAutoCloseDays hooks, setReopenObserverForTests) and waits for those PIDs only (C6).
