Access is CONTENT (an archived project or task is ARCHIVED). It takes no version and locks instead (contract section 9, K88: no conflict promise). The group is the top-level tasks of the project in the target status without the moved task, archived tasks included (`groupWhere` `:49-58`). `placeAfterTaskId` is read as `input.placeAfterTaskId ?? null`; an anchor that is not a well-formed id, equals the task (`:103-105`) or is outside the target group is INVALID_INPUT field placeAfterTaskId; a status outside TASK_STATUSES is INVALID_INPUT field status (`:96-101`). A status change runs the status path, so a move into DONE of a repeating task can create its successor in another column.

## Decisions recorded by this plan

The outline fixes this plan's purpose, its files (`[projectId]/board/page.tsx`, `loading.tsx`, `actions.ts`, `src/components/projects/board/*`, the spec) and the scope-neutral export rule; plans 15-04, 15-06 and 15-12 fix the column read shape, the anchors and drop arguments, and the frame. Where they are silent, these choices were made inside 15-CONTEXT and bind plan 15-20:

1. **Own column reads (`board-data.ts`) instead of the List's grouped loader.** The List loader is built around a view-state sort and named groups; the Board has no sort (15-04: no sort gives (rank, id), which the 15-06 anchors require), always has exactly the five status columns, keeps its rows generic so the workspace Board can carry project info, and reloads every expanded column with its loaded depth after a move. The read pattern (counts with `limit: 1`, at most 4 reads at a time, 50 per page) is the List's.
2. **The read action never forwards a sort, and only nine option keys.** `pickBoardReadOptions` copies statuses, priorities, assigneeUserIds, labelIds, milestoneIds, group, groupCounts, cursor and limit; never sort, archived, parentId, window or unscheduled, so the project Board always reads top-level, non-archived tasks in (rank, id) order (N4). The pickers live in `board-data.ts` because an action file may export only async functions, and the unit test proves them.
3. **Fail-closed move input.** `pickBoardMoveInput` copies `status` only when the key is present and `placeAfterTaskId` as given; a missing key or a non-object gives the empty-string anchor, which reorderTask refuses with INVALID_INPUT, so a malformed request never moves a task to the top.
4. **One move at a time.** Moves (menu and drop) run through one queue in request order; each requested card's Move button is pending from the request until the reload after its own move has finished; pointer drag is off while any move is queued or running. Arguments are computed from the cards on screen when the move is requested; if an earlier move changed the column, the server refuses the stale anchor and the Board says so.
5. **Reload after every move: all expanded columns and the counts, keeping depth.** A move into Done can create a repeat successor in another column and a refusal can come from a change anywhere, so the Board re-reads every expanded column with the limit `max(50, loaded + 1)` capped at LIST_MAX, plus the counts. Reloads are serialized; a request during a run coalesces into one more run. The column reload is the "reload" of the move surface's `reloadNow` (not the frame remount), so the Board keeps its loaded depth and focus can return to the Move button. Every depth-keeping reload request of the Board body (after a move, after a quick add, on the task-change signal) goes through the body's one `createCoalescedReload` runner (decision 16, K92).
6. **Announcement after the reload.** The live-region text is written when the reload has finished, after focus returned, so the focus change does not cut it off. A same-column drop is announced as "moved to the top." at insert index 0, otherwise "moved up." or "moved down." by direction; a cross-column drop and a drop on a collapsed column as "{key} moved to {status}.".
7. **Refusal text (revised for K98, S5-W2).** For a returned refusal the Board's text is the "Board move refused" row of the key; for every code other than INVALID_INPUT field placeAfterTaskId (whose meaning that row already states, so it takes precedence over G3) one space and the outcome's `reason` row follow (INVALID_INPUT with any other field or none is G3 `INVALID_INPUT_GENERAL`; ARCHIVED, NOT_FOUND, CONFLICT and the rest their rows). The callout above the columns shows NOTHING_WAS_CHANGED, one space, then that text, as every returned refusal does (UI-SPEC Surface 18 line 443 and Copywriting rules line 854); MEMBERSHIP_ENDED keeps the UI-SPEC's no-prefix rule, exactly as the outcome map gives it (its message has no prefix). The polite live region announces the shorter form without the prefix (the view's `reason`). UNKNOWN keeps the outcome map's warning notice and announces its text. Decided by K98; no copy-review item remains.
8. **Card details the UI-SPEC leaves open.** The avatar is `Avatar` size-5 with initials (no size-5 in AssigneeAvatar); an unassigned card shows no avatar (the meta row shows only what exists); the name comes from the frame's eligible-assignee names, else "Someone". Because `Card` is a flex column with its own gap, the card passes `gap-2` for the UI-SPEC's 8px stack instead of `space-y-2`.
9. **Collapsed-column drop feedback** is the same `h-0.5 bg-primary` indicator line (Color accent item 6, the Board's drop indicator) at the top of the collapsed column body; no new accent use.
10. **Collapse keys.** The Board tells the view config that all five statuses are current group keys, so a saved collapse is never pruned. Collapse works in archived projects (view-state writes are allowed there). Column toggles carry aria-expanded, and aria-controls only while the column body exists.
11. **Quick add through `view-actions.ts`.** The column quick add reuses 15-12's `QuickAdd`, `runQuickAdd` and `quickAddTaskAction` (createTask with the column's status). `board/actions.ts` therefore holds reorderTask and listProjectTasks only; the SUMMARY records that the createTask of its 18.1 row is served by `view-actions.ts`. After the empty-state quick add, focus moves to the new card's title link, because the empty state and its input are replaced by the columns.
12. **Empty Board.** With every count 0 and no filter the columns are replaced by the List's "No tasks yet" EmptyState plus one quick add with no column value (createTask's default status To do); with filters, by the "Nothing matches" EmptyState and "Clear filters".
13. **No copy added.** Every string the Board needs exists in ui-copy.ts (rows of "Move menus and announcements", "Views, groups, bulk", the shared states, BOARD_REGION_LABEL, collapsedColumnLabel); this plan does not edit ui-copy.ts, so it shares no file with 15-11 or 15-13. A missing string stops the plan and is reported (outline convention 3).

16. **Task-change signal (K92, S5-W1; revision 1).** The project Board subscribes inside its body under `ViewFrame` (so a frame Reload remount resubscribes): one `createCoalescedReload` runner per body mount wraps `useBoardColumns`'s depth-keeping `reload` (every expanded column at boardReloadLimit of its loaded cards, plus the counts); every depth-keeping reload request of the body goes through that runner (`requestColumnsReload()`: the move queue's reloadColumns, the column and empty-state quick adds, the signal); `useTasksChanged(() => { void requestColumnsReload(); })`. The detail is ignored (a task moved out of or into this project changes the columns too, and taskIds may name cards that are not loaded). No announcement, no focus move, no `useViewReload().reload()`, no router refresh. The Board's own moves and quick adds keep their own reload and send no signal. The runner is created in a mount effect and disposed in its cleanup, so a development StrictMode remount gets a fresh runner. 17. **Signal generation across adoption (K102, CX1-4; revision 2).** The server props of a new query may have been read before a task change whose signal reload the adoption guard (decision 16, Task 3 B) then drops, which would leave the pre-change columns on screen until the next signal. The Board uses 15-12's watch exactly as 15-12 decision 22 hands it off. (1) One `createAdoptionWatch()` per body mount: the mount effect of decision 16 that creates the runner also sets `adoptionWatchRef.current = createAdoptionWatch()` and sets it to null in its cleanup. (2) One body-local `navigateView(href, nextQuery)` is the only place the body navigates: it calls `adoptionWatchRef.current?.begin(viewQueryKey(nextQuery))` and then `router.push(href, { scroll: false })` inside the body's navigation transition. ViewToolbar's `onNavigate` is `navigateView` (filters, chips, the toolbar's Clear filters and the saved-view chip's close all arrive with their next query), and the no-match empty state's "Clear filters" button calls `navigateView(viewQueryHref(pathname, clearFilters(query)), clearFilters(query))`. The Board has no range, zoom or form control and renders no Link that changes its own query (a card's TaskLink opens the task), so nothing else begins. (3) `useBoardColumns` calls `onAdopted(totalCount, queryKey)` with the adopted `initial.queryKey` as the second argument, after the adopted columns are committed and that adoption's `columnsToLoad` reads have settled. The body's onAdopted announces the count (unchanged), then calls `adoptionWatchRef.current?.shouldReloadAfterAdopt(queryKey)` once and, when it is true, calls `void requestColumnsReload()`. That is one depth-keeping reload of every expanded column and the counts through the runner. It starts after the adoption, so the adoption guard keeps its result, and it reads with the adopted filters and the adopted columns' depth, because the hook's refs already hold them. It makes no announcement and no focus move; the adoption announcement stays the only one. The Board adopts server columns as they are (it has no grouping or sort that could differ), so a true result always requests the reload. Client reads (expand, Load more, the move and quick-add reloads) need no watch: a signal during them requests a runner reload that starts later and wins. The frame's Reload is 15-12's (view-frame.tsx). The adoption guard and the move queue are unchanged, and the Board has no open editor. When a later adoption happens before an earlier adoption's loads settle, only the later one calls onAdopted. The earlier key's watch record then stays until it is consumed or dropped (16 records at most); at worst that costs one extra depth-keeping reload when the reader returns to that query, never a stale column. Residual stated by 15-12: a signal that lands while a navigation into the Board from another page (a tab link) is in flight is not a navigation the Board starts, and the next signal or Reload corrects it. `useBoardColumns` gains no option; only its onAdopted callback gains the second argument, so a caller that reads only the count is unaffected.
