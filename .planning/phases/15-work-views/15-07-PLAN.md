## Decisions recorded by this plan

The outline and contract section 18.2 fix the option names, semantics, bounds and field names; this plan uses them exactly. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched):

1. Builder placement: the workspace parser and builders live in `src/lib/projects/task-query.ts` beside the plan 15-04 ones and share its private validators. Where a plan 15-04 builder's parameter type is the whole ProjectTaskQuery, it is narrowed to the fields it reads (exported subset types such as TaskFilterQuery), a type-only widening; the project behaviour and every plan 15-04 unit test stay unchanged. No builder is duplicated.
2. Groupings at workspace level are exactly status, project, assignee and priority (18.2), exported as WORKSPACE_TASK_GROUPINGS in that order; `group` or `groupCounts` by milestone is INVALID_INPUT field group or groupCounts. The workspace Timeline may group by milestone (view state 18.7) by grouping its complete window result in the view (18.2: window results are complete), so no server milestone grouping is needed at workspace level.
3. Project groups: the value is the project id; `group: { by: "project", value: null }` is INVALID_INPUT field group (a task always has a project); entries list non-empty groups only, with label `{ name, keyPrefix, color, icon }`, ordered by name then id in code-unit order (the comparator plan 15-04 uses for assignee names), with no null group.
4. projectIds: undefined and null are absent; otherwise an array of 1 to LIST_MAX distinct well-formed ids; an empty array, more than LIST_MAX values, a duplicate, a null or malformed element and a non-array are INVALID_INPUT field projectIds. There is never an existence check: an id enters only as a bound array next to the read predicate and the not-archived project term, so an unreadable, archived or missing project id matches nothing in every statement (18.2: "an unreadable id behaves exactly like a missing one"). One validator, parseProjectIdsFilter, serves both reads.
5. Validation order inside listWorkspaceTasks, all after the membership read and afterReadCheck: limit, status, assigneeUserId, dueFrom, dueTo (the Phase 14 order and fields), then statuses, priorities, assigneeUserIds, labelIds, milestoneIds, the old-and-new conflicts, projectIds, sort, group, groupCounts, window, unscheduled, the combination rules (window first, then unscheduled), and the cursor last. listWorkspaceMilestones keeps from, to, from after to, limit, cursor, then checks projectIds, so every Phase 14 call keeps its first error.
6. Combinations: window with a present cursor, limit, group, unscheduled, sort, dueFrom or dueTo is INVALID_INPUT field window (18.2 for dueFrom and dueTo; the rest mirrors plan 15-04 decision 5); unscheduled with group or groupCounts is INVALID_INPUT field unscheduled (18.2); unscheduled with dueFrom or dueTo is allowed and returns their intersection (empty, since an unscheduled task has no due date), because nothing is ignored; group with groupCounts and both with a cursor are allowed; projectIds combines with every option.
7. Absent-sort cursor: exactly the one-element `[id]` array that Phase 14 writes (a string element). A longer array, including a tagged cursor passed without a sort, is INVALID_INPUT field cursor. This tightens only inputs Phase 14 never produced and mirrors plan 15-04's rule; because isWellFormedId accepts a sort name, the length is the only reliable mark. With an explicit sort the plan 15-04 tagged cursor applies unchanged.
8. Rows: WorkspaceTaskListItem is the 16 TaskListItem keys in their order followed by `project: { id, name, keyPrefix, color, icon }` (TaskProjectInfo, typed like ProjectListItem); listProjectTasks rows do not change.
9. Result keys mirror plan 15-04 decision 9: `groups` only when groupCounts is given, `tooMany` only for a window read; with every new option absent the result is exactly `{ ok, tasks, hasMore, nextCursor }`.
10. listWorkspaceMilestones rows stay `MilestoneView & { projectName }`; contract 18.2 freezes only its options. projectIds enters the same Prisma where as readableProjectWhere (one statement).
11. N5: the workspace assignee filter options come from `groupCounts: "assignee"` of the workspace read without filters; the groups hold readable data only and the label carries a name only for a current organization member.
12. Race binding follows plan 15-03 decision 10 and plan 15-04 decision 13: the parked read's backend PID from createServiceRace.holdAt, checked to be `idle in transaction` on a one-connection observer client after the change commits and before the release; describeReadRaces is reused unchanged where its world fits, other worlds stay local to the race file.
13. Two-worlds data: a ref that exists only in the hidden world resolves in the plain world to one fixed well-formed id that exists nowhere (missingId() taken once per test), so each query differs between the worlds only by ids and the comparison also proves "unreadable id equals missing id"; hidden prefixes and names are long and distinctive (for example AHIDALDER, "Alder hidden") so the hidden-trace scan cannot match by chance inside a base64url cursor.
14. Files beyond the outline's list for this plan (recorded deviations, no wave 3 plan owns them): the new unit file `tests/unit/project-workspace-query.test.ts`, because the new pure builders need the same unit proofs plan 15-04 gave its own, including the value-binding check; and `tests/integration/project-task-query.test.ts` and `tests/integration/project-task-query-isolation.test.ts` of plan 15-04, edited only where one of their assertions pins the exact key set of a workspace row or deep-equals a whole workspace row, to add `project`.
