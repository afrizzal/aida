The outline fixes the purpose, the owner files and the routes; contract 18.1 fixes both routes' statuses, headers and bodies. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or security is touched):

1. **Helpers are client-safe; the routes hold the service and storage calls.** `src/lib/project-ui/attachment-download.ts` and `attachment-upload.ts` (outline files) import only the contract, ui-copy and outcome modules of `src/lib/projects`, `src/lib/attachments/constants.ts` and `src/lib/project-ui/paths.ts`, so the Files section (a client component) imports the upload call and the unit tests run without a database. A unit test checks their import specifiers.
2. **Download headers** are the 18.1 set, written fresh (C7): Content-Type, Content-Disposition, X-Content-Type-Options, Cache-Control and, since K91, `Content-Security-Policy: sandbox` (a file a browser renders anyway runs in an opaque origin with scripts off). The RFC 5987 value is `encodeURIComponent` of the stored name after lone surrogates become U+FFFD, plus percent-encoding of `'`, `(`, `)` and `*`; an empty name becomes "file". No ASCII `filename=` parameter is added, because the frozen header form has only `filename*` (RFC 6266 allows that). The 404 and 403 text responses also carry `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`; they stay byte-identical because one builder makes them.
3. **A stored file that is gone** (storage read rejects with ENOENT or ENOTDIR) gives the same 404; any other storage error propagates, so the handler sends no other status (18.1).
4. **The 403 is MEMBERSHIP_ENDED only.** The download is READ-level, so a readable attachment is always downloadable; no other refusal exists on this route. Any other refusal code is a programming error and throws.
5. **Upload order:** the Content-Length gate (a strict decimal string not above UPLOAD_REQUEST_MAX_BYTES, imported from `src/lib/projects/contract.ts` and never redefined, K91; anything else, a missing header included, is 413), then `getSessionActor()`, then `request.formData()`, then the one-entry rule, then `uploadTaskAttachments`. 18.1 lists the session read, the parse and the service call without an order; reading the session before the body avoids parsing a body for a dead session and changes no status. Form field name "files". The one-entry rule (18.1, K91): every entry of `getAll("files")` counts, files and strings alike; more than one is 422 `{ ok: false, code: "TOO_MANY", field: "files" }` before `uploadTaskAttachments`, so no task is read and the answer is the same for a readable, an unreadable and a missing task (no oracle); otherwise the non-string entries (none or one file) go to the service, so a form without a file reaches the service's INVALID_INPUT field files. The catch calls `unstable_rethrow` first (the sign-in redirect stays a redirect, the D-03 rule), then logs one fixed line and answers 500 UNKNOWN; a body that cannot be parsed is such a thrown error (18.1: "any thrown error"). A declared Content-Length smaller than the real body passes the gate; the parse then either reads the whole body (the service refuses an oversized file, 422) or fails (500 UNKNOWN), and nothing is written either way (S9-W9; the integration test records which one happens).
6. **No revalidation from the upload route.** Project and task pages are force-dynamic; the Files section refreshes the route itself after a success.
7. **One request per file, client checks first (K91, S9-B1).** Before any request the browser checks the whole selection: more than MAX_UPLOAD_FILES files gives the TOO_MANY upload row and any file above MAX_BYTES gives the FILE_TOO_LARGE row, each after "Nothing was uploaded." (true: nothing was sent), in the service's own order. A selection that passes is sent one file per request, in selection order, one request at a time (the next starts only after the previous answer). Per file, `uploadStepAfter(view)` decides: success records "uploaded"; a file-level refusal (FILE_TOO_LARGE, UNSUPPORTED_FILE_TYPE, INVALID_INPUT, CONFLICT: `UPLOAD_FILE_LEVEL_CODES`) records "refused" with the row without prefix and the sequence goes on, because the next file may be fine; NOT_FOUND calls `markGone()` and ends everything (the task is gone, K74); any other refusal (ARCHIVED, NOT_ALLOWED, MEMBERSHIP_ENDED, TOO_MANY and any code not file-level) records "refused" and marks every later file "not sent", because it would repeat for each; UNKNOWN or a rejected request records "result not known", marks every later file "not sent" and takes the K88 path (warning notice, immediate reload, "Upload files" aria-disabled until the reload ends, no retry). Display: a one-file selection keeps the single outcome (uploadingLine(1) while it runs, uploadSuccess(1) on success, the outcome callout with its "Nothing was uploaded." prefix on a refusal, which is true for one file); a selection of two or more shows "Uploading {i} of {n}…" while file i runs and, at the end, uploadSuccess(n) when every file was stored, else "{k} of {n} files uploaded." above the per-file outcome list, whose refused rows name the file and give the row without the "Nothing was uploaded." prefix (false for a partly stored selection).
