## Decisions recorded by this plan

The outline fixes the purpose, the owner files and the routes; contract 18.1 fixes both routes' statuses, headers and bodies. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or security is touched):

1. **Helpers are client-safe; the routes hold the service and storage calls.** `src/lib/project-ui/attachment-download.ts` and `attachment-upload.ts` (outline files) import only the contract, ui-copy and outcome modules of `src/lib/projects`, `src/lib/attachments/constants.ts` and `src/lib/project-ui/paths.ts`, so the Files section (a client component) imports the upload call and the unit tests run without a database. A unit test checks their import specifiers.
2. **Download headers** are the 18.1 set, written fresh (C7). The RFC 5987 value is `encodeURIComponent` of the stored name after lone surrogates become U+FFFD, plus percent-encoding of `'`, `(`, `)` and `*`; an empty name becomes "file". No ASCII `filename=` parameter is added, because the frozen header form has only `filename*` (RFC 6266 allows that). The 404 and 403 text responses also carry `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`; they stay byte-identical because one builder makes them.
3. **A stored file that is gone** (storage read rejects with ENOENT or ENOTDIR) gives the same 404; any other storage error propagates, so the handler sends no other status (18.1).
4. **The 403 is MEMBERSHIP_ENDED only.** The download is READ-level, so a readable attachment is always downloadable; no other refusal exists on this route. Any other refusal code is a programming error and throws.
5. **Upload order:** the Content-Length gate (a strict decimal string not above the bound; anything else, a missing header included, is 413), then `getSessionActor()`, then `request.formData()`, then `uploadTaskAttachments`. 18.1 lists those three steps without an order; reading the session before the body avoids parsing a body for a dead session and changes no status. Form field name "files"; string entries are ignored, so a form without files reaches the service's INVALID_INPUT field files. The catch calls `unstable_rethrow` first (the sign-in redirect stays a redirect, the D-03 rule), then logs one fixed line and answers 500 UNKNOWN; a body that cannot be parsed is such a thrown error (18.1: "any thrown error").
6. **No revalidation from the upload route.** Project and task pages are force-dynamic; the Files section refreshes the route itself after a success.
7. **One request per selection, client checks first.** The browser sends one selection as one request, so the all-or-nothing rule behind "Nothing was uploaded." holds. Before sending, more than MAX_UPLOAD_FILES files gives the TOO_MANY upload row and a file above MAX_BYTES gives the FILE_TOO_LARGE row, with nothing sent (the service's own rows and order). A 413 response reads as FILE_TOO_LARGE whatever its body; any response that is not a contract JSON body reads as rejected and becomes UNKNOWN.
8. **Section list model.** The rows are seeded from the loader's first page and seeded again only when the task id changes. After its own upload or delete, the section re-reads page one with limit `min(LIST_MAX, max(LIST_DEFAULT, loaded + added))`, so newly added rows show even past the first page, and then refreshes the route so the other sections update. Load more appends the next keyset page. The heading shows the count only when every file is loaded (the read returns no total).
9. **Delete is shown only where it can succeed:** to the uploader or a project manager on an editable task (UPLOADER_OR_MANAGE). The Copywriting Contract has no disabled reason for files, as for comments in 7c. Upload and Delete are hidden when `editState.readOnly`; Download stays.
10. **NOT_FOUND per operation.** Upload and the section's reads are task-level, so NOT_FOUND calls `markGone()`. Delete's NOT_FOUND may mean only the file is gone, so it shows the NOT_FOUND row with Reload; the reload then shows either the current list or the not-available state.
