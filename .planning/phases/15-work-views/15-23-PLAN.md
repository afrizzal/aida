## Decisions recorded by this plan

The outline fixes this plan's purpose, its files, the mount points (15-18) and the anchor rules (15-06); contract 18.1 fixes the action-file operations. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched) and bind the later plans:

1. **Subtask versions (D-12, K88).** `getTask`'s subtasks carry no version, but `setTaskStatus` needs one and must never overwrite. The Subtasks section therefore reads the parent's subtask group through `loadSubtasksAction` (Phase 14 `listProjectTasks` with `parentId`, `archived: "include"`, every page at LIST_MAX) on mount, whenever the loader's subtask list changes, and after every Reload, and shows each row's status from that read, so the version sent is the version of the status shown. Rows (identity and order) come from `data.task.subtasks`; a row the read does not return has no version and its Select is aria-disabled until the next read. This adds `listProjectTasks` to the content-actions row of 18.1 (allowed by the 18.1 rule; recorded in the SUMMARY).
2. **NOT_FOUND per operation.** Task-level operations (createTask with the open task as parent, addTaskComment, listTaskComments, listTaskActivity, listProjectTasks of the subtask group) call `markGone()` (K74). Item-level operations (setTaskStatus or reorderTask on one subtask, editTaskComment, deleteTaskComment) show the NOT_FOUND row with Reload; the reload then shows the current list or, when the task itself is gone, the not-available state (the 15-21 decision 10 precedent).
3. **Moves.** One move at a time per section. Items and arguments come from `subtaskMoveMenu`, built on `subtaskMoveOptions` over the shown rows' ids (all subtasks, archived included, because they are part of the reorder group). `reorderSubtaskAction` builds the service input from `placeAfterTaskId` alone. After every move outcome the section refreshes the route itself (router.refresh in a transition, not `props.reload()`, which would move focus to the title) and keeps that Move button pending until the refresh ends (K88); focus returns through `useMoveFocusReturn`, with the section heading as fallback when the subtask left the list.
4. **Own live region.** The Subtasks section mounts its own `ViewAnnouncerProvider`: the drawer is a modal dialog, so a live region outside it is hidden from assistive technology while it is open, and the full task page has no view frame.
5. **Stale-anchor copy (one gap row).** The Copywriting Contract has a stale-move row only for Board columns. `subtaskMoveRefused(key)` = "{key} was not moved. The subtasks changed, so the list was reloaded." is appended to `ui-copy.ts`, marked "written by plan 15-23", pinned in `tests/unit/project-copy.test.ts`, and used only for INVALID_INPUT with field placeAfterTaskId; every other move refusal uses the "Announce refused" row with the outcome's reason. The append is allowed because the orchestrator executes plans one at a time on one checkout and the edit is append-only.
6. **Archived subtasks** are listed (getTask returns them and they anchor moves) with the Archived chip, a read-only status chip and the Move button aria-disabled with TASK_ARCHIVED_REASON.
7. **Read-only sections show the true reason.** `sectionReadOnlyReason(editState)` gives the "Archived reason" row for an archived project, PARENT_ARCHIVED_REASON under an archived parent and TASK_ARCHIVED_REASON for an archived task; Subtasks and Comments show it as a 12px muted line in place of their composer and on every Move button; Edit and Delete are hidden (the Copywriting Contract has no disabled reason for comments, UI-SPEC 7c); History is unchanged.
8. **Comment rows** are owned by the section: seeded from `data.comments`, seeded again only when the task id changes, re-read after the section's own writes with `commentsReloadLimit(loaded, added)` = min(LIST_MAX, max(LIST_DEFAULT, loaded + added)), then the route is refreshed so History picks up the new activity (the 15-21 pattern). Known limit: on a task with more than 200 comments of which fewer are loaded, a new comment past the re-read limit appears after Load more (recorded, not hidden).
9. **Comment editing.** "Edit" turns the body into a Markdown Textarea with "Save changes" and "Discard changes"; the same body (`changed: false`) counts as success. CONFLICT uses the G2 row (outcome rule: editTaskComment is not a task edit), keeps the typed text in the editor and offers Reload, which runs `props.reload()`, re-reads the comments, closes the editor and shows the stored body. The editor binds no Escape key (inside the drawer, Escape closes the drawer as for every dialog).
10. **Permissions shown only where they can succeed:** Edit for the author (`authorUserId === data.viewerUserId`), Delete for the author or `data.canManage`, both hidden when read-only.
11. **Empty sections** use muted lines as UI-SPEC 7c and the E8 row say ("No subtasks.", "No comments yet.", "No history yet."), like 15-21's Files section; page-level empty states keep EmptyState. 15-24's scan must allow this.
12. **History reuses ActivityList** (outline note, 15-09 decision 14) with three additive optional props: `heading` (`{ level: 2 | 3; id: string }`: a visible heading at that level and id instead of the sr-only h2), `emptyText` (a muted line instead of the EmptyState) and `onAccessLost` (called instead of showing the callout when a Load more read gives kind accessLost). With none of them given it renders exactly as 15-09 built it; the Activity tab passes none. `activity-list.tsx` is 15-09's file; 15-23 is the only plan of wave 8, and the regression run includes `projects-detail.spec.ts`. HistorySection keys ActivityList by `activityPageKey(data.activity)` so fresh loader data after a write remounts it.
13. **Escape in the subtask composer** closes only the composer: while its input has focus, a window capture-phase keydown listener calls preventDefault on Escape, so the drawer's dismissable layer (which ignores a default-prevented Escape) stays open, and the input's own handler closes the composer and focuses "Add subtask". The E2E proves the drawer stays open.
14. **Revalidation.** Every write action revalidates `taskPath` of each task it touches (the open task; for subtask writes also the subtask), `{ path: "/projects/[projectId]", type: "layout" }` and `{ path: "/workspace", type: "layout" }` (the 15-18 set), unless the 15-18 SUMMARY records its router.refresh contingency, in which case the actions pass no target; sections refresh the route after a success either way.
15. **Subtask composer** reuses 15-18's `titleDraftError` (title 1 to 200 code points); a created subtask gets the service defaults (To do, no priority). The input stays open and empties after success (UI-SPEC 8c).
