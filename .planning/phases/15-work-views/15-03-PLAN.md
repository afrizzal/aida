## Decisions recorded by this plan

The outline and contract section 18 fix names, signatures, access levels, isolation classes and the main semantics; this plan uses them exactly. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where authorization or privacy is touched):

1. getProject's `isFavorite` is a top-level result key next to `myRole` and `canManage` (section 18.2 says "the result gains isFavorite"), so the result is `{ ok: true, project, myRole, canManage, isFavorite }`.
2. listProjects runs one raw-SQL path for every option set, so the absent-option case and the new sorts share one statement shape. Ids are ordered and compared in the database default collation exactly as the Phase 14 Prisma orderBy did (the K71 order stays byte-identical); only the name key uses C collation.
3. The cursor anchor is checked by one statement under readableProjectSql (missing or unreadable: INVALID_INPUT field cursor, the K71 behaviour), and the page statement re-reads the anchor's sort key in a CTE under readableProjectSql, so no sort value travels through JavaScript and the anchor key is read in the same statement as the page. An anchor that disappears between the two statements yields an empty page. An id-only cursor taken under one sort and passed with another continues after the anchor in the new order (well defined, no tag needed, C9). The anchor check runs after every other validation (Decision 5) and is one statement, `id = decoded AND readableProjectSql`, so a missing, hard-deleted, unreadable, foreign (another organization's) or forged id all give the same `{ ok: false, code: "INVALID_INPUT", field: "cursor" }` and the refusal carries no signal; the isolation block proves the equality for every TWO_WORLD_READERS reader against a cursor built from missingId() (S1-W2).
4. canManage on list items: the MANAGER-row term and the privacy term are evaluated inside the page statement; the organization owner-or-admin half is the conservative membership read of the same read transaction (requireMembership, read before the afterReadCheck seam), the rule of requireProject step 7 that getProject already uses. canManage is a UI hint, never an authorization: every MANAGE operation re-checks.
5. Validation order inside listProjects (after the membership read): archived, limit, q, statuses, sort, cursor. resolvePeopleNames validates its input after the membership read, so the outsider with organization A gets MEMBERSHIP_ENDED whatever the input.
6. q case folding is PostgreSQL ILIKE under the database's character type; tests prove ASCII folding and literal matching of percent, underscore and backslash, and claim nothing about non-ASCII case folding.
7. listAddableProjectMembers: one raw statement carries readableProjectSql plus, stricter than the minimum of section 18.3, the manage term (a MANAGER row of the actor, or a non-private project with the conservative admin flag of requireProject) and the not-archived term, because the result exposes email addresses (charter rule 4); a demotion or archive committed while the read waits gives an empty page. The organization-admin half comes from requireProject's conservative read (the section 3 stated limitation on member-table races applies). Paging is pageInMemory over (name, userId), the listEligibleAssignees pattern.
8. resolvePeopleNames: one raw statement joining member and user with the actor's member EXISTS (section 2, "every read"), so an actor removed while the read waits gets `{ ok: true, people: [] }` (the list rule), not MEMBERSHIP_ENDED. Every malformed input (not an object, userIds not an array, empty, more than LIST_MAX, an id that is not well formed) is INVALID_INPUT field userIds.
9. Item shapes: listProjectMembers `{ userId, name, email, role }`; listAddableProjectMembers `{ userId, name, email }` (type AddableMemberView); resolvePeopleNames reuses PersonView `{ userId, name }`; project-list items append `isFavorite` then `canManage` after the Phase 14 keys.
10. Race binding for lock-free reads: these reads take no row lock, so waitForBlockedBy (a lock-wait proof) has nothing to wait on. The binding is the parked read's backend PID from createServiceRace.holdAt, checked on a one-connection observer client (createObserverClient) to be `idle in transaction` after the change committed and before the release. The Phase 14 harness describeReadRaces is reused unchanged where its world fits; the other worlds are local to the race test file (outline: support helpers are not modified).
11. Test files: behaviour in project-list-query.test.ts, isolation in project-list-query-isolation.test.ts (one describe per operation, title starting with the operation name), D-06 in project-list-two-worlds.test.ts, races in project-list-query-race.test.ts. Every case seeds fresh organizations (section 17).
