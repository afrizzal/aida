## Decisions recorded by this plan

The outline fixes this plan's purpose, its owner files (`src/components/projects/saved-views/*`, `saved-view-actions.ts`, `project-header.tsx`, the spec) and the action row of contract 18.1; plans 15-11 and 15-12 fix the header slot, the bridge and the hand-offs; the plan-check dispositions K93 and K97 fix decisions 11 and 15. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched):

1. **depends_on adds 15-15 and 15-17** (deviation from the outline row, rule 10 of the per-plan rules): Task 3's E2E saves a Table view with a column choice and a Timeline view with a zoom and opens both from the List tab, which needs the Table and Timeline tabs. Both are wave 5, so the wave stays 6 (max of 3, 5, 4, 5, 5 plus one), as the orchestrator gave.
2. **Visibility by pathname.** The Views button renders only when `usePathname()` equals `projectPath(projectId, TASK_VIEW_TABS[kind])` for one of the five task-view kinds (UI-SPEC "project task-view tabs only"); the decision is made in the header from the URL, so it renders on the server too and never flickers. The snapshot only decides whether the write items are available (a snapshot of another project, scope or kind counts as none).
3. **The list is read when the menu opens**, every time, with every page (`collectAllPages` over `loadSavedViewsPageAction` with limit LIST_MAX): no loader reads it (contract 18.1), and a fresh read on each open shows renames and deletes made in another tab. A read failure closes the menu and goes to the header's outcome callout.
4. **Opening a view** calls openProjectSavedView first, because the list has no filters and 15-12 decision 4 requires the filters in the URL: a readable view navigates to its own tab with `savedViewQuery(id, payload)` (mode, date and from are dropped, so a view opens on the default range); an unreadable view, or a NOT_FOUND answer (deleted meanwhile in another tab), navigates to the current tab with the current URL plus `saved={id}`, so 15-12's page shows the unreadable notice or the one neutral not-available notice. MEMBERSHIP_ENDED, UNKNOWN and any other refusal go to the header callout. Selecting the already checked item does nothing.
5. **Saving opens the new view** on the current tab (`saved={viewId}` added, every other URL parameter kept), so the chip confirms what was saved; focus goes to the Views button (Focus table).
6. **The payload sent** is the snapshot's payload; when the frame could not build one (it is null, for example above 4096 bytes), the raw object of version 1, the kind, the URL filters and the kind's state keys is sent and the service decides (INVALID_INPUT field payload, shown in the dialog callout). The browser never judges validity beyond the name check that mirrors the contract.
7. **Update is offered for an unreadable view too** (contract 18.3: update may replace an unreadable payload with a version-1 payload); it stores the page's current settings, so nothing of the unknown payload is ever applied. Update is a direct menu item without a dialog; an unchanged update (`changed: false`) still shows "View updated." because the view now equals the page.
8. **Delete targets the open view only** (the menu shows "Delete…" only for the open view; the unreadable notice requests the open view). After success the URL drops `saved` and keeps the filters (`withoutSavedView`).
