## Decisions recorded by this plan

The outline fixes this plan's purpose, its files (`[projectId]/timeline/page.tsx`, `loading.tsx`, `actions.ts`, `src/components/projects/timeline/*`, the spec) and the scope-neutral export rule; plans 15-04, 15-06 and 15-12 fix the reads, the date math and the frame. Where they are silent, these choices were made inside 15-CONTEXT and bind plan 15-22:

1. **Three reads, own data module.** The page reads the window (`window: serviceWindow(window.from, window.to)` with the filters only, as 15-04 requires), the first Unscheduled page, and every page of the milestones with the same `from` and `to` (LIST_MAX per page), in parallel through `loadTimelineData`. 15-16's calendar-data module is in the same wave and cannot be imported, so the Timeline has its own (same shape, same rules). The server page and the client use the same functions with different fetchers.
2. **One more operation in the action file.** `timeline/actions.ts` holds listProjectTasks, setTaskDates and also listProjectMilestones: a zoom change is a view-state change, not a URL change, so the client must read the milestone lane of the new window itself (contract 18.1 rule "a plan that needs one more operation in its own action file adds it and records it"; recorded in the SUMMARY).
3. **Window on the client.** The view computes `timelineWindow(state.zoom, query.from ?? defaultTimelineStart(today))` from the local zoom and the URL's `from`. A zoom change (setZoom) keeps `from`, re-reads the window and the milestones through the actions and shows skeleton rows while the loaded window differs from the shown one (never bars of another window). New server props for a new query (filters or `from`) are adopted whole when their window key equals the client's, otherwise their Unscheduled part is adopted and the window is read again with the local zoom (the 15-12 adoption rule). Navigation never edits `view-query.ts`: every href is `viewQueryHref(pathname, { ...query, from })`.
4. **Grouping in the view.** Window results are complete (18.2), so `groupTimelineTasks` partitions them on the client for every grouping, project scope and workspace alike: only non-empty groups; status in TASK_STATUSES order (label null); assignee by name then user id in code-unit order with unnamed users (no name in `names`, label null, shown as "Someone") after named ones and "Unassigned" last; milestone in the order of the given milestone list (date, id) with milestones missing from it after them by name then id (label `{ name }` from the task's own milestone) and "No milestone" last; project (workspace) by name then id with label `{ name, keyPrefix, color, icon }`. The count is the group's task count in the window. `timelineGroupKeys` feeds `setCurrentGroupKeys` with every status, every eligible assignee, every project milestone and "~none" besides the shown groups, so a collapse survives paging to a window where that group is empty.
5. **Group header rows.** A group header is a full-width chart row: the label cell holds a toggle button with the 8b rules (aria-expanded, aria-controls, the "Collapse group / Expand group" name, ChevronRight with `motion-reduce:transition-none`, `GroupLabel`, the count) at `px-2` because the label column is 240px wide, and the track cell is a `bg-muted/40` band. It is not sticky to the top: the scale header holds the region's top. The shared `GroupHeader` (`px-6`, sticky top) is not reused here, following the 15-15 Table precedent.
6. **Sizes.** Day widths `TIMELINE_DAY_WIDTH_PX` day 40, week 16, month 4 (UI-SPEC sizes); label column 240px; rows `h-9`; bars `h-6`; track width = days × day width, set with React style properties (`width`, `gridTemplateColumns: repeat(days, Wpx)`, `gridColumn`), because the values depend on the zoom.
7. **Scale rows.** Top row: months from `monthSegments` (Day zoom "November 2026", Week and Month zoom "Nov 2026"). Bottom row: one cell per day with the day number in Day zoom (weekends `bg-muted/30`); week starts from `weekSegments` in Week zoom ("9 Nov") and Month zoom ("9"). The scale is aria-hidden: bars and points carry their full dates in their names.
8. **Bars and points.** A task with both dates is a bar (`timelineItem` shape bar; a square end where clipped); one date is a point marker whose dot is centred on its day by a React style margin of day width / 2 − 6 px, with the title to its right; both carry the project colour (`stripe` on bars, `dot` on points), both are draggable. A bar has `role="img"` and the "Bar label" name, a point the "Point label" name; neither is a link (the label cell's title is the link and the drawer's focus-return target).
9. **Drop region.** Every task row's track cell carries `data-drop-region` = "timeline" (TIMELINE_DROP_REGION_ID); a release over any task row's track drops with the horizontal pointer delta, a release anywhere else (label column, scale, milestone lane, group rows, outside the region) cancels with reason outside. The ring shows on the dragged task's own row while the snapped shift is not zero.
10. **Set dates dialog.** Two date inputs prefilled with the task's dates. An empty input means null (that end is cleared); both empty keeps "Set dates" aria-disabled (clearing every date belongs to the task drawer, and no announcement row exists for it); a value the browser marks as bad input, or a date outside 1970 to 2999, shows the service's INVALID_INPUT view for that field resolved locally through resolveProjectOutcome without a call (the 15-13 and 15-16 precedent); start after due shows the "Date order error" text under the due date input. A returned refusal stays in the dialog with the typed dates (kind field under the named input, else the callout; CONFLICT and NOT_FOUND offer Reload, which reloads the Timeline and refreshes the dialog's version and current dates while keeping the typed values, or closes the dialog when the task is no longer loaded).
11. **Unscheduled section.** Sorted by title (A to Z, then key, then id), 50 per page; the heading shows a count only when `hasMore` is false (no server total, plan 15-04); its collapse is page state, not view state (it is not a group; 18.7's collapsed holds group keys), expanded on load. After "Set dates" from a row succeeds focus goes to the section heading (UI-SPEC Focus row: the task left the section); closing without acting returns focus to the row's button.
12. **Focus fallback.** After a move focus returns to the task's Move button; when the task left the window (no row after the reload) it goes to the Timeline region (`TIMELINE_REGION_ID`, tabIndex 0).
13. **One write queue and reload rule.** Shifts, drops and Set dates run one at a time through `useTimelineMoves`; the control is pending from the request until the reload after its write has ended; pointer drag is off while any write is queued or running; nothing is retried by itself (K88). After every write the window, the milestones and the Unscheduled list are re-read (Unscheduled limit `timelineReloadLimit(loaded)` = max(50, loaded + 1) capped at LIST_MAX); reloads are serialized and coalesce; a reload that started before a window change or an adoption discards its result.
14. **Empty and too-many states.** With no task in the window the chart still renders its scale, milestone lane and today line (UI-SPEC E14 empty: rows only for dated tasks). With `tooMany` the whole chart is replaced by the warning notice; the range controls and the Unscheduled section stay; "Clear filters" renders only while a filter is set.
15. **Scroll region.** `role="region"`, `tabIndex={0}`, `min-w-0 overflow-auto max-h-[calc(100vh-220px)] contain-inline-size`: the region scrolls both ways, its sticky label column and scale stay in view, and size containment keeps its content width from widening `main` or the document, so the page never scrolls sideways at 1920px (proved by E2E) independently of the (app) layout's missing `min-w-0`, which is plan 15-18's file. Narrow widths stay a manual item.
16. **Archived.** Move buttons and Unscheduled "Set dates" buttons stay visible and aria-disabled, described by one visible 12px muted line "Restore the project to change this." (`TIMELINE_ARCHIVED_REASON_ID`); MoveMenu also carries the reason; drag is off. Zoom, grouping and collapse stay enabled (view-state writes are allowed on an archived project, 18.3).
17. **Announcements.** "{n} tasks shown" (n the window's task count) or the too-many text after a filter change (adoption with a different filter key); a window change is announced by the aria-live heading; moves and cancels by their rows.
18. **Module purity.** `timeline-model.ts` imports no component module except type-only imports, so the E2E spec can import its day widths and DOM hooks; everything that needs the drag layer at runtime (`snapSteps`, `closestDropZone`) lives in `timeline-drag.ts` (the 15-14 `board-drag.ts` precedent). `TIMELINE_DROP_REGION_ATTRIBUTE` repeats "data-drop-region" and a unit test pins it equal to `DROP_ZONE_ATTRIBUTES.region`.
19. **No copy added.** Every string exists in ui-copy.ts (rows of "Calendar and Timeline", "Move menus and announcements", "Task drawer and page" Property labels and Date order error, "Views, groups, bulk", "Primary CTAs and global", the shared states and the inline TIMELINE_REGION_LABEL); the range heading is date data (`formatDateRange`), not copy. This plan does not edit ui-copy.ts or its test. A missing string stops the plan and is reported (convention 3); a gap row would then be appended after the last one, marked "written by plan 15-17", under the one-checkout rule 15-12 recorded (plans of a wave execute one at a time on one checkout).
20. **E2E shape.** Dates are anchored on the default window: `WIN` = `timelineWindow("week", defaultTimelineStart(TODAY))` and `winDay(n)` = `dayOffset(n, WIN.from)`, so every seeded date and its moves stay inside the default Week window whatever today is. The time-zone runs are a describe per zone inside this spec (outline E2E map), each with `test.use({ timezoneId })` and a `getTimezoneOffset` check. Viewport 1920x1080.
