## Decisions recorded by this plan

The outline fixes this plan's purpose, owner files and the loader reads of contract section 18.1; this plan uses them. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy is touched):

1. **Project NOT_FOUND is decided in the layout** (K74). `[projectId]/layout.tsx` calls `notFound()` when `getProject` is NOT_FOUND, so no tab page renders and the output is the same for every tab, including tabs built later. Because a layout's own `not-found.tsx` cannot catch it (Next 16), the boundary is a new `src/app/(app)/projects/not-found.tsx` that renders `<NotAvailable />` (deviation: one file outside the outline list; no other plan of any wave names it). `[projectId]/not-found.tsx` (outline file) renders the same component for a NOT_FOUND that a tab page meets after the layout's read succeeded (access lost between two reads); that case shows inside the shell, which the reader could read a moment earlier. Contingency: if Task 1's E2E shows Next's default 404 page instead of the not-available state, the layout renders `{children}` without the shell on NOT_FOUND and each page calls `notFound()` itself (so `[projectId]/not-found.tsx` renders it); the SUMMARY records which path shipped.
2. **Status code is compared, not pinned.** Missing, malformed, deleted and unreadable take one code path, so their status is identical. It is 404 while no Suspense boundary sits above the layout and becomes 200 with a noindex tag once plan 15-10 adds `projects/loading.tsx`; the E2E asserts equality (and that it is 200 or 404) so it stays green across that change.
3. **No per-project document title.** Project routes export no metadata function, so the title never carries a project name and is identical for every not-available case (K74).
4. **One cached loader module** `src/lib/project-ui/load-project.ts` (deviation: new file in a D-04 directory; unclaimed by any plan): `loadSessionActor` and `loadProject` wrap `getSessionActor` and `getProject` in React `cache()`, so the layout and the page share one read per request; later tab plans call `loadProject` for the getProject read of section 18.1.
5. **The shell cancels the (app) main padding** with `-m-6` (the `tickets/layout.tsx` precedent), so the tab nav border spans the full width and the UI-SPEC paddings (`px-6 pt-6` header, `px-6 py-6` content) apply exactly. Tab pages add no page padding of their own.
6. **Not-yet-built tabs** (List, Board, Table, Calendar, Timeline, Files) are links to their final URLs from the first commit (outline convention 6: the nav is complete, a link to a page whose plan has not landed is transitional). No commit adds a stand-in page for them; no E2E of this plan follows one of those links (the spec checks their names and hrefs only); each tab plan adds its own `page.tsx` and `loading.tsx` under `[projectId]/`, and the layout, the nav and `[projectId]/error.tsx` need no change for it.
7. **Header controls of this plan** are the favorite toggle and the actions menu with Copy link, Add to favorites or Remove from favorites, and Archive project or Restore project. The "Edit project" header button, the settings menu items, "Add a description", "Manage members" and "Manage milestones" are plan 15-11's (outline: 15-11 wires them into the header, the menu and the Overview cards), so this plan renders no control that has nothing to open. `OverviewData` carries `canManage` and `archived` for 15-11's buttons.
8. **Surfaces of the outcome map**: the favorite toggle uses surface `inline` (focus stays on the toggle), archive and restore use `view`; there is no dialog. The one callout sits under the header row (role alert), shared by all header actions.
9. **Members card total**: `loadAllProjectMembers` reads every page of `listProjectMembers` with limit LIST_MAX, so "+{n} more" is a true count (`listProjectMembers` returns no total).
10. **Overview reads** follow section 18.1 except `resolvePeopleNames`, which the Overview does not need (member rows carry names); reading less than the matrix lists changes no rule. Upcoming milestones use `from` = `todayForViews(new Date())` (15-06, per request on the server) and limit 5.
11. **Overdue rule** (UI-SPEC Color, destructive row): a project due date is overdue when it is earlier than today and the status is not COMPLETED; shown with the CalendarX icon, the date and the sr-only "Overdue label", never colour alone. Exported as `projectDueState` for plan 15-10.
12. **Activity task references.** The `{task}` text is the key the row itself carries (per verb, see Task 3); otherwise the key a caller passes in `taskKeys` (plan 15-23's History passes the open task's key); otherwise the gap row "a task". The link target is the row's `taskId` (TASK_DUPLICATED: the source `before.taskId`; TASK_RECURRED: `after.predecessorTaskId`; TASK_DELETED: no link, the task is gone); a redacted row has no link because redaction nulls its task id. No extra read is made for keys: the Activity loader reads exactly `listProjectActivity` and `resolvePeopleNames` (section 18.1) and D-07 forbids re-deriving data.
13. **Three copy gap rows, numbered at execution time** (deviation from outline convention 3, which says no plan adds copy; the gap was found at planning time and is settled here so the executor does not stop): the Copywriting Contract has no text for a task reference without a key or for a label or milestone update that did not change the name. `src/lib/projects/ui-copy.ts` (owned by 15-05 in wave 2; no other wave-3 plan touches it) gains `ACTIVITY_TASK_FALLBACK` "a task", `activityLabelUpdatedUnnamed(actor)` "{actor} updated a label" and `activityMilestoneUpdatedUnnamed(actor)` "{actor} updated a milestone".
