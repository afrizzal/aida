## Decisions recorded by this plan

The outline and contract section 18 fix the names, signatures, access levels, locks, isolation classes, result shapes and the K90 placement; this plan uses them exactly. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy, authorization or schema is touched):

1. **listProjectSavedViews pages in memory.** One statement reads all of the owner's views of the project under readableProjectSql; the rows are sorted by (name, id) in code-unit order and paged with pageInMemory over `[name, id]` (the listEligibleAssignees pattern). SQL collation orders UTF-8 bytes, which differs from code-unit order above U+FFFF; the per-owner set is bounded by PROJECT_SAVED_VIEW_MAX (soft, Decision 13), so reading it whole is cheap and exact.
2. **createProjectSavedView** counts the owner's views of the project after its lock and refuses TOO_MANY at the bound, then inserts with `ON CONFLICT DO NOTHING RETURNING "id"` and, when nothing was inserted, re-reads `lower("name")` to refuse NAME_TAKEN (the createLabel shape, section 14 "idempotent inserts use ON CONFLICT DO NOTHING and re-read"). At the bound TOO_MANY wins over NAME_TAKEN.
3. **Rename and update** are raw UPDATE statements. NAME_TAKEN of a rename comes from the new UNIQUE_INDEXES entry `SavedView_project_name_key` in db-errors.ts (the "mapped by its name as in section 14" rule of 18.3), so a concurrent rename or create that commits first still yields NAME_TAKEN, never a thrown error. Rename's no-op is exact equality with the stored trimmed name (a change of case is a change); update's no-op is decided in the statement with `IS DISTINCT FROM` on jsonb (structural equality of the canonical values).
4. **VIEW_OWNER writes lock the view row.** Step 7 of the 18.3 resolution is a locking re-read (`FOR UPDATE`) of the owner's SavedView row after the project `FOR SHARE`, so two writes of one view by its owner serialize and an update never reports a false no-op for a view deleted meanwhile. Lock order: the project row (section 3, class 2), then the view row; deleteProject holds the project FOR UPDATE before it deletes view rows, and no writer of view rows holds a view row without the project FOR SHARE, so no cycle exists.
5. **Validation after access.** Every operation validates its input (name, payload, viewKind, state, limit, cursor) after the access check (after the lock for a write), so a refused actor learns nothing from validation and an outsider with organization A gets MEMBERSHIP_ENDED whatever the input (15-03 Decision 5), except a malformed id, which is refused NOT_FOUND first wherever section 2 step 1 or 18.3 step 1 puts it first. All four VIEW_OWNER operations check a malformed view id first, before the membership read, in the 18.3 step order (step 1 malformed id, step 2 membership): the three writes in lockOwnView before requireMembership, and openProjectSavedView before it enters runProjectRead (whose first statement is the membership read), returning `refusalResult("NOT_FOUND")` without a database read (S3-I1, adopted). So an outsider with organization A gets the same answer from open as from the writes: NOT_FOUND for a malformed view id, MEMBERSHIP_ENDED for a well-formed one. A malformed id is a property of the input alone, so answering it before membership discloses nothing.
6. **openProjectSavedView computes stale in its final statement** from the row's own stored filters (jsonb array extraction guarded by jsonb_typeof), together with the row and the read predicate, so the payload and the stale flag come from one statement and a malformed stored value never makes the statement fail.
7. **Final statements of the state reads.** getProjectViewState reads the Project row under readableProjectSql with a LEFT JOIN of the actor's state row: no project row is refuseUnreadable, a project row without state is `{ state: null }`. getWorkspaceViewState reads the actor's own member row with the state in a scalar subquery: no member row is MEMBERSHIP_ENDED.
8. **saveWorkspaceViewState** (MEMBER, lock NONE) calls requireMembership and then afterLock before its write, the createProject shape, so it has the same test seam as the other writes.
9. **db-errors.ts and its unit test join files_modified** (deviation from the outline's file list; no wave-3 plan owns either file: 15-07 owns tasks.ts, task-query.ts, milestones.ts and its tests, 15-09 owns UI files). Besides the unique index, four CHECKs that a malformed input could reach if a validator ever regressed map to INVALID_INPUT with the service's field: SavedView_name_length_check (name), SavedView_project_payload_size_check (payload), ProjectViewState_state_size_check (state), ProjectViewState_kind_scope_check (viewKind). SavedView_scope_project_check, SavedView_project_private_check and the inbox name indexes stay unmapped: these services never write such a row, so a violation is a programming error and is rethrown.
10. **Raw writes stamp `updatedAt` with `now()`** (the transaction time) and generate ids with randomUUID (well-formed ids under section 2 step 1); no decision of these operations reads the clock, so no test needs `opts.now`.
11. **Race bindings.** K90 and revocation races are real lock waits: waitForBlockedBy(observer, holderPid, [waiterPid]) with assertNoDeadlock, the project-delete.test.ts shape. Lock-free read races bind to the parked read's PID and check it is `idle in transaction` on the one-connection observer (15-03 Decision 10). NAME_TAKEN and upsert interleavings park the first writer after its lock (PID asserted `idle in transaction`) while the second writer runs to completion; no lock wait exists there to bind.
12. **Read races reuse the Phase 14 race world unchanged.** world, applyChange, gone, PROJECT_CHANGES and CHANGE_NAMES are imported from tests/support/project-read-race.ts; the reader's view rows are created on top through the services before each race; describeReadRaces is not used because its cases cannot seed rows.
13. **Soft TOO_MANY bound** (stated limitation of 18.3, lock mode PROJECT_SHARE): only the single-writer bound is tested; two concurrent creates of one owner may each pass the count. The SUMMARY records it; it has no security effect (every row is the owner's own and size-bounded).
14. **Task order and registration positions.** Task 1 registers listProjectSavedViews and createProjectSavedView, Task 2 inserts openProjectSavedView between them and appends rename, update and delete, Task 3 appends the four view-state lines; the line positions always follow the frozen order, as the registration-aware tests of 15-01 require.
15. **Rename swap deadlock (stated limitation, S3-I2).** Two concurrent renameProjectSavedView calls by one owner that swap the names of two of its views of one project (A to B's name while B goes to A's name) can deadlock on the unique index SavedView_project_name_key: each UPDATE writes its new row version and then waits in the index check on the other's in-progress old version. PostgreSQL aborts one of them with 40P01, which mapDatabaseError maps to CONFLICT (db-errors.ts:108, the section 14 last resort), the same as Phase 14 label renames; the other then meets the still-taken name and returns NAME_TAKEN. No view changes its name and nothing is half-written; a swap can never succeed in one step anyway (each target name is taken), so the only effect is CONFLICT in place of NAME_TAKEN for one of the two calls, and the caller may retry. The K90 lock order is unaffected: both renames hold the project FOR SHARE and only their own view row FOR UPDATE, deleteProject waits for every FOR SHARE holder before it deletes view rows, so no cycle includes deleteProject. Not tested: the window lies inside one UPDATE statement, between the row write and the index check, where no seam can park a transaction. The SUMMARY records it.
16. **Upsert last-commit-wins (stated limitation the simplified K100 relies on, owner decision 15-o2).** Within one tab, view-state saves are serialized per mounted view only (15-12: one saver per mount, no registry); two saves of one key from different mounts or tabs both reach saveProjectViewState or saveWorkspaceViewState, and the later commit is the stored state. The upsert interleaving test of this plan proves that order on the server; 15-12 records the three stated limitations that rely on it. No lock or version column is added for it.
