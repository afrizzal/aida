## Decisions recorded by this plan

The outline fixes this plan's purpose, its files and its owner role for the (app) layout in wave 5; contract 18.1 fixes the loader reads and the action-file operations. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched) and bind the later plans:

1. **Drawer mechanism (D-02, checked in Context7).** `src/app/(app)/@drawer/(.)tasks/[taskId]/page.tsx` intercepts `/tasks/[taskId]` on soft navigation; `src/app/(app)/@drawer/default.tsx` returns null; the (app) layout renders `{drawer}`. No catch-all page in the slot: a catch-all inside the (app) group would make every unknown URL resolve inside the authenticated layout (a sign-in redirect instead of the 404) and overlap other groups' paths. Instead the drawer derives `open` from the pathname: it is open only while `usePathname()` equals `taskPath(taskId)`, so a link out of the drawer closes it although the slot keeps its content.
2. **D-02 fallback rule.** If Task 1's E2E shows that a TaskLink click makes a full document load or that direct entry shows the drawer, and the cause is the route mechanism rather than this plan's code, the executor takes the D-02 fallback in the same task: `TaskLink`'s href and `taskPath` change as 15-05 allows (the drawer state lives in `?task={id}` on the current view URL, `/tasks/{id}` stays the full page), the drawer is hosted by a client component in the (app) layout that reads the `task` search parameter and loads `TaskViewData` through a read action calling `loadTaskView`, the spec's URL assertions follow, and the SUMMARY records the deviation with the failing evidence. Nothing else in this plan changes.
3. **Close semantics.** "Close", Escape and an outside click call `router.back()` (UI-SPEC "Drawer mechanism"); a guard ignores a second close. Focus returns when the drawer unmounts: SheetContent's onCloseAutoFocus is prevented and the drawer's unmount effect calls `restoreTaskFocus()` (focusTaskOpener, else the first `main h1`). A drawer closed by a pathname change (a link out of it) moves no focus and clears the opener. Closing from a drawer reached by a link inside another drawer goes back one step, as the browser would.
4. **Loading without a second Sheet.** The intercepted page renders `TaskDrawer` at once and streams its body through a Suspense boundary (fallback: the drawer skeleton), so there is one Sheet instance and one slide-in; there is no drawer `loading.tsx`. An unexpected loader error is caught by a new `@drawer/(.)tasks/[taskId]/error.tsx` that renders the drawer frame with the "Load error" callout and "Try again" (deviation: one file outside the outline list, inside this plan's slot folder).
5. **Not available.** The full page calls `notFound()` and `tasks/[taskId]/not-found.tsx` renders `<NotAvailable />` inside a `div` with `data-task-not-available`. The drawer never calls `notFound()` (a slot has no not-found boundary of its own): its frame renders the same wrapper and `<NotAvailable />`, and its header keeps only "Close". An action or edit that returns NOT_FOUND switches the TaskView of either form to the same wrapper (UI-SPEC 7f). No task route exports metadata, so the document title never names a task (K74). MEMBERSHIP_ENDED renders `OutcomeCallout` with `MEMBERSHIP_ENDED_VIEW`.
6. **The loader reads all of 18.1 now.** Plans 15-21 and 15-23 own no loader file, so `loadTaskView` already reads the first pages of comments, attachments and task activity, the task progress and the people names, and passes them in `TaskViewData`; the parent's key and title come from a second `getTask` call on `parentId` (the same operation; an unreadable parent gives no parent line). A NOT_FOUND from any read gives the not-available state (the task moved or vanished between reads); MEMBERSHIP_ENDED gives the ended state; any other refusal throws (a programming error, N6).
7. **Content mount points.** `task-view.tsx` exports `TASK_SECTION_ORDER` (subtasks, attachments, comments, history) and `TASK_SECTION_RENDERERS`, a record of four renderers taking `TaskSectionProps` and returning null in this plan. TaskView renders, after the description, the parent line in place of the subtasks section for a subtask (this plan), else each renderer's output in order. 15-21 replaces `attachments`; 15-23 replaces `subtasks`, `comments` and `history`. Section components import their own action files directly (client components may import server actions), so no later plan edits a route or the loader.
8. **Actions are imported directly** by the client components of this plan (not passed as bound props), because two pages render the same TaskView and the later sections follow the same rule.
9. **Revalidation.** Every write action revalidates `taskPath(taskId)`, `{ path: "/projects/[projectId]", type: "layout" }` and `{ path: "/workspace", type: "layout" }`; the response then re-renders the current tree, drawer included. Contingency: if Task 1's E2E shows that a revalidating action closes the drawer or swaps it for the full page, the task actions pass no revalidation target and the client calls `router.refresh()` after each success; the SUMMARY records it.
