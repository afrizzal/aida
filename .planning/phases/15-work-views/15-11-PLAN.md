## Decisions recorded by this plan

The outline fixes this plan's purpose, its owner files, the action file name and the action row of contract section 18.1; 15-09 fixes where the controls go. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched):

1. **One settings provider in the project shell** (deviation: `src/app/(app)/projects/[projectId]/layout.tsx` is modified; no wave-4 plan names it). The layout wraps the shell in `ProjectSettingsProvider` with the editable project (the ProjectView fields id, name, keyPrefix, color, icon, status, isPrivate, version, descriptionMarkdown, dueDate), canManage, archived and the viewer's user id from `loadSessionActor()` (cached, no extra read). One instance of each dialog per page; the header button, the actions menu and the Overview buttons open them with `useProjectSettings().openSettings(kind, opener)`. Reason: the header lives in the layout and the Overview in the page; one provider avoids two dialog instances and gives the Members dialog the viewer's id for "Remove yourself" without a new read. `ProjectHeader` keeps its props.
2. **Availability table** (`projectSettingsItemState(kind, { canManage, archived })` returns `{ available, reason, readOnly, readOnlyReasons }`, UI-SPEC 3i and P12, disabled with a reason and never hidden). `reason` is why an unavailable item is disabled (null when available); `readOnlyReasons` lists, in display order, why an available item opens read-only (empty otherwise). Edit, labels and milestones are unavailable with the manager-only reason for a non-manager (also in an archived project, because restoring would not help them) and with the archived reason for a manager in an archived project. **Members is always available** (revision 1, K98, S4-W3): listProjectMembers is a READ and the dialog has a read-only mode, so in an archived project it opens read-only for everyone instead of being disabled (3i's "every edit item is disabled" is met because the dialog's write controls are absent): a manager of an active project gets `{ available: true, reason: null, readOnly: false, readOnlyReasons: [] }`, a manager of an archived project `readOnlyReasons: ["archived"]`, a non-manager of an active project `["managerOnly"]` (3f), a non-manager of an archived project `["managerOnly", "archived"]` (both lines are true: only managers can change members, and only after a restore), each with `readOnly: true` and `reason: null`. Duplicate is always available on the same reasoning (duplicateProject needs READ only and does not change the archived source). Delete is unavailable with the manager-only reason for a non-manager and otherwise available, archived included (MANAGE_ARCHIVED). For every kind other than members, `readOnly` is false and `readOnlyReasons` empty. The header's `blocked` flag (15-09: pending or UNKNOWN until reload) makes settings items aria-disabled without a reason.
3. **Reason display.** Menu items: an aria-hidden 12px muted reason line referenced by aria-describedby (the 15-09 and status-manager pattern). Header "Edit project" button: aria-disabled, an sr-only reason element referenced by aria-describedby and the same text in a `title` attribute (15-10 decision 9; no Radix Tooltip, which would overwrite aria-describedby). Overview buttons: a visible 12px muted reason line referenced by aria-describedby. "Add a description" renders only for managers (UI-SPEC Surface 5 "for managers").
4. **Ordered edit calls** (UI-SPEC 3b, D-08): updateProject with only the changed keys of name, description, colour, icon and due date; then setProjectStatus, setProjectPrivacy and changeProjectKeyPrefix, each only when changed, in that order; each call takes the version the previous success returned (or the baseline version when a result carries none); the first non-success stops the save. No change at all sends nothing and closes the dialog like "Close without saving". The dialog keeps a baseline (values and version) that advances after each success, so a second "Save changes" sends only what still differs. A returned refusal after at least one success shows the "Partial save" row followed by the refusal row, without the "Nothing was changed." prefix (which would be false), with Reload; a refusal of the first call shows the normal prefixed row; UNKNOWN or a rejected call shows the UNKNOWN notice, refreshes the route at once, keeps "Save changes" aria-disabled until that refresh ends and then re-reads the baseline from the refreshed provider props while the typed values stay.
5. **Edit fields and client checks.** Order: Name, Description, Status, Due date (with "Clear date"), Key prefix (with the prefix notice), Colour, Icon, Private project (with the privacy notice). Client checks mirror the contract (name 1 to 80 code points without NUL; description at most 5000 code points without NUL; due date empty or a CalendarDate; key prefix accepted by normalizePrefix). An invalid field gets aria-invalid, its help line turns `text-[12px] text-destructive`, focus moves to the first invalid field and nothing is sent (no new copy; the Due date field without a help line is linked to the INVALID_INPUT row only when the service returns it). The Key prefix help shows the typed prefix when it is valid, else the stored prefix. A stored null icon stays null unless the reader picks one (the 15-05 picker shows Folder for null).
6. **Neutral prefix copy** (D-08): PREFIX_INVALID and PREFIX_TAKEN reach the screen only through resolveProjectOutcome (one row, field keyPrefix); the dialogs add no text of their own, so a prefix held by a hidden private project, a visible project or a kept reservation reads identically. The probe itself stays owner item 14-o3.
7. **Management dialogs read on open and after every write.** Members reads every page of listProjectMembers and, only for a manager in a non-archived project, every page of listAddableProjectMembers (P1; limit LIST_MAX per page); Milestones every page of listProjectMilestones; Labels listLabels.
