## Decisions recorded by this plan

The outline and contract section 18.2 fix the option names, semantics, bounds and field names; this plan uses them exactly. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched):

1. `task-query.ts` is a pure builder: it imports only the generated Prisma client (value import, for Prisma.sql, Prisma.join and Prisma.empty) and the contract module, both by relative path; it performs no database call, imports neither the service nor the access module, and exports no function that takes an actor. The statements run in `tasks.ts` and `milestones.ts`, which pass in `readableProjectSql("p", actor)`. Because it loads the Prisma runtime, client components never value-import it (types only); UI value sets come from `contract.ts` and `view-payload.ts`.
2. `TaskListItem` moves to `task-query.ts` and `tasks.ts` re-exports it as a type. Contract 18.2 makes it the item of both task lists ("TaskListItem, also of the workspace read"), so `listWorkspaceTasks` moves onto the same raw item path in Task 1 with its Phase 14 filters, order, `[id]` cursor and validation order unchanged. This is a recorded deviation from the outline's file note, which names only listProjectTasks and getTask for tasks.ts; tasks.ts is this plan's file in wave 2, so nothing collides, and plan 15-07 extends the workspace read in wave 3. Key order: the 13 Phase 14 keys, then estimateMinutes, milestone, labels.
3. One raw statement returns a page: the task columns, the labels as a JSON aggregate subquery, the milestone through a join with explicit organization and project terms, estimateMinutes and the sort-key columns, with `readableProjectSql` in the same statement. Labels are sorted in JavaScript by name then id in code-unit order (the comparator getTask uses), because PostgreSQL C collation is byte order, not UTF-16 code-unit order.
4. Validation order inside listProjectTasks, all after `requireProject` and `afterReadCheck` (so a refused actor gets NOT_FOUND whatever the options, as in Phase 14): limit, parentId, status, assigneeUserId, archived (the Phase 14 order), then statuses, priorities, assigneeUserIds, labelIds, milestoneIds, the old-and-new conflicts, sort, group, groupCounts, window, unscheduled, the combination rules (window first, then unscheduled, then parentId), and the cursor last.
5. Combinations where 18.2 is silent: window with an explicit sort is INVALID_INPUT field window (the window order is fixed and a silently ignored option would mislead; 15-01 decision 6, narrow combinations); parentId with group, groupCounts or unscheduled is INVALID_INPUT field parentId (18.2: parentId combines with the filters, sort and paging only); window with groupCounts is allowed and its groups count every window task, also when tooMany is true (complete numbers, no rows); group and groupCounts may be combined, and both may be combined with a cursor.
6. Presence: an option is present when its value is neither undefined nor null, except the Phase 14 assigneeUserId, where null means unassigned and the filter is present whenever the value is not undefined. unscheduled is present only when it is true; false, null and undefined are absent, any other value is INVALID_INPUT field unscheduled. group and window must be plain objects with exactly their two keys (a third key with a defined value is INVALID_INPUT field group or window).
7. Tagged cursor shapes (base64url JSON, raw value at most 4096 characters): manual `["manual", rank, id]`; dueDate and startDate `[sort, date or null, key, id]`; priority `["priority", priority, key, id]`; title `["title", lower(title) exactly as PostgreSQL computed it, key, id]`; createdAt `["createdAt", ISO timestamp with milliseconds, id]`. Each value is validated (rank a safe integer from 0 to RANK_MAX, a CalendarDate or null, a key matching TASK_KEY_PATTERN, a TASK_PRIORITIES value, a title string without NUL of at most 4 times TASK_TITLE_MAX code points, an ISO string that round-trips through Date, a well-formed id). The cursor is never re-read as an anchor: the next page is the rows after those values, so the result depends only on rows the reader can read. Task rank is not secret (the Phase 14 task cursor already carries it); K71 protects only the project position.
8. Sort SQL: keys compare in C collation (`COLLATE "C"`); ids carry no collation clause, so the manual and absent orders are byte-identical to the Phase 14 Prisma order; priority is a CASE with URGENT 0, HIGH 1, NORMAL 2, LOW 3, NONE 4; title is lower(title) in C collation.
9. Result keys: `groups` only when groupCounts is given, `tooMany` only for a window read; with every new option absent the result is exactly `{ ok, tasks, hasMore, nextCursor }`.
10. The bound is decided in the one window statement with LIMIT TASK_WINDOW_MAX + 1: more rows than TASK_WINDOW_MAX gives tooMany true and an empty tasks list.
11. getTask returns `{ task, isFavorite }` with isFavorite top level, the shape 15-03 chose for getProject; TaskView is unchanged. isFavorite comes from getTask's last statement, a raw read of the task under `readableProjectSql` that replaces the Phase 14 count.
12. listProjectMilestones: `from` and `to` follow listWorkspaceMilestones' Phase 14 rule (undefined absent; any other value must be a CalendarDate, else INVALID_INPUT field from or to; from after to is field to), validated after limit and cursor so a Phase 14 call keeps its error order.
13. Race binding for these lock-free reads follows 15-03 decision 10: the parked read's backend PID from createServiceRace.holdAt, checked to be `idle in transaction` on a one-connection observer client after the change commits and before the release; describeReadRaces is reused unchanged where its world fits, and the other worlds stay local to the race test file.
