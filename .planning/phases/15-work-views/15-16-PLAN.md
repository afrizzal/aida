## Decisions recorded by this plan

The outline fixes this plan's purpose, its files (`[projectId]/calendar/page.tsx`, `loading.tsx`, `actions.ts`, `src/components/projects/calendar/*`, the two specs) and the scope-neutral export rule; plans 15-04, 15-06 and 15-12 fix the reads, the date math and the frame. Where they are silent, these choices were made inside 15-CONTEXT and bind plan 15-22:

1. **Two reads, own data module.** The Calendar reads the window (`window: serviceWindow(range.from, range.to)`, nothing else but the filters, as 15-04 requires) and the first Unscheduled page in parallel through `loadCalendarData`; the 15-12 grouped loader does not fit (no groups, no counts). The server page and the client reload use the same function with different fetchers.
2. **Unscheduled order and count.** The Unscheduled list is sorted by `title` (A to Z, then key, then id; a TASK_SORTS value both scopes accept, so 15-22 can reuse it), 50 per page. Because the read has no server total (15-04), the heading shows a count only when `hasMore` is false, where the loaded rows are the complete list; otherwise it shows the word alone. Listed for the UI checker (the UI-SPEC says "with count").
3. **Reload after every write.** Success, refusal and UNKNOWN all re-read the window and the Unscheduled list (limit `calendarReloadLimit(loaded)` = max(50, loaded + 1) capped at LIST_MAX). This depth-keeping reload is one `createCoalescedReload` runner per `useCalendarData` mount (revision 1, K92): one run in flight, and every request during a run shares one follow-up run. Every adoption of new server props (a filter, mode or date navigation) bumps an adoption counter held in a ref (`adoptionCountRef`, the name 15-14's data hook uses); a run records the counter when it starts and applies its result only when the counter is unchanged when the reads return, otherwise it drops the result, so an old range or filter never overwrites the new one. Because a task-change signal can start a reload at any moment, this guard is what keeps a signal reload from putting an old window's tasks back (orchestrator cross-plan rule from the 15-14 revision; E2E test 16).
4. **One write queue.** Shifts, drops, Set date and adds run one at a time in request order through `useCalendarMoves`; the item's Move button (or the day's Add button) is pending from the request until the reload after its own write has finished; pointer drag is off while any write is queued or running. A call is never repeated by itself (K88).
5. **Focus fallback.** After a write the Move button of the item gets focus when it is on screen; otherwise the day cell of the item's new placement when that day is in the visible range (the item may sit behind "+{n} more"), else the cell it left, or the Unscheduled heading for a task that came from the Unscheduled list. Day cells carry `tabIndex={-1}` and the id `calendarDayCellId(day)` for this.
6. **Set date dialog.** Surface `dialog`: a returned refusal stays in the dialog with the typed date kept (kind field: a 12px destructive line under the input linked by aria-describedby, aria-invalid, focus on the input; other kinds: the callout, focused; CONFLICT and NOT_FOUND offer Reload, which reloads the Calendar and then takes a new snapshot of the task's version and dates from the reloaded data, or closes the dialog when the task is no longer loaded; that explicit Reload is the only thing that replaces the snapshot, decision 23). Success and UNKNOWN close the dialog and continue in the move flow (UNKNOWN's warning shows above the grid). An empty or unparsable date keeps "Set date" aria-disabled, described by the dialog description ("Pick a new date…"); a date equal to the current one closes the dialog with no call; a chosen day whose shifted other end would leave the representable years (setCalendarDate throws a RangeError) shows the service's INVALID_INPUT view, resolved locally through resolveProjectOutcome without a call (the plan 15-13 precedent for a refusal the service would give anyway).
7. **Range and view state.** Month sets `mode` to null and Week to "week"; Today sets `date` to null; previous and next set `date` to `calendarStep(mode, date ?? today, ±1)`; every href is `viewQueryHref(pathname, { ...query, ... })` (15-12: view-query.ts is not edited). The Calendar writes no view state (CALENDAR is version only, 18.7); it still uses `useViewConfig` for the saved-view chip, Modified and the 15-19 bridge snapshot, and never calls a setter. Today is the frame loader's value (todayForViews computed once per request on the server, plan 15-12); the page does not compute it a second time, and no client module computes it.
8. **Add on a day.** One popover per day cell, anchored on its Add button; `addCalendarTaskAction` copies only `title` and `dueDate`, so the new task takes createTask's defaults and no filter value (D-13 says only the due date). Days outside the stored range are display-only and get no Add button; they stay drop zones, so a shift there is sent unchanged and refused by the service (15-06 decision 5).
9. **Overflow.** Month cells show the first three items in window order and a "+{n} more" button with a popover listing every task of the day; items in the popover are not draggable (Move menu only). Week cells list every task.
10. **Announcements.** "{n} tasks shown" (through `resultsCountAnnouncedTasks`, so one task reads "1 task shown", K98) with n the number of tasks drawn on the grid is announced only after the filters changed (adoption of new server props whose filter part differs); a range change is announced by the aria-live heading; with `tooMany` the too-many text is announced instead.
11. **Honest empty text.** The Unscheduled empty line is "Every task has a date." only when no filter is set; with a filter it is the existing "Tasks no match body" row, because "every task" would be untrue under a filter. "A filter is set" means `viewFilterCount(query)` above 0 (15-12 K94 hand-off; in project scope it equals filterValueCount of the filters).
12. **Too-many notice.** Its "Clear filters" button renders only while a filter is set (`viewFilterCount(query)` above 0); the copy already offers "pick a shorter range", which the range controls do.
13. **Archived.** Move, Add and Set date buttons stay visible and aria-disabled, described by one visible 12px muted line "Restore the project to change this." (id `CALENDAR_ARCHIVED_REASON_ID`) under the toolbar; the Move button also carries its own reason through MoveMenu (orchestrator note for 15-16; P12 disabled-with-reason).
14. **Grid semantics.** role grid with role row, columnheader and gridcell as UI-SPEC Surface 12 states; every control stays in the normal Tab order (Add, title links, Move buttons, "+{n} more"); no arrow-key cell navigation is built because the UI-SPEC names none and every action is reachable by Tab; the screen-reader check stays a manual item.
15. **Items.** The item root carries the drag props and `data-calendar-item`; the Move button carries the drag-ignore attribute; the title link may start a drag after 4px and a plain click still opens the task. Each day number is aria-hidden beside an sr-only full date (data, not copy).
16. **No copy added.** Every string exists in ui-copy.ts (rows of "Calendar and Timeline", "Move menus and announcements", "Views, groups, bulk", "Task drawer and page" Property labels and Title errors, the shared states). This plan does not edit ui-copy.ts or its test, so it shares no file with 15-11 or 15-13. A missing string stops the plan and is reported (convention 3); a gap row would then be appended after the last one, marked "written by plan 15-16", under the same one-checkout rule 15-12 recorded.
17. **E2E shape.** Every scenario that is not about today uses the month after today (`ANCHOR` = `calendarStep("month", dayOffset(0), 1)`, days reached with `dayOffset(daysBetween(dayOffset(0), ANCHOR) + n - 1)`), so all seeded dates and their ±7-day moves stay inside one month grid whatever today is; those tests always open the page with an explicit `?date=`, so they never depend on the server's today. The tests that are about today (main spec tests 1 and 2, the time-zone spec) read today from the server-rendered marker (decision 20). Equivalence tests seed twin projects with identical tasks, run the mouse path on one and the keyboard path on the other, and compare the stored dates read through Prisma after a reload. The spec sets a 1920x1400 viewport so a whole month grid and the Unscheduled panel are on screen. Seeding stays in `tests/e2e/support/projects.ts`; the 1,000-bound test seeds TASK_WINDOW_MAX + 1 tasks through it.
18. **Extra files** (deviation, inside the outline's `calendar/*` directory or a new test with no other owner, checked with grep): `calendar-data.ts`, `calendar-model.ts`, `use-calendar-data.ts`, `use-calendar-moves.ts`, `calendar-grid.tsx`, `calendar-item.tsx`, `calendar-range-controls.tsx`, `set-date-dialog.tsx`, `add-on-day-popover.tsx`, `unscheduled-panel.tsx`, `calendar-view.tsx`, and `tests/unit/project-calendar.test.ts`.
19. **Task-change signal (revision 1, K92, S5-W1).** The runner of decision 3 lives in `useCalendarData`, so the data API's `reload` is that runner's `request` and every depth-keeping reload of the Calendar goes through it (the write queue's reload after a move, Set date or add, and the signal). The hook itself does not subscribe; the composing view does, once, in its own file: the project `CalendarView` body calls `useTasksChanged(() => { void data.reload(); })` (the K92 `runner.request()` call), ignores the detail (a task moved into or out of this project changes this window too), and makes no announcement, no focus move, no `useViewReload().reload()`, no router refresh and no frame remount. The workspace Calendar (15-22) subscribes the same way in its own file with the same hook, so no runner wraps another and no event is handled twice. The Calendar's own writes keep their own reload and emit no signal. The range controls are disabled only while a range or filter navigation is pending, not while a reload runs, so a range change can arrive during a signal reload; decision 3's adoption counter drops that reload's result.
20. **Today in the specs (revision 1, S6-I1).** Server and test runner read the same machine clock and DEFAULT_TIME_ZONE is "UTC", but a fixed `TODAY` computed once in the test process and compared with a later render fails without a defect when a run crosses UTC midnight. The specs therefore read today from the server-rendered grid: the helper `serverToday(page, before)` returns the `data-drop-day` of the one gridcell holding the "Today (sr-only)" text and checks it lies in `[before, after]`, two `dayOffset(0)` readings taken immediately before the navigation and right after the read (equal unless a UTC midnight passed during that navigation); every check that depends on today uses the marker of the same render, and a task seeded "today" keeps its seeded day, with its expected placement computed from that day and the render's range. In a run that crosses no midnight every check equals the strict one (the today cell holds the marker and the today task).
21. **Load more never overlaps a reload (revision 1, found during the K92 revision).** With reloads now able to start at any moment, two races are closed inside `useCalendarData` (internal; the API is unchanged): a reload run first awaits a Load more in flight, so its Unscheduled depth counts the appended rows, and `loadMoreUnscheduled` first awaits the run in flight, if any, before it reads the cursor (the hook keeps the current run's promise in a ref; waiting never requests a reload); a Load more applies its page only when `adoptionCountRef` is unchanged since it began, so rows read under an older filter or range never join the new list (it then returns `{ firstNewTaskId: null, hasMore }` of the current state and the panel moves focus to the Unscheduled heading if the Load more button is gone).
22. **Signal generation across adoption (revision 2, K102, 15-12 decision 22).** Adopted server props may have been read before a task change whose signal reload decision 3's guard then drops (or whose reload read the old range), leaving the new range or filter stale. `useCalendarData` therefore creates exactly one `createAdoptionWatch()` per hook mount, held in a ref beside the runner (the hook is called once per view body, so this is one watch per body mount), and its API gains `beginNavigation(queryKey: string)`: it calls `watch.begin(queryKey)` unless the key equals the adopted queryKey (a navigation to the query already shown adopts nothing, so no record is left behind). The adoption step (new `initial` with a different queryKey) runs in this order: update the base and window refs from the same render, increment `adoptionCountRef`, replace both states, call `onAdopted`, then call `watch.shouldReloadAfterAdopt(initial.queryKey)` exactly once and, when it is true, `void runner.request()`; the Calendar always adopts the props as they are (no grouping or sort to mismatch), so a true result always requests. The follow-up records the incremented counter when it starts, so its result applies, while a run that started before the adoption is still dropped by decision 3; it announces nothing and moves no focus (decision 10's filter announcement stays the only one, so after a held filter navigation it counts the adopted props). The composing view starts every navigation through one local helper `navigate(href, nextQuery)` that calls `data.beginNavigation(viewQueryKey(nextQuery))` and then `router.push(href, { scroll: false })` inside the navigation transition: ViewToolbar's `onNavigate(href, nextQuery)` is `navigate` (filters, chips, the saved-view chip and the popover's Clear filters), CalendarRangeControls' onToday, onStep and onMode call it with `viewQueryHref(pathname, nextQuery)`, and so does the too-many notice's "Clear filters" (Task 3); `router.push(` appears nowhere else in calendar-view.tsx. The Calendar renders no Link that changes its own query. Client reads (Load more, the runner's reloads) need no watch: a signal during them requests a runner reload that starts later. The frame's Reload is already covered by 15-12 (view-frame.tsx). Residual stated by 15-12: a signal that lands during a navigation into the Calendar from another page (a tab link) is not a navigation this view starts; the next signal or Reload corrects it. The workspace Calendar (15-22) gets the watch through the same hook and only calls `data.beginNavigation` before its own navigations. Proven by E2E test 17.
23. **Set date keeps its opening snapshot (revision 3, K104, CX2-1).** An open editor keeps the version it opened on. `SetDateDialog` takes a snapshot of its `task` prop (id, key, title, dates and version, as loaded) when it opens and from then on reads only the snapshot: the label (setDateTarget), the prefill, the current-dates list, the paired-date math (setDateSubmission of the snapshot's dates and the typed value, so the other end moves by the same number of days measured from the dates the user saw) and the expectedVersion it sends (the dialog calls `submit(snapshot, args)`, as 15-17's Set dates does). The `task` prop keeps its meaning (the latest loaded copy by id, or null), so the view call sites and 15-22 need no change, but a change of that prop, null included, never replaces the snapshot and never closes the dialog: the task-change signal's reload, the K102 adoption follow-up and every other runner reload are background reloads. A submit on a stale snapshot is refused CONFLICT by the service (NOT_FOUND when the task is gone), stays in the dialog with the typed date kept and stores nothing. Only the user's explicit Reload on that refusal (the OutcomeCallout's Reload in the dialog) awaits onReload and then, on the first render with `reloading` false, reads the latest `task` prop: when it is null the dialog closes with focus on the opener when that is still in the document, else on the Unscheduled heading (`UNSCHEDULED_HEADING_ID`), as 15-17 does; otherwise the latest task becomes the next snapshot, the current-dates list and the label show the newest dates, the input becomes the pure `setDateReloadInput(previous, latest, raw)` of calendar-model.ts (the one-input counterpart of 15-17's `setDatesReloadInputs`: an input still equal to the old snapshot's target end, never edited or typed back, empty for an undated task, shows the newest target end; any other input keeps the typed value), the refusal clears and focus goes to the input, so the next submit uses the new version. The current-dates list is a `dl` with `data-set-date-current` under the description (`text-[12px] text-muted-foreground`), one row per non-null end of the snapshot: the term from the "Property labels" Start date or Due date part, the value `formatCalendarDate(day, "full")` with `data-day` set to the YYYY-MM-DD day; an undated snapshot shows no list. It adds no copy (existing Property labels and the existing formatter) and is listed for the UI checker as an addition to Surface 12's one-input dialog, made so that the dates a submit is measured from are visible and the explicit Reload visibly shows the newest ones. Not affected: the Move menu's shift items are not editors (they read the version and dates at the click from the rendered data) and the add popover creates a task and sends no version.
