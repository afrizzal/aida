## Decisions recorded by this plan

The outline fixes the migration name, the files, the model and field names and section 18.9's object names; this plan uses them exactly. Where the outline is silent, these choices were made inside 15-CONTEXT (charter rule 4 where schema, privacy or authorization is touched):

1. **ProjectViewState_owner_kind_key is written by hand and not declared in the schema.** Prisma refuses an optional field in `@@unique` and cannot express NULLS NOT DISTINCT. The index is listed in the migration header and above the model with the keep rule every hand-written object of this repository carries. The post-deploy `prisma migrate diff` output is recorded; if Prisma 7.8 reports a drop of this index, the header and the model comment also say that every later generated migration must delete that drop by hand (the treatment of the full-text search objects since Phase 11).
2. **Two plain Prisma indexes** `SavedView_organizationId_projectId_idx` and `ProjectViewState_organizationId_projectId_idx` (`@@index([organizationId, projectId])`), as ProjectFavorite has: PostgreSQL checks a RESTRICT relation on every Project delete and plan 15-08's K90 step deletes by (organizationId, projectId); neither unique index leads with those columns. They change no rule of section 18.9.
3. **ProjectViewState.id and updatedAt have no database default** (`@default(cuid())` and `@updatedAt` are client-side, the Phase 14 convention); createdAt has the database default. Plan 15-08's raw upsert supplies id and updatedAt.
4. **C5 site mapping.** The outline's six sites reach the table through eight statements, because two shared helpers sit between them and the table (see "C5 call sites" below). All eight get the INBOX term (D-17 "every read and write"), and `saved-views-scope.test.ts` enumerates all eight from the source plus a behaviour case per site where data can tell the difference.
5. **Snapshot keys.** `projectTableSnapshot` gains the keys `SavedView` (that organization's rows of scope PROJECT only, as the outline fixes) and `ProjectViewState` (all rows of the organization), through one per-model extra filter constant `SNAPSHOT_WHERE` next to SNAPSHOT_ORDER.
6. **`tests/integration/projects-schema.test.ts` joins files_modified.** Its snapshot test pins the key set to the 18 Phase 14 tables; section 18.9 adds two, so that one assertion and its title change in the commit that extends the snapshot, keeping every commit green. No other wave-2 plan lists the file.
7. **`tests/support/project-hard-delete.ts` stays unchanged.** It does not delete view rows, so the RESTRICT relations refuse it for a project that has one; a test that seeds view rows deletes that project through `deleteProject` after plan 15-08 (which owns K90).
8. **Scratch database name** `aida_p15_work_views`; **back-relation names** `Project.savedViews`, `Project.viewStates`, `organization.projectViewStates`, `user.projectViewStates`.
9. **CHECK forms:** `SavedView_scope_project_check` as the equality of `"scope" = 'INBOX'` and `"projectId" IS NULL`; `SavedView_project_private_check` as `"scope" <> 'PROJECT' OR "visibility" = 'PRIVATE'`; `SavedView_project_payload_size_check` as `"scope" <> 'PROJECT' OR octet_length("filters"::text) <= 4096`; `ProjectViewState_state_size_check` as `octet_length("state"::text) <= 4096`; `ProjectViewState_kind_scope_check` as `("viewKind" <> 'FILES' OR "projectId" IS NOT NULL) AND ("viewKind" <> 'PROJECT_LIST' OR "projectId" IS NULL)`.
10. **The ON CONFLICT inference is proven here** (Task 3), because section 18.3 freezes the 15-08 save as one raw `INSERT ... ON CONFLICT` on the key's columns. If PostgreSQL cannot infer the NULLS NOT DISTINCT index for a null projectId, the executor stops and reports; K82's write path would need a contract change.
11. **Populated-data proof on the Phase 12.1 harness** (own container, migrations through `20261113100000_projects_foundation`, raw-SQL seed local to the test file, then only this migration), because the shared container is always migrated to the newest folder.
