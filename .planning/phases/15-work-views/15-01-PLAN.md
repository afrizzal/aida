### 18.6 Date semantics (D-13, D-15, K79, K80, K87, K96)

- Span of a task: from its start date (else its due date) to its due date (else its start date). A task with neither date is unscheduled. A window read returns the tasks whose span overlaps the window, both ends inclusive.
- Calendar placement: a task appears once, on its due date, else on its start date; unscheduled tasks sit in the Unscheduled list.
- Move by n days (pointer drag or a Move menu item, Calendar and Timeline): every non-null end shifts by n days in one `setTaskDates` call with `expectedVersion` (K80); a null end stays null. A result outside CALENDAR_DATE_MIN to CALENDAR_DATE_MAX is refused by the service as INVALID_INPUT.
- Calendar "Set date…": the chosen day becomes the due date when the task has one, else the start date, and the other end moves by the same number of days, so the duration is kept; on an unscheduled task it sets the due date only. Timeline "Set dates…": sets either end directly, start not after due (client check; the service decides with INVALID_DATE_RANGE). Add on a day: createTask with that day as the due date (at workspace level in a project the user picks first).
- Today: `todayInTimeZone(DEFAULT_TIME_ZONE, now)`, computed on the server for each request (UTC until AIDA-98). Weeks start on Monday (WEEK_START_DAY 1, the `getUTCDay` number of Monday).
- Calendar URL `?mode=month|week&date=YYYY-MM-DD` (CALENDAR_MODES; absent or invalid: month and today). Month mode shows the Monday-to-Sunday weeks that cover the month containing `date` (28 to 42 days); week mode shows the Monday-to-Sunday week containing `date`.
- Timeline URL `?from=YYYY-MM-DD`: the window starts on the Monday on or before `from` (absent or invalid: the Monday of the week before today). Windows by zoom (TIMELINE_WINDOWS): day 28 days, week 112 days, month 53 weeks (371 days; K96): from the Monday start to `endOfWeek` (the Sunday on or after) of the day before `addCalendarMonths(start, TIMELINE_WINDOWS.month.months)`, where 29 February maps to 28 February. Because the start is a Monday and 12 calendar months are 365 or 366 days, the month window is always exactly 371 days and always contains the 12 calendar months from the start; TIMELINE_WINDOWS.month stays `{ months: 12 }`. Previous and next shift the Monday start by exactly one window length at every zoom (28, 112 or 371 days), so consecutive windows tile with no gap and no overlap (plan 15-06 owns the date functions and the tiling test). Every window is at most TASK_WINDOW_MAX_DAYS (400) long; the longest, 371 days, stays under it.
- Above TASK_WINDOW_MAX tasks the Calendar grid and the Timeline are replaced by the "too many tasks" notice; nothing partial is drawn (K87).
- Dates stay CalendarDate strings end to end and are never converted to local time; display uses `Intl.DateTimeFormat("en-GB", { timeZone: "UTC" })` on the UTC midnight of the date.

### 18.7 Payload and view-state schemas (D-17, D-18, K81, K82; `src/lib/projects/view-payload.ts`)

- Scope of a view state: `project` (a row with a projectId) or `workspace` (projectId null). Allowed kinds: with a project VIEW_KINDS_WITH_PROJECT (LIST, BOARD, TABLE, CALENDAR, TIMELINE, FILES); without one VIEW_KINDS_WITHOUT_PROJECT (LIST, BOARD, TABLE, CALENDAR, TIMELINE, PROJECT_LIST). Any other pair is INVALID_INPUT field viewKind.
- The key `(organizationId, userId, projectId, viewKind)` is unique with NULLS NOT DISTINCT and read one way by every plan (C2): the workspace Tasks forms list, board and table (`?form=`, WORKSPACE_TASK_FORMS) are the rows LIST, BOARD and TABLE with projectId null (P2); the workspace Calendar and Timeline are CALENDAR and TIMELINE with projectId null; the project list form is PROJECT_LIST with projectId null; FILES exists only with a project. No other kind is added.
- View state version 1 is `{ version: 1, ...keys }` with the keys allowed by kind (the same in both scopes): LIST grouping, sort, collapsed; BOARD collapsed; TABLE grouping, sort, columns, collapsed; TIMELINE grouping, zoom, collapsed; FILES form; PROJECT_LIST form; CALENDAR none (version only).
- Saved-view payload version 1 is `{ version: 1, view, filters, ...keys }`: `view` is a TASK_VIEW_KINDS value, `filters` is required (it may be the empty object), and the other keys are those the view's kind allows in project scope. It is stored in the SavedView `filters` column with scope PROJECT and visibility PRIVATE.
- Values:
  - `grouping`: a TASK_GROUP_BYS value, or null for no grouping. Project scope: LIST status, assignee, priority, milestone (null refused); TABLE null, status, assignee, priority, milestone; TIMELINE null, status, assignee, milestone. Workspace scope: LIST status, project, assignee, priority (null refused); TABLE null, status, project, assignee, priority; TIMELINE null, status, assignee, milestone, project.
  - `sort`: in project scope every TASK_SORTS value; in workspace scope every value except manual.
  - `columns`: distinct TABLE_COLUMNS values that include `title`; project scope refuses `project`.
  - `collapsed`: 0 to VIEW_COLLAPSED_MAX (50) distinct group keys, each GROUP_NONE_KEY (`~none`, the null group) or a string that matches the section 2 id pattern (ids and set values); for BOARD each must be a TASK_STATUSES value. A key that names no current group is ignored by the view.
  - `zoom`: a TIMELINE_ZOOMS value. `form`: for FILES a FILES_FORMS value, for PROJECT_LIST a PROJECT_LIST_FORMS value.
  - `filters` (saved views only): an object with at most the keys statuses (TASK_STATUSES values), priorities (TASK_PRIORITIES values), assigneeUserIds (well-formed ids or null), labelIds (well-formed ids) and milestoneIds (well-formed ids or null); each present array holds 1 to VIEW_FILTER_VALUES_MAX (50) distinct values.
- Both schemas fail closed. A value that is not a plain object, a missing required key, an unknown key, a key the kind does not allow, a value outside its set, a duplicate, an empty filter array or a count above its bound is refused: INVALID_INPUT field payload or state on a write, unreadable on a read. A `version` other than the number 1 (missing included) is an unknown version: on a read it opens as unreadable (a saved view shows its name and a delete control) and nothing is applied; a write of it is INVALID_INPUT. A key whose value is undefined counts as absent.
- Size: the canonical value's serialized size is at most VIEW_PAYLOAD_MAX_BYTES (4096), measured like `octet_length(value::text)` of the jsonb (compact JSON plus the space PostgreSQL prints after every colon and every comma, counted in UTF-8 bytes). The CHECKs of section 18.9 repeat the limit, and plan 15-02's schema test compares the measure with the database for a fixed value.
- Canonical form: the validators return enum arrays in set order (TASK_STATUSES, TASK_PRIORITIES, TABLE_COLUMNS), id arrays in code-unit order with null last, and collapsed keys in code-unit order; services store exactly that value, so equal settings compare equal.
- Defaults (`defaultViewState`; a stored key overrides its default, an absent key takes it): LIST grouping status, sort manual (workspace dueDate), collapsed empty; BOARD collapsed empty; TABLE grouping null (workspace status), sort manual (workspace dueDate), columns key, title, status, priority, assignee, dueDate (workspace also project), collapsed empty; CALENDAR version only; TIMELINE grouping null, zoom week, collapsed empty; FILES form grid; PROJECT_LIST form grid.
- Effective settings of a task-view page (plan 15-12): filters come from the URL; the other keys come from the open saved view's payload when `?saved=` names a readable view of the actor, else from the stored view state, else from the defaults. While a saved view is open, changes are not written to view state.
- Module names (view-payload.ts): `parseSavedViewPayload(raw)`, `parseViewState(kind, scope, raw)`, `parseViewFilters(raw)`, `isViewKindAllowed(kind, scope)`, `defaultViewState(kind, scope)`, `jsonbTextByteLength(value)`; tables `VIEW_STATE_KEYS`, `VIEW_GROUPINGS`, `VIEW_SORTS`, `VIEW_COLUMNS`, `VIEW_FORMS`, `VIEW_FILTER_KEYS`; types `ViewStateScope` ("project" or "workspace"), `ViewFilters`, `SavedViewPayload`, `ViewState`, `JsonValue` and `ViewParseResult` (`{ ok: true, value }`, or `{ ok: false, reason }` with reason UNKNOWN_VERSION, INVALID with a `path`, or TOO_LARGE with `bytes`).
