## Decisions recorded by this plan

The outline fixes this plan's purpose, its files and N6; contract sections 18.1 and 18.7 fix the URL parameter names and the precedence. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched) and bind the later view plans:

1. **One grammar module for every task view and workspace page.** `view-query.ts` parses and serializes the whole frozen grammar of 18.1 now (status, priority, assignee, label, milestone, project, saved, mode, date, from, form), because the outline makes 15-12 its only owner and 15-16, 15-17, 15-20 and 15-22 cannot edit it. The scope decides which parameters apply: project scope reads status, priority, assignee, label, milestone, saved, mode, date and from; workspace scope reads status, priority, assignee, project, mode, date, from and form.
2. **Strict parsing (N6).** A parameter given more than once, an empty or unknown part, a malformed id, a value outside its set, more than VIEW_FILTER_VALUES_MAX (50) values (LIST_MAX for project) or a date that parseCalendarDate refuses drops the whole parameter; duplicates collapse; an empty string counts as absent; the output is canonical (enum lists in set order, ids in code-unit order with null last, as parseViewFilters returns them). GROUP_NONE_KEY ("~none") stands for null in assignee and milestone. Dropped names are listed in `query.dropped` for tests only; nothing is shown for them.
3. **`?saved=` statuses.** None when the parameter is absent; notAvailable when it is malformed (no service call), when openProjectSavedView returns NOT_FOUND, or when the readable payload's view kind is not this tab's kind (fail closed: nothing of another view is applied); unreadable when the view is not readable (nothing applied, chip with its name); open otherwise (payload applied, stale flag kept). MEMBERSHIP_ENDED from the open renders the MEMBERSHIP_ENDED callout; any other refusal throws to the error boundary.
4. **Filters only from the URL** (18.7 wording). Opening a saved view therefore means navigating to its tab with its filters written into the URL plus `saved` (`savedViewQuery`, used by plan 15-19). A `?saved=` link without the filters applies the payload's other keys and shows "Modified" because the page's filters differ from the payload, which is true.
5. **No view-state write while `saved` is in the URL** (open or unreadable): changes stay in the page and are lost on reload (UI-SPEC researcher choice 11). Close saved view removes only `saved` from the URL and keeps the filters; focus then goes to the element carrying `data-saved-views-trigger` (plan 15-19's Views button) when present, else the Filter trigger.
6. **Stale URL filters.** A label or milestone id that is not in the project's labels or milestones, or an assignee id that is not an eligible assignee, keeps matching nothing (service rule) and raises the existing "View stale notice"; its chip names it "Someone" (people, N2 fallback) or the new gap rows "Unknown label" and "Unknown milestone" (G{n}, marked "written by plan 15-12"). The two gap rows are appended to `ui-copy.ts` and pinned in `project-copy.test.ts`, files plan 15-10 also appends to in this wave; that sharing is allowed only because the orchestrator executes wave-4 plans one at a time on one checkout, every edit is append-only, and each plan takes the next free G number at execution time.
7. **Saving view state.** Save on change, no timer: a serialized saver keeps at most one save in flight, a newer state replaces the queued one, and a state canonically equal to the last saved one is not sent. The saved state is complete (every key of the kind), canonical through parseViewState. A refused save keeps the arrangement on screen (reverting would move the page under the reader before they can act, and every code a preference save can return, NOT_FOUND, MEMBERSHIP_ENDED, a deadlock CONFLICT or INVALID_INPUT, is resolved by Reload), shows the callout of surface view, drops the queue and blocks the settings controls until reload; UNKNOWN or a rejected call follows K88 (reload at once, controls blocked until it completes).
8. **Collapse rules.** A grouping change resets `collapsed` to empty and saves grouping and collapsed in one state. A save keeps only collapsed keys that name a current group and at most VIEW_COLLAPSED_MAX (50) of them in code-unit order; beyond 50 the extra collapses hold for the page only (manual item).
9. **Data loading.** The server page reads the group counts (listProjectTasks with groupCounts and limit 1) and, with at most 4 reads at a time, the first page (50 rows, LIST_DEFAULT) of every expanded group with a count above 0. The client List stays mounted across filter navigation (its key is project, kind, saved id and the reload generation, never the query): when new server props arrive for a new query it adopts their groups if their grouping and sort equal its own, else it reloads with its own settings through the List read action; a re-render for the same query (an action's revalidation) changes nothing on screen; Reload remounts it with fresh server props. Grouping or sort changes, expanding a group whose rows were never loaded, Load more and the reload after quick add go through the same grouped-read functions on the client.
10. **Action files.** `view-actions.ts` holds saveProjectViewState, createTask and setTaskMilestone. setTaskMilestone is added to the 18.1 row of this file (the 18.1 rule "a plan that needs one more operation adds it and records it"), because createTask takes no milestone and the milestone group's quick add needs it. - **Effective settings.** `resolveViewConfig({ kind, scope, stored, saved })` returns `{ state, source, persist }` with every key of the kind present (defaults from `defaultViewState`); filters always come from the URL. `savedViewStatus(kind, query, opened)` gives none, notAvailable (missing, foreign, malformed or another kind's view), unreadable or open (with stale); `viewNotices` gives "savedNotAvailable", "savedUnreadable", "staleFilters". persist is false while `saved` is in the URL: nothing is written to view state then.
- **Project task-view loader (15-14 to 15-17).** `loadProjectViewFrame({ projectId, kind, searchParams })` from `src/lib/project-ui/load-view-frame.ts` does the 18.1 reads (loadProject, getProjectViewState, openProjectSavedView, listLabels, every page of listProjectMilestones and listEligibleAssignees) and returns `{ actor, project, archived, query, config, saved, notices, options, names, today }` or null for MEMBERSHIP_ENDED (render `MEMBERSHIP_ENDED_VIEW`); the page then makes its own task reads with `frame.query.filters`. Workspace pages (15-20, 15-22) write their own loader with getWorkspaceViewState and scope "workspace" and no saved view.
- **Frame composition (client).** Wrap the view in `ViewFrame({ resetKey, reloadFocusId, children })`; it mounts the page's one `ViewAnnouncerProvider` (do not mount another) and `useViewReload()` gives `{ reload, reloading }` (refresh, remount, focus reloadFocusId: `PROJECT_HEADING_ID` in a project). resetKey is `${projectId}|${kind}|${savedId}`: never include the query, so local settings survive filter navigation. Use `useViewConfig({ scope, kind, projectId, config, filters, saved, saveState })` for settings: setters `setGrouping` (resets collapsed), `setSort`, `setColumns`, `toggleCollapsed`, `setZoom`, plus `setCurrentGroupKeys`; it saves through one serialized latest-wins saver (`saveState` is the page's `saveProjectViewStateAction.bind(null, projectId, KIND)`), exposes `outcome`, `blocked` (disable the settings controls) and `modified`, and publishes the bridge snapshot.
- **Toolbar.** `ViewToolbar({ scope, kind, pathname, query, options, grouping?, sort?, columns?, saved, modified, blocked, pending, start?, end?, onNavigate })`; grouping, sort and columns are `ToolbarSelect` `{ value, options, onChange }` (options from VIEW_GROUPINGS, VIEW_SORTS, VIEW_COLUMNS of view-payload for the scope and kind; omit what the view lacks: Board and Calendar pass no grouping or sort); `start` takes 15-13's "Select all loaded" checkbox, `end` takes the Calendar mode and range controls and the Timeline zoom; `options` is `ViewFilterOptions` (workspace passes `projects` and no labels or milestones). Filter changes navigate through `onNavigate(href)` wrapped in the view's transition. Render `ViewNotices({ notices, saved })` under the toolbar and the outcome callout below it.
- **Groups and grouped reads.** `GroupHeader({ name, label, count, collapsed, controlsId, disabled, onToggle })` with `GroupLabel` and `groupDisplayName` from `view/group-label.tsx`; `groupKeyOf` and `groupValueOf` map null to "~none". `loadGroupedTasks(fetch, { base, sort, grouping, collapsed, pageSize? })`, `loadGroupPage` and `appendGroupPage` from `view/group-data.ts` take any fetcher returning a listProjectTasks or listWorkspaceTasks result (15-15 grouped Table, 15-20 workspace list with `base` including projectIds); grouping null is not handled there (read one flat page directly).
- **Quick add.** `QuickAdd({ label, disabled, onSubmit, onAdded })` with `runQuickAdd({ title, values, create, setMilestone })` and `quickAddValuesFor(grouping, value)` (null means not offered: project grouping); `quickAddTaskAction` and `setQuickAddMilestoneAction` in `[projectId]/view-actions.ts` are reusable by Board (15-14) and Table (15-15) instead of new createTask actions. Hide it in archived projects.
- **List extension (15-13).** `ListRow` has a `leading` slot for the row checkbox; `ListGroup` keeps rows of collapsed groups in memory but hidden; `ListView` owns the groups state and the toolbar `start` slot; 15-13 adds `bulk-bar.tsx`, its selection module and `bulkUpdateTasks` to `list/actions.ts` (keep `loadListTasksAction` unchanged) and reloads the groups after a bulk success the way quick add does.
- **Saved views UI (15-19).** Read the open view through `useViewFrameSnapshot()` from `view/view-frame-bridge.ts` (`{ scope, kind, projectId, filters, state, saved, modified, payload }`; `payload` is what Save or Update stores, null if it cannot be built); register the unreadable notice's delete with `registerSavedViewDeleteHandler(handler)` (the "Delete view" button appears only while a handler is registered); open a view by navigating to `viewQueryHref(projectPath(projectId, TASK_VIEW_TABS[payload.view]), savedViewQuery(id, payload))`; put `data-saved-views-trigger` on the Views button (focus target after "Close saved view"). The chip, its Close button, Modified and the three notices are already rendered by every view through this frame; 15-19 adds no notice.
- **Rows and dates.** `TaskDueDate({ dueDate, status, today })` and `taskDueState` in `view/task-due-date.tsx` (overdue: earlier than today and not DONE) for Board cards and Table cells; `today` comes from the loader (`todayForViews` on the server).
