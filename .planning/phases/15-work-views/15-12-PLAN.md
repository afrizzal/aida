## Decisions recorded by this plan

The outline fixes this plan's purpose, its files and N6; contract sections 18.1 and 18.7 fix the URL parameter names and the precedence. Where they are silent, these choices were made inside 15-CONTEXT (charter rule 4 where privacy or authorization is touched) and bind the later view plans:

1. **One grammar module for every task view and workspace page.** `view-query.ts` parses and serializes the whole frozen grammar of 18.1 now (status, priority, assignee, label, milestone, project, saved, mode, date, from, form), because the outline makes 15-12 its only owner and 15-16, 15-17, 15-20 and 15-22 cannot edit it. The scope decides which parameters apply: project scope reads status, priority, assignee, label, milestone, saved, mode, date and from; workspace scope reads status, priority, assignee, project, mode, date, from and form.
2. **Strict parsing (N6).** A parameter given more than once, an empty or unknown part, a malformed id, a value outside its set, more than VIEW_FILTER_VALUES_MAX (50) values (LIST_MAX for project) or a date that parseCalendarDate refuses drops the whole parameter; duplicates collapse; an empty string counts as absent; the output is canonical (enum lists in set order, ids in code-unit order with null last, as parseViewFilters returns them). GROUP_NONE_KEY ("~none") stands for null in assignee and milestone. Dropped names are listed in `query.dropped` for tests only; nothing is shown for them.
3. **`?saved=` statuses (K93).** `savedViewStatus(kind, query, opened, projectId)`, checked in this order: none when the parameter is absent; notAvailable when it is malformed (no service call), when openProjectSavedView returns NOT_FOUND (opened null), when `opened.projectId !== projectId` (a view of another project, readable or not: a saved view belongs to its project, so on `/projects/Q/list?saved=<view of P>` nothing of P's view is applied, no chip is shown and Update is never offered over Q's filters), or when the readable payload's view kind is not this tab's kind (fail closed: nothing of another view is applied); unreadable when the view is not readable (nothing applied, chip with its name); open otherwise (payload applied, stale flag kept). The loader passes the page's projectId; no privacy changes (an unreadable project's view is already NOT_FOUND), only integrity. MEMBERSHIP_ENDED from the open renders the MEMBERSHIP_ENDED callout; any other refusal throws to the error boundary.
4. **Filters only from the URL** (18.7 wording). Opening a saved view therefore means navigating to its tab with its filters written into the URL plus `saved` (`savedViewQuery`, used by plan 15-19). A `?saved=` link without the filters applies the payload's other keys and shows "Modified" because the page's filters differ from the payload, which is true.
5. **No view-state write while `saved` is in the URL** (open or unreadable): changes stay in the page and are lost on reload (UI-SPEC researcher choice 11). Close saved view removes only `saved` from the URL and keeps the filters; focus then goes to the element carrying `data-saved-views-trigger` (plan 15-19's Views button) when present, else the Filter trigger.
6. **Stale URL filters.** A label or milestone id that is not in the project's labels or milestones, or an assignee id that is not an eligible assignee, keeps matching nothing (service rule) and raises the existing "View stale notice"; its chip names it "Someone" (people, N2 fallback) or the new gap rows "Unknown label" and "Unknown milestone" (G{n}, marked "written by plan 15-12"). The two gap rows are appended to `ui-copy.ts` and pinned in `project-copy.test.ts`, files plan 15-10 also appends to in this wave; that sharing is allowed only because the orchestrator executes wave-4 plans one at a time on one checkout, every edit is append-only, and each plan takes the next free G number at execution time.
7. **Saving view state (K99).** Save on change, no timer. The saver holds `baseline` (the state known stored: the initial stored state, or the state of the last save that completed ok; null when unknown), `inFlight` (the state being sent, or null) and `desired` (the latest submitted state not yet sent, or null). The last requested state is `desired` when one is queued, else `inFlight` when one runs, else `baseline`. A submit is dropped only when it is canonically equal (jsonValueEqual) to the last requested state, never merely because it equals the last stored one; otherwise, while a save runs it replaces `desired`, and while idle it is sent at once. When a save completes ok, `baseline` becomes the state it stored and, if `desired` differs from that state, `desired` is sent next, else `desired` is cleared. So with A stored, B in flight and A chosen again, A is queued, sent after B and is the stored result; with C queued between, C is replaced by A and never sent; with B in flight, C queued and B chosen again, nothing more is sent after B. Where the saver lives and how it survives a remount is decision 21 (K100). The saved state is complete (every key of the kind), canonical through parseViewState. A refused save keeps the arrangement on screen (reverting would move the page under the reader before they can act, and every code a preference save can return, NOT_FOUND (including the identity refusal of decision 23, K105), MEMBERSHIP_ENDED, a deadlock CONFLICT or INVALID_INPUT, is resolved by Reload), shows the callout of surface view, drops the queue and blocks the settings controls until reload; UNKNOWN or a rejected call follows K88 (reload at once, controls blocked until it completes).
8. **Collapse rules.** A grouping change resets `collapsed` to empty and saves grouping and collapsed in one state. A save keeps only collapsed keys that name a current group and at most VIEW_COLLAPSED_MAX (50) of them in code-unit order; beyond 50 the extra collapses hold for the page only. This is a decided limit (K98, S5-I2), not a manual item: the bound comes from the frozen view-state schema and collapsedForSave's cap is unit-tested.
9. **Data loading.** The server page reads the group counts (listProjectTasks with groupCounts and limit 1) and, with at most 4 reads at a time, the first page (50 rows, LIST_DEFAULT) of every expanded group with a count above 0. The client List stays mounted across filter navigation (its key is project, kind, saved id and the reload generation, never the query): when new server props arrive for a new query it adopts their groups if their grouping and sort equal its own, else it reloads with its own settings through the List read action; a re-render for the same query (an action's revalidation) changes nothing on screen, and a write made elsewhere (the drawer) reaches the List through the task-change signal (decision 19), not through re-renders; Reload remounts it with fresh server props. 19. **Task-change signal (K92, S5-W1).** `src/components/projects/view/task-change-signal.ts` (no directive; imported by client code only; no package, no storage) exports `TASKS_CHANGED_EVENT` = "aida:tasks-changed", the type `TasksChangedDetail` `{ taskIds?: string[]; projectId?: string }`, `notifyTasksChanged(detail)` (dispatches a `window` CustomEvent with that detail, so it crosses the drawer slot and any React root; does nothing when no window exists), `subscribeTasksChanged(callback)` (adds a window listener passing the detail, returns the unsubscribe function), `useTasksChanged(callback)` (subscribes on mount through subscribeTasksChanged with a ref to the latest callback, unsubscribes on unmount) and `createCoalescedReload(run)` returning `CoalescedReload` `{ request(): Promise<void>; dispose(): void }` (idle: start run; while a run is in flight: mark one follow-up shared by every request in that time; each request's promise resolves when the run that covers it ends; a rejected run is swallowed so later requests still run; after dispose nothing runs and request resolves at once). The List subscribes and requests its body-local depth-keeping `reloadGroups()` through one coalesced runner per body mount; it ignores the detail (a task moved to another project changes this project's groups too); no announcement, no focus move, no frame remount, no router refresh. 21. **One saver per preference key across remounts (K100).** `view-state-saver.ts` keeps a module-level registry (a Map in the module, one per browser tab, cleared only by a document load) of one saver per key `viewStateSaverKey(identity, scope, projectId, viewKind)` (organizationId, userId, scope, the project id or "~workspace" for null, and the kind, joined by "|"; identity per decision 23, K105). `acquireViewStateSaver({ identity, scope, projectId, viewKind, save, initial })` returns the registry's saver for the key, creating it with createViewStateSaver on first use, and rebinds it for the new mount: the latest `save` function is used for later sends (the bound action of the same project and kind, so equivalent); a stopped saver resumes (not stopped, nothing queued, baseline = initial), because a mount carries fresh server props, which is the reload a stop waits for; an idle saver keeps its baseline only when it equals the mount's initial, else sets it to null (unknown, so the next submit is sent even if it equals what the page shows; this covers props read while the last save was still in flight); a busy saver (in flight or queued) keeps everything, so the re-entered view's choices are compared with the old mount's last requested state and start from it (decision 24, K106). `useViewConfig` acquires the saver in a mount effect only when persist is true, attaches its result listener (`attach(listener)` sets the one listener and returns a detach that clears it only while it is still that listener), and on unmount only detaches: nothing in flight or queued is dropped, so the unmounted view's state is still sent in order and the re-entered view's later choice follows it. An outcome that arrives while no view of the key is attached is shown nowhere (the next mount renders the stored state from the server) and a refusal still stops the saver until that mount. Entries are never removed during the tab's life (at most one per key the reader opened, each holding at most three small states). Cross-tab concurrency is not serialized: two tabs saving one key stay last-commit-wins on the server, as plan 15-08's race test proves; this is a stated limitation, not a defect.
22. **Signal generation across adoption (K102).** `task-change-signal.ts` keeps a module-level counter that counts every `TASKS_CHANGED_EVENT` the window sees, whatever dispatched it (`notifyTasksChanged`, any other `window.dispatchEvent` of a CustomEvent of that name, or a test's `page.evaluate`) (Revision 2b). One module-level counting listener for TASKS_CHANGED_EVENT is added to `window` lazily by a private `ensureGenerationListener()` that every exported function runs first (useTasksChanged reaches it through subscribeTasksChanged in its mount effect): at most once per window object (it remembers the window it listens on; a browser has one window, and a unit test that replaces the global window gets the listener moved to the new object), never on the server and never at module evaluation (no window: no listener, no error, the counter stays where it is). The listener adds exactly one per event; `notifyTasksChanged` only dispatches and never increments by itself, so nothing is counted twice; `subscribeTasksChanged` and `useTasksChanged` keep their behaviour. Because every export adds the counting listener before a subscriber can add its own, the counting listener comes first on that window and the generation has already advanced when any subscriber callback runs. `tasksChangedGeneration()` returns the counter. `createAdoptionWatch()` returns `AdoptionWatch` `{ begin(key: string): void; shouldReloadAfterAdopt(key: string): boolean }`: begin records the current generation for the key unless the key already has a record (the earliest unadopted start wins, so a signal between two navigations to one key is never missed) and keeps at most 16 records (a 17th drops the oldest, an abandoned navigation); shouldReloadAfterAdopt removes the key's record and returns true exactly when the current generation is greater than the recorded one, and returns false for a key without a record (first render, a revalidation, a navigation the view did not start). The List creates one watch per body mount (a ref beside its runner); its toolbar `onNavigate(href, nextQuery)` calls `watch.begin(viewQueryKey(nextQuery))` before `router.push`; when it adopts new server props it calls `watch.shouldReloadAfterAdopt(props.initial.queryKey)` and, when true and the props' groups were adopted as they are, requests one depth-keeping reload through `runner.request()`; when grouping or sort differ it already reloads with its own settings after the adoption point, so it consumes the record without a second reload. Client reads need no watch: a signal during a grouping, sort or expand read requests a runner reload that starts later and wins through the body's read counter. The frame's Reload records the generation when its refresh starts and, if a signal arrived before the refresh transition ended, refreshes once more before the remount (at most one extra refresh per Reload). A navigation into a view from another page (a tab link) is not a read the view starts; a signal that lands during it is corrected by the next signal or Reload (stated residual, see Revision 2).
