<objective>
Keep the container healthcheck green under any request volume that reaches `app` through Caddy (review C2), without loosening D-20's public throttle. The container healthcheck moves to a dedicated probe path, `/api/health/probe`, that Caddy refuses to forward, that carries no throttle, and that answers from the same 3-second single-flight snapshot as `/api/health`. Wave 9: it needs plan 08-12's `readHealthSnapshot()`, plan 08-13's last Caddyfile edit, and plans 08-09 and 08-18's compose edits.

Purpose: today the healthcheck shares a 429-capable bucket with other traffic. In production the probe lands in the loopback identity, because Next.js fills a missing X-Forwarded-For with the TCP peer (verified in plans 08-10 and 08-12); in unit tests it lands in the shared bucket. Either bucket can be exhausted by someone: the shared bucket by all public traffic when a misconfigured `TRUSTED_PROXY_HOPS` makes every chain fail closed, the loopback bucket by anything inside the container. A probe path public traffic cannot reach is the only mechanism that holds in both cases without an exemption keyed on a header.

## Why this satisfies D-20 and AIDA-30 (recorded per review C2)

- D-20 asks for an in-memory throttle on `/api/health`, a 2 to 5 second cache with single-flight, no exemption for requests without X-Forwarded-For, and a shared bucket sized so the container healthcheck always passes. `/api/health` keeps all of that unchanged (plan 08-12): 60 per minute per identity, 120 per minute shared, 429 with Retry-After, no exemption. The probe is not an exemption on that endpoint; it is a separate path that no request through Caddy can reach, so the shared bucket's sizing clause holds trivially and can no longer be broken by a misconfiguration.
- D-20's database bound holds for both paths: the probe reads only through `readHealthSnapshot()`, so all health traffic together causes at most one database read per 3-second window per process.
- AIDA-30 asks that `/api/health` be throttled without breaking the container healthcheck. `/api/health` is throttled; the container healthcheck answers 200 under a flood of every bucket it could have shared (Task 1 test, repeated over real HTTP in plan 08-21 and through real Caddy in plan 08-22).
- The protection rests on topology, not on a header: only Caddy is published, and Caddy refuses the path. Direct access to `app:3000` reaches the probe; that is the documented trust boundary (review C7), and even there the probe adds no database load beyond the cache.

Output: the probe route, the Caddy and compose wiring, unit tests for the flood and the wiring, and the operator docs.

|----------|-------------|
| anonymous client -> Caddy -> app | public request volume and headers are attacker-controlled |
| container healthcheck -> app (loopback) | internal probe that decides whether the container is healthy |
| anything on the compose network -> app:3000 | the documented trust boundary; it can reach the probe directly |
