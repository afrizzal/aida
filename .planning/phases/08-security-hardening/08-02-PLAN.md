## Disposable dev database (rule J)

Owner rule J in `.planning/run-loop/PIAGAM.md`, with its "Tafsiran run" paragraph and the "Test dan bukti" line on dev migrations, says:
- The existing `aida-dev-db` container is not touched again: not started, stopped, removed, changed or used for a migration.
- Dev migrations use a new disposable container whose name starts with `aida-test-`, labelled `aida.test=1`, on another free port.
- Cleanup removes only what matches both the label and the prefix.

This plan owns exactly one such container per run. Tasks 1 to 3 use it, and the "Dev database teardown" removes it.

**Start method: plain `docker run`, not `startLabeledPostgres`.** Why:
- `startLabeledPostgres` is built for a database that the same test process stops in its own teardown. This database must stay up across many separate commands over three tasks (`prisma migrate deploy`, the capture script, the CLI generate, `prisma migrate dev`, the session check), and the cleanup script removes it, not a process handle.
- Its options are only `kind`, `database`, `username` and `password`. It cannot pin the `127.0.0.1` bind address or the host port this plan checks free first; Testcontainers maps a host port of its own choosing.
- `--pull never` is a `docker run` flag, so a missing image becomes `blocked (image)` instead of a pull.

The `docker run` below reproduces what J1's `labeledPostgres` sets: the name from `testResourceName`, the labels from `testLabels`, and the tmpfs at `/var/lib/postgresql/data` with `rw` (K109).

From here on, every `docker exec` and `docker inspect` of this plan names `"$DEVDB_NAME"` loaded from `devdb.env`, never a typed name.
8. **Readiness.** Run `docker exec "$DEVDB_NAME" pg_isready -h 127.0.0.1 -p 5432 -U aida` once a second, at most 60 times. It checks over TCP because the image's first-start init server listens only on the Unix socket. Still not ready after 60 tries: record `failed (devdb not ready)` with the output of `docker logs --tail 50 "$DEVDB_NAME"`, never restart the container, run the teardown and stop the plan.
9. **Port identity.** `devdb.ts identity` connects from the host with the repo's `pg` package to database `aida` on `127.0.0.1:<port>` and prints `SELECT system_identifier FROM pg_control_system()`. The value must equal what `docker exec "$DEVDB_NAME" psql -U aida -Atc 'SELECT system_identifier FROM pg_control_system()'` prints. Colima forwards the VM port to the host, so this proves the host port reaches this container and not another listener. On a mismatch: record `failed (port identity)`, run the teardown and stop the plan.
10. **Connection.** `DATABASE_URL=postgresql://aida:$DEVDB_PASSWORD@127.0.0.1:$DEVDB_PORT/<database>` is set on the command only. `.env` is never read or edited.
11. **Liveness.** The data is in tmpfs, so it exists only while this container runs. Never stop, restart or recreate the container between tasks. Before the first dev database step of Tasks 2 and 3, `docker inspect --format '{{.State.Running}} {{index .Config.Labels "aida.test.run"}}' "$DEVDB_NAME"` must print `true <runId>`. Otherwise record `blocked (devdb lost)` for every step that needs the pre-upgrade data, and start no replacement: a new container would hold no 1.6.22 data.

## Dev database teardown

This is the only way this plan removes a Docker resource. It runs once:
- at the end of Task 3 (step 6);
- at every earlier stop of the plan after Task 1 created the scratch directory, whatever the cause: `blocked (image)`, `blocked (port)`, `failed (devdb not ready)`, `failed (port identity)`, `blocked (devdb lost)`, a task that stops after its fixes under the charter's "Titik keputusan", or any other stop.

A stop before the scratch directory exists has created nothing and needs no teardown.

1. **Health check.** Docker health rule step 1 (`colima status`, then `docker info`). If either fails: rule steps 2 and 3, then step 5 here.
2. **Dry run.** Run `pnpm test:docker-cleanup --run "$AIDA_TEST_RUN_ID"` with output to `<scratch>/cleanup-dry-1.log`, and read the exit code without a pipe. Record the whole list.
   - The list names this plan's dev database container: each `aida-test-devdb-<runId>-...` name that start steps 5 and 6 created, including one left by a port retry. It also names any leftover of this run's own test processes.
   - The script lists only resources with `aida.test=1`, `aida.test.run=<runId>` and the `aida-test-` prefix, so every entry belongs to this run (charter rule H).
   - A non-zero exit: record `failed (cleanup)` with the output, skip steps 3 and 4, and report the container name for the orchestrator's end-of-round cleanup.
3. **Apply.** Run `pnpm test:docker-cleanup --run "$AIDA_TEST_RUN_ID" --apply` with output to `<scratch>/cleanup-apply.log`. Record the `removed:`, `already gone:`, `skipped:` and `FAILED:` lines and the exit code. A non-zero exit or a `FAILED:` line is `failed (cleanup)`, recorded and reported. It is never retried with `docker rm`, `docker stop` or any other command.
4. **Final dry run.** Run step 2's command again, with output to `<scratch>/cleanup-dry-2.log`. It must exit 0 and print `0 resource(s) of run <runId>; dry run, nothing removed.`; record it. Any other count is `failed (leftover)`, recorded with the list and reported. Nothing is removed by hand.
5. **Scratch directory.** Copy the cleanup logs' text into the SUMMARY. Then remove the directory with `rm -r -- "<scratch path>"`. This is allowed only because this plan created it with `mktemp -d` and it lies under `${TMPDIR}` (charter owner rule C). J1's run ledger under `${TMPDIR}/aida-test-runs/` belongs to the run, not to this plan, and stays.
