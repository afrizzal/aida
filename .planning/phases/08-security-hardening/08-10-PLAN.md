- Better Auth (1.7 docs, Context7): `advanced.ipAddress.ipAddressHeaders: string[]` names trusted headers to read; values are validated as IPs and IPv6 is collapsed to `ipv6Subnet` (default 64); without a valid value it uses a shared per-path bucket in production and a localhost constant in development and test. 08-02-SUMMARY records the exact installed behaviour.
- Caddy (Context7, caddyserver/website): `reverse_proxy` sets or augments X-Forwarded-For and ignores incoming values unless `trusted_proxies` is configured; `{remote_host}` is the client address of the TCP connection.
- Caddyfile today: `request_body { max_size 12MB }` and `reverse_proxy app:3000 { header_up X-Forwarded-Proto {scheme}; header_up X-Forwarded-Host {host} }`.

- Next.js 16.2.11 `node_modules/next/dist/server/base-server.js` line 577 sets `x-forwarded-for` to the socket's remote address when the header is absent, in `handleRequestImpl`, which also runs the proxy (middleware invoke at line 938). |----------|-------------|
| client -> Caddy | X-Forwarded-For and any custom header are attacker-controlled |
| Caddy -> app | the only hop the app trusts; Caddy overwrites the header from the TCP peer |
| proxy -> Better Auth | the internal identity header must only be written by the proxy |

## Docker health rule (review R2-2)

A Docker step is any step that needs the Docker daemon: Testcontainers (through `pnpm test:integration`, `pnpm test:e2e` or `pnpm test:e2e:prod`), the `aida-dev-db` container, an image build, or a compose stack. `docker compose ... config` renders without the daemon and is not a Docker step.

1. Immediately before the first Docker step of each task, run `colima status` and then `docker info` as two separate commands and read each exit code without a pipe.
2. If either exits non-zero or prints an error: never stop, restart or delete Colima or Docker (charter owner rule B); skip every remaining Docker step of this plan and every step that needs a Docker result; record each skipped step and each skipped Docker verify command in the SUMMARY as `blocked (docker unhealthy)` with the output of both commands; finish and commit only the remaining work that needs neither; then stop this plan and end the SUMMARY and the final report with the line `DOCKER-UNHEALTHY: <command> exit <code>`, so the orchestrator applies charter rule B and "Berhenti total".
3. A `blocked (docker unhealthy)` step is never recorded as passed or failed, and its verify command is not run.
