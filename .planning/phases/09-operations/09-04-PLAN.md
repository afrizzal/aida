## Fence contract (U-12; the backup side is plan 09-06)

Chosen mechanism: a two-signal database fence. Codex suggested an advisory file lock on the shared volume; it is not used because Node 22 has no flock API (a helper process would depend on a busybox applet in the runner image that cannot be checked without a container run), and a flock taken on the macOS host and one taken in the Colima VM are separate lock domains, so the U-12 interleaving tests could not run on this host until the Phase 8.1 harness exists. The two signals below meet each U-12 clause and are testable on Testcontainers Postgres.

- Lock key: `hashtextextended('aida:file-fence', 0)` (exported as `FILE_FENCE_KEY_SQL`), session-level advisory lock.
- Backup (holder, plan 09-06): (1) a dedicated psql session (`application_name` `aida-backup-fence`) takes the exclusive lock with `pg_advisory_lock`, waiting up to `BACKUP_FENCE_WAIT_SECONDS`; (2) after the lock is held it writes the committed SystemSetting row `backup:lease` = JSON `{"holder":"<setId>","expiresAt":"<ISO UTC from the database clock>"}`, only when no unexpired lease exists, and renews it every TTL/3 through fresh connections; (3) the dump starts after both; (4) both are released at the end of the run.
- Deleter (the sweep): (1) verify the uploads volume; (2) on its own `pg` connection (`application_name` `aida-delete-fence`) `pg_try_advisory_lock_shared`; false -> skip (`backup-archiving`); (3) on the same connection evaluate `BACKUP_LEASE_ACTIVE_SQL` (a value that is not a JSON object with an ISO `expiresAt` counts as no lease); active -> unlock, skip (`backup-lease`); (4) select due rows and delete, tracking every `storage.delete` promise; (5) release the shared lock only after the transaction ended and every tracked promise settled, in the background so the job returns as today; (6) a fence connection error before step 4 -> skip (`fence-unavailable`); a drop during steps 4 and 5 -> one log line, deletes in flight continue (G6 keeps this harmless).
- Guarantees: G1 to G6 in must_haves, each tested in Task 2. Limit L1 (flagged): a backup that is paused AND has lost its fence session AND whose lease has expired, all at once, no longer fences deletions; that run then aborts on lease loss when it resumes (plan 09-06) and its dump-to-archive verification fails any set missing a referenced file, so nothing inconsistent is published.

## Flagged assumptions

- L1 (combined fault): paused backup + dropped fence session + expired lease at once lifts the fence; the safety net is the backup's lease-loss abort and its dump-to-archive verification (plan 09-06). Reported to the owner as a stated limit.
- Upload intents (review P4's "failure after a file is stored") are not built: a process crash between storing a file and committing its reference leaves an unreferenced file. It cannot break a backup (verification checks only keys the dump references, U-13) and costs disk only; an intent row that a sweep acts on next to a live reference path would risk deleting a referenced file if one clear were missed. Stated limit.
- Outside a container `UPLOADS_DIR` is usually not a mount point, so a local `pnpm worker` deletes no files (Phase 14 behaviour changes in local development only); documented in the SUMMARY and by plan 09-08 in docs/OPERATIONS.md.
