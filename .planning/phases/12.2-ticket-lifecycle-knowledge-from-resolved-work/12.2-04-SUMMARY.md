# Phase 12.2 Plan 04: Proposal request and shared source module Summary

An active owner or admin can request a KB proposal from 1 to 5 tickets whose state group is RESOLVED or CLOSED: membership, role, count, AI and per-ticket eligibility are checked in one transaction with typed, whole refusals, the GENERATING proposal and its sources are created with `generationQueuedAt` from the request clock, and `{ proposalId, epoch }` is sent on `kb-proposal-generate` only after commit; the shared source module reads only the subject and PUBLIC messages (at most 21 per ticket), returns the ticket's true largest PUBLIC seq as a bigint snapshot, rechecks eligibility without touching messages, and reports changed sources with bigint comparison.

## Deviations from Plan

### Test design notes (no scope change)

**1. The mixed-selection behaviour case was split into two requests.** The behaviour list names seven entries for one selection (RESOLVED, CLOSED, PENDING, OPEN, merged, other organization, repeated id), but seven ids exceed the 5-ticket limit and would be refused with COUNT before eligibility. The case is therefore two requests: [RESOLVED, PENDING, OPEN, merged, other organization] and [CLOSED, RESOLVED, unknown id, CLOSED again]. Every listed reason and the "none for RESOLVED and CLOSED" assertion is covered; an unknown id was added to show NOT_FOUND is the same for an unknown and a foreign id.

**2. Extra cases beyond the behaviour lists:** plain member with a valid selection and AI on (NOT_ALLOWED); another organization's owner (MEMBERSHIP_ENDED); RESOLVED with CLOSED accepted; the null-snapshot case of must-have truth 7; cross-organization findChangedSources and recheck.

**3. Task 1 module split.** `proposal-sources.ts` was drafted in full during Task 1; the Task 1 commit holds only `checkSourceEligibility`, and the rest was restored in Task 3 after the RED run (see RED evidence).
