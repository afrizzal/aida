# Phase 12.2 Plan 08: Proposal server actions, loaders, list page and Start dialog Summary

The proposal services now reach the app. Three loaders check the member row and the owner or admin role before any proposal or ticket query, and they build their results field by field from explicit selects, so no result carries `snapshotSeq` or a bigint. Seven server actions take the actor from `getSessionActor()`, and only the session read and the service call can turn into `UNKNOWN`; revalidation runs afterwards and never changes a committed result. On top of these sit the `/kb/proposals` list with polling and a live announcement, the admin-only Proposals button on `/kb`, and `StartProposalDialog`, which applies `resolveActionOutcome` to every request result and to a rejected call.

## What the integration test proves (16 cases)

- Owner: `requestProposalAction` with one RESOLVED ticket returns `{ ok: true, proposalId }`, sends one job and revalidates `/kb/proposals` and the proposal path. `loadProposalList` then lists the row (GENERATING, null title, one source). A second case checks newest-first order, every field and the source count.
- Plain member: all seven actions return NOT_ALLOWED, with no revalidation, no proposal send and no change. `loadProposalList`, `loadProposalReview` and `loadStartSelection` return exactly `{ kind: 'NOT_ALLOWED' }`.
- Deleted member row: the same, with MEMBERSHIP_ENDED.
- NOT_FOUND is returned for another organization's proposal id, an unknown id and an empty id. The owning organization can still read the foreign proposal.
- `loadStartSelection` keeps the given order and leaves out another organization's ticket.
- Review C6: when `revalidatePath` throws (`mockImplementationOnce`) after a committed request, the action still returns ok with the proposal id. The proposal exists, exactly one generate job was sent, and the second path was still revalidated. The same holds for `publishProposalAction` on a seeded DRAFT: ok with `indexingQueued: true`, one article and one embed send. When the request service throws an Error carrying a marker, the action returns `{ ok: false, code: 'UNKNOWN' }`; neither the result nor the console calls contain the marker, and nothing was created or sent. When the session read throws, every action returns UNKNOWN.
- Pass-through: a save field refusal returns its field (`TITLE_TOO_SHORT`, `title`); a save success returns its new version; restart and retry return `queued: true`; reject returns ok.
- `loadProposalReview` returns sources in position order with chip data and `citedSections`, plus changed numbers, the requester's name, `aiEnabled` and `inputTruncated`. `stuck` counts from `generationQueuedAt` with an injected clock and is unaffected by an older `createdAt` (review C5). `article.embeddingStatus` is returned as stored, PENDING and then FAILED (review C2), and a publisher without a user row gives a null name.
- Review P3: a DRAFT has two sources whose stored `snapshotSeq` is `9007199254740993n` (read back as a bigint). The walker finds no `snapshotSeq` key and no bigint anywhere in the DRAFT review, a PUBLISHED review, the list, or the start selection. It searches objects, arrays, Map keys and values, and Set values, and treats a Date as a leaf. A separate case shows that the walker does find a nested bigint and a nested `snapshotSeq` key.
