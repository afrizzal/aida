## Summary

I reviewed every test file the phase added or changed, and read the code they exercise where a
test's strength depends on it: `src/lib/worker/jobs/kb-embed-article.ts` (hook placement),
`src/lib/kb/generate-proposal.ts` (claim hooks), `src/lib/llm/providers/ollama.ts`
(`withDeadline`), `src/lib/kb/proposal-sources.ts` (which client it queries),
`src/lib/insight/run-insight.ts` (KB-gap path), the AuditEvent and KbProposal triggers in the
migrations, `tests/e2e/global-setup.ts`, `tests/e2e/support/test-env.ts`, `tests/e2e/support/db.ts`
and `tests/support/lock-wait.ts`.

Most of the suite holds up:

- **Race tests.** Every concurrency proof waits on backend PIDs it recorded. Each PID is read
  inside the run's own transaction, through hooks that sit in the right places: `onSwapStart`
  and `onFailStart` come before the row lock, `beforeClaim` comes before the claim UPDATE, and
  `afterClaim`, `afterProposalUpdate` and `afterArticleInsert` come before the commit. Each wait
  is a `waitForBlockedBy(holder, [waiter])` on the named holder. No test counts anonymous waiters,
  and no test relies on timing. The only polling is the bounded 50 ms loop in `waitForBlockedBy`.
- **No real provider calls.** The OpenAI and embedding adapters are mocked below `complete()` and
  `embed()`, so the real redaction, dispatch and audit code still runs. The Ollama tests stub
  `fetch` and still run the real `ollama` client. The E2E stub listens only on 127.0.0.1.
- **The stub's default path is unchanged.** With no hold and `chatMode = "ok"`, `/api/chat` still
  answers `JSON.stringify(chatResponse)` on request end. The only addition is that it now records
  each request body.
- **No fixed sleeps.** None of the E2E cases uses one.

The defects are concentrated in four places:

1. The E2E cleanup in `kb-proposals.spec.ts`, the known item: details below.
2. One E2E case and one integration file whose assertions cannot fail for the leak they claim to
   rule out.
3. A unit test that checks component source text instead of behaviour.
4. A few assertions that pass vacuously.

### Known item: `cleanUp()` with `session_replication_role = replica`

- **Can it reach another database?** Not in practice. `prisma` comes from `src/lib/db.ts`, and
  `./support/test-env` sets `DATABASE_URL` from `.auth/env.json` before `src/lib/db.ts` is first
  imported. The spec's earlier static imports (`proposal-copy`, `proposal-prompt`, `rag/types`)
  do not import the database, and the fixtures are imported dynamically. `global-setup.ts`
  deletes `.auth/` and rewrites `env.json` with the URL of the container it just started, so a
  stale file cannot outlive a run. Even pointed at another database, the replica block would do
  nothing: it runs only when `proposalIds.length > 0`, and the proposals are selected by an
  `orgId` that exists only in this container. The role check is no protection, though. The
  Testcontainers `e2e` user is a superuser, and so is the `POSTGRES_USER` of the compose dev
  database. A one-line `current_database()` guard would make the boundary explicit (WR-01).
- **Does a safer alternative exist?** Yes. The published article cannot be removed otherwise:
  `KbProposal.publishedArticleId` is `ON DELETE RESTRICT`, the status fence forbids changing it
  on a PUBLISHED row, `AuditEvent.kbProposalId` is `RESTRICT`, and AuditEvent refuses DELETE.
  Deleting a whole organization does not help either, because `AuditEvent.organizationId`
  cascades and would hit the same trigger. The only real alternative is to stop sharing the
  organization: run this file in its own organization and owner, or make `phase5-rag.spec.ts`'s
  empty-state case independent of other files. Either removes the trigger bypass entirely.
- **Does it hide anything?** Yes, two things (WR-01, WR-02):
  - It deletes every AuditEvent row of the file's proposals, of any `actionType`, without first
    asserting what was there. The E2E file never checks the audit trail, so a regression that
    wrote extra AuditEvent rows (for example on publish or reject, against D-12) would be erased
    silently.
  - The post-cleanup check reuses the selection's own `createdAt >= specStart` predicate, so it
    cannot detect a row that predicate missed.

## Warnings

### WR-01: The E2E cleanup erases every AuditEvent of the file's proposals unchecked, and has no database guard

**File:** `tests/e2e/kb-proposals.spec.ts:455-458`
**Issue:** The transaction sets `session_replication_role = replica`. That disables every
ordinary trigger and every foreign-key trigger on the connection, not only the append-only
trigger. It then deletes
`AuditEvent WHERE organizationId = $org AND kbProposalId = ANY($ids)`, whatever the
`actionType`. Nothing in the file asserts the audit rows first: the happy path, the two
provider-failure cases and the injection case all produce or skip audit rows that are never
checked. A product defect that wrote a second `KB_PROPOSAL_GENERATED` row, or an AuditEvent on
publish, reject or save (D-12 says review actions never go there), would be deleted without
notice. There is also no check that the connection is the Testcontainers database. The
container user is a superuser, and so is the compose dev database's `POSTGRES_USER`, so the
`SET` would be allowed there too. Only the `orgId` scoping keeps the block a no-op elsewhere.
**Fix:** The preferred fix removes the bypass. Run this file in its own organization: sign up a
second owner in `beforeAll` the way `global-setup.ts` creates the member (`auth.api.signUpEmail`,
`member.create`, a browser login, `storageState`), and leave its rows in the disposable
container. Alternatively, make `phase5-rag.spec.ts`'s "KB empty state" case use a fresh
organization. If the bypass stays, guard it and assert what it removes:

```ts
const [{ db }] = await tx.$queryRaw<{ db: string }[]>`SELECT current_database() AS db`;
if (db !== "aida_e2e") throw new Error(`cleanUp: refusing to bypass triggers on ${db}`);
const audits = await tx.$queryRaw<{ kbProposalId: string; actionType: string }[]>`
  SELECT "kbProposalId", "actionType"::text AS "actionType" FROM "AuditEvent"
  WHERE "organizationId" = ${orgId} AND "kbProposalId" = ANY(${proposalIds})`;
expect(audits.every((a) => a.actionType === "KB_PROPOSAL_GENERATED")).toBe(true);
expect(new Set(audits.map((a) => a.kbProposalId)).size).toBe(audits.length); // one per proposal
await tx.$executeRawUnsafe("SET LOCAL session_replication_role = replica");
await tx.$executeRaw`DELETE FROM "AuditEvent" WHERE "organizationId" = ${orgId}
  AND "kbProposalId" = ANY(${proposalIds}) AND "actionType" = 'KB_PROPOSAL_GENERATED'`;
```

### WR-02: The cleanup's own verification is tautological and does not check what phase5-rag depends on

**File:** `tests/e2e/kb-proposals.spec.ts:446-449, 473-480`
**Issue:** The cleanup selects proposals with `createdAt >= specStart`. It then "checks itself"
with the same predicate (`count(createdAt >= specStart) === 0`) and by counting articles whose
ids it already collected. Any proposal the predicate misses is invisible to both the delete and
the check. For example, `specStart` comes from the Playwright worker's clock, while a row's
`createdAt` may come from a different clock (the server process or the container). So is any
article published through such a proposal. The comment at line 472 promises that "a later file
never meets this file's rows silently", but the check cannot keep that promise. The invariant
the next file actually needs (zero KB articles in the E2E organization) is never asserted.
**Fix:** Record the ids the file creates and select by them: `proposalIdFromUrl`, `seedDraft`,
`seedProposal` and the source-ticket ids. Then assert the downstream invariant directly:

```ts
expect(await prisma.kbProposal.count({ where: { organizationId: orgId,
  sources: { some: { ticketId: { in: createdTicketIds } } } } })).toBe(0);
expect(await prisma.kbArticle.count({ where: { organizationId: orgId } })).toBe(0); // phase5-rag precondition
```

### WR-03: The "absent from RAG and Insight" E2E case cannot fail if a proposal leaks into retrieval

**File:** `tests/e2e/kb-proposals.spec.ts:885-886, 913-926, 929-953`
**Issue:**
- **RAG half.** The marker is only in a Draft proposal's title. Without `RAG_TOKEN`, it gets
  `UNRELATED_VECTOR` from the stub (line 101). The drafted-reply query contains `RAG_TOKEN`, so
  it is embedded as `CANONICAL_VECTOR`. The two vectors are orthogonal, at cosine distance 1. A
  wrongly chunked or embedded proposal would therefore sit far outside
  `MAX_COSINE_DISTANCE = 0.5` (`src/lib/rag/generate-draft.ts:24`) and never reach the prompt.
  `not.toContain(marker)` at line 926 passes whether or not proposals leak.
- **Insight half.** The KB-gap reader (`nearestKbChunk`, `src/lib/insight/run-insight.ts:179`)
  runs only for reported clusters. The case does not assert that any cluster exists, so the
  marker check at line 953 may never touch the KB path.

The integration test `kb-proposal-reader-isolation.test.ts` covers retrieval meaningfully, using
identical vectors. This E2E case does not add the coverage its title claims.
**Fix:** Put `RAG_TOKEN` into the Draft proposal's title and body, so a leaked chunk would be the
nearest one:

```ts
await seedDraft("absent", `Draft only ${marker} ${RAG_TOKEN}`);
```

Then assert retrieval positively: the request contains the real article's chunk text and not the
marker. For Insight, assert that the completed run has at least one cluster with a computed
`nearestArticle` (or coverage) before the marker check, or drop "Insight" from the case title.

### WR-04: Most reader-isolation cases re-implement the reader query and cannot fail

**File:** `tests/integration/kb-proposal-reader-isolation.test.ts:142-151, 153-166, 183-200, 202-215`
**Issue:** The header says that "a server page, server action or non-exported helper is covered
by running the same query it runs". In practice the test writes its own
`db.kbArticle.findMany`, `count`, `findFirst` or `updateMany`, for the KB list, the article
loader, settings, re-embed-all, ticket detail, the demo seed and `create-article`. A Prisma
query on `kbArticle` cannot return a `KbProposal` row by construction, so these cases assert
Prisma's table mapping and not the readers. If `src/app/(app)/kb/page.tsx` or
`ticket-detail-data.ts` started reading proposals (a union, a second query, a shared loader),
every case here would still pass. Only the cases that call exported code exercise real behaviour:
`retrieveRelevantChunks`, `nearestKbChunk`, `kbEmbedArticleHandler`, and the raw `KbChunk` LIKE
scans.
**Fix:** Call the real entry points: `findRelated` from `src/lib/tickets/ticket-detail-data.ts`,
the settings server action that `reembedAllKb` uses (with the session mocked the way
`kb-proposal-actions.test.ts` does it), and `createKbArticle` or `updateKbArticle` with a
proposal's title, asserting the slug and the row count. Extract the KB list and article loader
queries into exported functions so the test can call them. Otherwise delete these cases and keep
the claim scoped to the readers that are actually called.

### WR-05: The status-chip test asserts on source text, not behaviour

**File:** `tests/unit/proposal-copy.test.ts:26-29, 655-671`
**Issue:** `CHIP_SOURCE` is the raw text of `kb-proposal-status-chip.tsx`, and the test checks
substrings in it:
- `toContain("icon: X")` also matches `icon: XCircle`, and none of the icon checks ties an icon
  to its status. Swapping the icons of REJECTED and PUBLISHED passes.
- `not.toContain("#")` fails on a harmless comment yet misses a colour written another way (for
  example an arbitrary class `bg-[hsl(...)]`).
- `toContain('from "@/lib/kb/proposal-copy"')` proves an import exists, not that the labels are
  used.

This is acceptance gaming: the UI-SPEC E3 pairing stays unverified. The E2E colour-contrast scan
in `a11y-contrast.spec.ts:394-405` only checks contrast and visible labels.
**Fix:** Export the status-to-presentation map from the chip module, or a small
`proposalChipPresentation(status)` helper, and assert it per status:

```ts
expect(proposalChipPresentation("PUBLISHED")).toMatchObject({ icon: Check, label: PROPOSAL_STATUS_LABELS.PUBLISHED });
expect(proposalChipPresentation("REJECTED").icon).toBe(X);
```

Keep the token-only rule as a lint or grep gate in the design checklist rather than as a unit
test.

### IN-01: Absence assertions right after a forced click pass at once

**File:** `tests/e2e/kb-proposals.spec.ts:685-686, 784-785, 838-839`
**Issue:**
- `click({ force: true })` followed at once by
  `expect(dialog).toHaveCount(0)` resolves on the first poll. A dialog that opened 100 ms later
  would not be seen. The real proof is the `aria-disabled` and `toBeDisabled` checks before it.
- At line 838, `/kb/proposals` is opened with no positive sync point. `gotoWarm` rejects only a
  404, so a 500 or error page would also satisfy `getByText(otherTitle).toHaveCount(0)`.

**Fix:** After the forced click, assert something that would change if the click had fired (for
example, that the menu is still open, or that focus is unchanged), or drop the negative
assertion. At line 838, assert the `PROPOSALS_PAGE_TITLE` heading, and ideally one of this
organization's proposals, before the absence check.

### IN-02: The injection case takes the first proposal request without asserting there was exactly one

**File:** `tests/e2e/kb-proposals.spec.ts:864-867`
**Issue:** `const [request] = ...filter(...)` has no length check. With zero requests,
`messageOf(undefined, …)` throws a `TypeError` that does not say what went wrong. With two
requests (a duplicate provider call), the duplicate goes unnoticed. The happy-path and both
failure cases assert `toHaveLength(1)`.
**Fix:** Assert the length before destructuring:

```ts
const requests = stub.chatRequests.slice(requestsBefore).filter(...);
expect(requests).toHaveLength(1);
```

### IN-03: The E2E file leaves tickets and a second organization in the shared database

**File:** `tests/e2e/kb-proposals.spec.ts:292-313, 822-831`
**Issue:** `cleanUp` removes settings, proposals, articles and Insight runs, but none of the
following:
- about 15 seeded RESOLVED, CLOSED or OPEN tickets, with their contacts, messages and
  TicketAuditEvents, in the E2E organization;
- the extra organization, its owner user, its ticket and its proposal, from the isolation case.

`a11y-contrast.spec.ts` deletes its own proposal source tickets, but this file does not. Later
files share the organization, for example `phase6-insight.spec.ts`, whose 7-day Insight period
now includes these resolved tickets. No assertion breaks today, but the header's claim that
"cases do not depend on each other's order" does not extend across files.
**Fix:** Track the seeded ticket ids and delete them in `cleanUp` after the proposals, with the
same delete-or-reopen fallback `a11y-contrast.spec.ts` uses. Alternatively, adopt the
separate-organization fix from WR-01, which removes the concern.

### IN-04: The total-bound prompt test barely checks source 5

**File:** `tests/unit/proposal-prompt.test.ts:115-116`
**Issue:** Source 5's subject is `Seeeeeeeee` and its first message is `e` repeated 4,000 times.
`not.toContain("E")` checks only the uppercase second message. A regression that kept source 5's
subject or first message would pass. Lowercase `e` cannot be checked directly because the block
label "Subject:" contains it.
**Fix:** Assert the exact block, `expect(block(prompt, 5)).toBe("Subject: ")` (or the exact
empty form the builder emits), and do the same for block 4.

### IN-05: A filler assertion and a duplicated status list

**File:** `tests/integration/kb-proposal-actions.test.ts:621`, `tests/e2e/a11y-contrast.spec.ts:123`
**Issue:**
- `expect(typeof 1n).toBe("bigint")` tests JavaScript, not the walker.
- `a11y-contrast.spec.ts` declares its own
  `PROPOSAL_STATUSES` instead of importing it from `src/lib/kb/proposal-contract.ts`. A status
  added to the contract would get no chip in the contrast scan, and no test would notice.

**Fix:** Delete the filler line. Import `PROPOSAL_STATUSES` from `proposal-contract` in
`a11y-contrast.spec.ts`; the seeding loop already handles text and FAILED codes by status.

### IN-06: The worker is stopped without waiting before cleanup and the next file

**File:** `tests/e2e/kb-proposals.spec.ts:150-161, 483-488`
**Issue:** `stopWorker()` sends SIGTERM and returns at once. `cleanUp()` then deletes the
articles and proposals the worker may still be processing (an embed or an Insight run after a
timed-out case), and the next file that starts a worker (`phase4-ai.spec.ts`) can overlap with
it. Today the jobs handle a deleted row safely (`lockArticleForJob` returns null), so nothing
fails. The pattern is copied from `phase5-rag.spec.ts`.
**Fix:** Await the child's `close` event, with a bounded timeout, before `cleanUp()`:

```ts
await new Promise<void>((r) => { worker?.once("close", () => r()); stopWorker(); });
```
