## Phase Boundary

AIDA proposes a new KB article drafted from one or more resolved tickets; an owner or admin reviews it, and nothing reaches the knowledge base without that explicit action. Requirement AIDA-18 in `.planning/REQUIREMENTS.md` (generation through `src/lib/llm/`, disabled when AI is off, secrets redacted, ticket text untrusted, nothing publishes without an admin action); ROADMAP Phase 12.2 success criterion 1. ## Implementation Decisions

Format: decision, then source. "Codex" means the round-1 brainstorm for this phase recommended it. "Orchestrator" means the run-loop orchestrator decided it (run decisions are logged in `run-loop/RUN-LOG.md`).

### Inherited

- **D-01:** Every new server path (request a proposal, list, read, edit, reject, publish, the generation job's writes) calls `findActiveMembership` first and then requires the exact `owner` or `admin` role (`isAdminRole`). The check is server-side on every action and route, including direct URLs, never only a hidden button. A test proves each path refuses a session whose member row was deleted and a plain `member`. The existing manual KB create action (`src/app/(app)/kb/actions.ts`, `getScopedDb` only, no role check) is not changed here and keeps AIDA-43 open. Source: 11 D-01, 12.1 D-01; Codex area 4; orchestrator.
- **D-02:** `AuditEvent` stays AI-only (11 D-07): one real row per generation (D-12); human actions are recorded elsewhere, never with placeholder AI columns. Source: 11 D-07; orchestrator.

### Data model and isolation

- **D-03:** New table `KbProposal`, not a draft status on `KbArticle`: `id`, `organizationId`, `status` (new enum with exactly `GENERATING`, `DRAFT`, `REJECTED`, `PUBLISHED`, `FAILED`), `version` (integer, incremented by every write, used for conditional updates), `title` and `bodyMarkdown` (null until generated), the requesting actor, reviewer and publisher ids, timestamps per transition, a failure code (an enum value, never a raw provider error), a source snapshot marker (D-08) and `publishedArticleId` (unique, set only on publish). Unique `(organizationId, id)` serves composite foreign keys. Reason: `createKbArticle` writes the article and enqueues embedding at once (`src/lib/kb/create-article.ts:43-70`), and the chunk readers have no publication filter, so a separate table needs no change to them. Existing articles need no migration. Source: Codex area 1 (revises area 7 of fase12); orchestrator.
- **D-04:** Join table `KbProposalSource` (`organizationId`, `proposalId`, `ticketId`), many-to-many, with organization scoping in the database: composite foreign keys on `(organizationId, proposalId)` and `(organizationId, ticketId)`, or a trigger where a composite key is not available on `Ticket` (the planner checks the schema). A cross-organization link is refused by the database, proven by a Testcontainers test. Source: Codex area 1; orchestrator.
- **D-05:** A proposal never gets `KbChunk` rows and never reaches RAG (`src/lib/rag/retrieve.ts:30`), Insight (`src/lib/insight/kb-gap.ts:24`, `run-insight.ts:151`), the KB list and article pages (`src/app/(app)/kb/`), search, embedding or re-embed. Only a published `KbArticle` is embedded. A test seeds a proposal with distinctive text and proves none of these readers returns it. `scoped-db.ts` `DOMAIN_MODELS` gains the new models. Source: Codex area 1; orchestrator.
- **D-06:** A `KbArticle` is created only by the explicit admin action "Approve and publish", in **one transaction**: a conditional update of the proposal from `DRAFT` to `PUBLISHED` on `(id, organizationId, status, version)`, then exactly one `KbArticle` insert linked back through `publishedArticleId`. `createKbArticle` cannot be reused as is (it is not transactional and enqueues inside the call); the planner adds a transactional variant that shares `slugify` and `renderMarkdown`. Slug collisions: `uniqueSlug` is a `findFirst` loop (`create-article.ts:18-27`) and `@@unique([organizationId, slug])` exists, so a concurrent publish can hit a unique violation; it is caught and retried with the next suffix, never a 500. Embedding is enqueued after commit and is recoverable: the article's `embeddingStatus` `PENDING` is the durable marker, and a retry re-enqueues for the same article without creating a second one. Source: Codex areas 1 and 6; orchestrator.

### Trigger and sources

- **D-07:** Manual only: an active owner or admin selects 1 to 5 tickets of their organization whose state's **group** is `RESOLVED` or `CLOSED` (not a state name). A merged source (`mergedIntoTicketId` not null) is refused with a pointer to its target. An invalid selection refuses the whole request with a typed reason per ticket, never a silent drop. No automatic generation, no agent trigger (corrects fase12 area 7). Source: Codex area 2; orchestrator.
- **D-08:** Eligibility is checked at request time **and again** in the job before any ticket text is read for generation; a ticket reopened or merged in between makes the proposal `FAILED` with an actionable code. The proposal stores a source snapshot marker per ticket (for example the last message `seq`); if a source changes after generation the reviewer sees a warning, and the draft is never rewritten or published automatically. Source: Codex area 2.

### Generation (AIDA-18 accept)

- **D-09:** Generation goes through `complete()` (`src/lib/llm/complete.ts`) only. `complete()` itself does not check `aiEnabled`; the caller does, at request time (refused, with UI copy) and again in the job right before the provider call (proposal `FAILED`, code AI off), as `ai-triage.ts:21-22` does. A call already running when AI is switched off may finish; its result is stored as `DRAFT` and is never published without D-06. Source: AIDA-18 accept; Codex area 5; orchestrator.
- **D-10:** Prompt shape: fixed instructions in `system`; ticket text only in `prompt`, fenced as untrusted data (`fenceContent`, `src/lib/rag/prompt-safety.ts`). Ticket text never goes into `system`, which `complete()` passes through without redaction (`complete.ts:19-25`). Input is the subject and **PUBLIC** messages only (`MessageVisibility`), no internal notes, no attachments, bounded in message count and length; when truncation drops part of a thread the reviewer is told. Redaction is the secret regex set in `redact.ts:8-13` (API keys, AWS key ids, bearer tokens, card-like numbers): it is **not** PII anonymisation, so the reviewer must remove customer details (owner item 12.2-o1). Source: AIDA-18 accept; Codex area 3.
- **D-11:** Output is validated against a schema (title and body length, structure) and every citation id must be one of the selected ticket ids; invalid output makes the proposal `FAILED` without retry. Citations are shown to the reviewer as internal ticket links, never rendered into the published article. Markdown is rendered only through `renderMarkdown`. A fenced injection attempt in a ticket is a test case (no action follows from it). Source: Codex area 3.
- **D-12:** One real `AuditEvent` per generation, with a new `AuditActionType` value (added to the enum and to `RecordAuditEventParams`, `src/lib/audit/record-audit-event.ts`), the actual provider and model, `complete()`'s `redactedPrompt` as input and the model output, written through `recordAuditEvent`. Edit, reject and publish are recorded on the proposal (actor ids, timestamps) or in a separate append-only record, never in `AuditEvent`. No raw prompt, output or provider error in logs. Source: 11 D-07; Codex area 3; orchestrator.

### Worker

- **D-13:** A pg-boss job (registered in `src/lib/worker/index.ts`, relative imports) carries only the proposal id; the proposal row is the persistent status. The job claims the proposal with a conditional update (`GENERATING` and the expected version) and stores its result only through a second conditional update, so two workers can never both store a result. A proposal left in `GENERATING` without a job (process died after commit) is recoverable by re-enqueueing the same id. Idempotency covers storage only: a retry may cause a second provider call. Source: Codex area 5; orchestrator.
- **D-14:** Every adapter has a call timeout: OpenAI and Anthropic have 30 s with `maxRetries: 0` (`providers/openai.ts:20`, `providers/anthropic.ts:21`); **Ollama has none** (`providers/ollama.ts`), so one is added. Retries are bounded (pg-boss `retryLimit`, at most 2, as the other jobs) and only for transient failures; configuration errors and invalid output are terminal `FAILED`. Tests use the fake provider only, never a paid API (charter). Source: Codex area 5; charter.

### Review

- **D-15:** Owner/admin only (D-01) for list, read, edit, reject and publish. The review view shows title, body, sources with their snapshot warning (D-08) and the truncation notice (D-10). Saving an edit increments `version` and never publishes; publish is the one explicit "Approve and publish" action (D-06). Source: Codex area 4; orchestrator.
- **D-16:** Every review write is a conditional update on `(id, organizationId, status, version)`. Two admins on the same version: one wins, the other gets a typed conflict refusal and reloads; two publishes create exactly one article (proven by a PID-bound race test). Rejection is terminal, the row is kept, and a rejected proposal can never be published; regeneration (also after `FAILED`) creates a new proposal. Source: Codex area 4; orchestrator.

### Plan shape

- **D-17:** Freeze first: the status machine (D-03, D-16), the source rules (D-07, D-08, D-10), the audit shape (D-12) and the AI-off semantics (D-09). Suggested waves: wave 1, schema, migration, tenancy constraints and their Testcontainers tests; wave 2, source selection, prompt, validation, audit, the job, the Ollama timeout and enqueue recovery; wave 3, review, edit, reject, publish (transactional create, slug retry, embedding enqueue) and their race tests; wave 4, the UI per UI-SPEC and `.planning/DESIGN-SYSTEM.md`; wave 5, E2E with the fake provider (organization isolation, AI off, provider failure, proposals absent from RAG and Insight), the phase gate and the §9 design checklist. At most three tasks per plan; the planner splits further and never drops scope. Source: Codex area 6; lessons from Phases 8 to 12.1.

## Instruction for the planner

Do not create `checkpoint:human-verify` tasks. Write every human verification as a manual item in the plan and in the SUMMARY, and leave it open. Do not reduce scope: if a plan is too big, split it. Every executor dispatch includes the charter's "Aturan eksekutor" section.

Lessons from Phases 8 to 12.1, binding here:

- Few plans, few new mechanisms. Prefer what Testcontainers or unit tests can prove: conditional updates, unique and foreign-key constraints, one transaction. Testcontainers needs the Colima socket environment that the orchestrator supplies.
- Race tests are bound to backend PIDs (`waitForBlockedBy`), never to a sleep. Time-dependent tests use an injected clock.
- AI tests use the fake provider only; no paid API, no real egress. No test may run a real compose stack (O-1).
- E2E tests assert observed outcomes; every expectation matches the behaviour an earlier plan specifies.
- Acceptance criteria point at the file where the code actually lives, and never contradict the plan's own action.
- No edit after a review without a new review of that edit.
- One test process at a time; long commands write to a log, and exit codes are read without a pipe.
