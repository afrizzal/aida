# Phase 12.2 Plan 07: KB proposal generation job Summary

A pg-boss job that claims a GENERATING proposal by an epoch-bound conditional update, rechecks the requester, the sources, the provider configuration and the AI switch before any provider call, generates through `complete()` with the fixed system prompt and the fenced, redacted PUBLIC-only prompt, writes one real `KB_PROPOSAL_GENERATED` audit row per returned call, validates the answer under run decision K51 and stores it as DRAFT by a second conditional update on the claimed version and epoch; failures end as typed FAILED codes or one bounded pg-boss retry, and a job superseded by a newer claim or by Restart generation can never store, fail or release the current generation.

## pg-boss metadata (includeMetadata)

Read in `node_modules/pg-boss/dist/types.d.ts` (pg-boss 12.23.0): `JobFetchOptions.includeMetadata?: boolean` (line 394); with `{ includeMetadata: true }` the `WorkHandlerFor` type selects `WorkWithMetadataHandler`, whose jobs are `JobWithMetadata<T>` (line 539) with `retryLimit: number` and `retryCount: number` (also `retryDelay`, `retryBackoff`, `retryDelayMax`, `state`, `startedOn`, `createdOn` and others, unused). The handler reads only `data`, `retryCount` and `retryLimit`. retryCount is 0 on the first attempt; with `retryLimit` 2 the attempts carry retryCount 0, 1 and 2, so "a retry is left" is `retryCount < retryLimit` and retryCount 2 of 2 is the last attempt. A retry keeps the original `data`, so it carries the epoch of the job that failed. The registration passes no explicit type argument to `boss.work` (an explicit `<ReqData>` would reset the inferred options type and drop the metadata handler type); the handler parameter is annotated `JobWithMetadata<unknown>[]`.

Queue options in `src/lib/worker/index.ts` equal `src/lib/queue/boss-client.ts`: `retryLimit: KB_PROPOSAL_JOB_RETRY_LIMIT` (2), `retryBackoff: true`, `retryDelayMax: 300`.

## Classifier decisions

Only errors thrown by `complete()` go through `classifyLlmError` (plan 12.2-03's table):

| Class | Outcome |
|-------|---------|
| CONFIGURATION (LlmConfigurationError; status 400, 401, 403, 404, 422) | FAILED CONFIGURATION, no throw, no AuditEvent |
| INVALID_OUTPUT (LlmOutputError, ZodError, SyntaxError) | FAILED INVALID_OUTPUT, no throw, no AuditEvent (K49) |
| TRANSIENT, retryCount < retryLimit | release (generationClaimedAt null, generationQueuedAt = now, version + 1, on claimedWhere), then throw KbProposalRetryError; DISCARDED without a throw when the release matched no row |
| TRANSIENT, last attempt | FAILED PROVIDER, no throw, no AuditEvent |

A returned answer that `validateProposalOutput` refuses is FAILED INVALID_OUTPUT with exactly one AuditEvent (the call was real). Any other exception after the claim (a database error, the audit write, the store transaction) is FAILED UNKNOWN on claimedWhere, rethrown (the original error) only when that FAILED write itself throws. Errors before the claim (load, claim transaction) propagate with nothing written.

Logs are fixed lines with the proposal id and a code: `kb-proposal-generate: <id> failed <CODE>`, `... transient failure, retry queued`, `... superseded, <CODE> not written`, `... superseded, draft discarded`, `... superseded, no retry`, `... stored DRAFT`, and the handler's `kb-proposal-generate: invalid payload`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] The transient path throws a fixed-text error instead of the provider's error**
- **Found during:** Task 1
- **Issue:** must-have truth 6 says TRANSIENT "rethrows"; rethrowing the provider's own error would let pg-boss store its message in the job row, which D-03 and D-14 (no raw provider error in any row or log) forbid.
- **Fix:** after the release `KbProposalRetryError` (message `kb-proposal-generate: <id> transient failure, retry queued`) is thrown; pg-boss still sees a failed attempt and retries with the same payload. The tests assert the handler rejects with it.
- **Files modified:** src/lib/kb/generate-proposal.ts
- **Commit:** 49df4cd

**2. [Rule 1 - Bug] A superseded job's transient failure does not throw**
- **Found during:** Task 1 (design), proven in Task 3
- **Issue:** when the release matches no row (a newer generation owns the proposal), throwing would make pg-boss retry a job whose epoch is already stale.
- **Fix:** return DISCARDED without a throw; the race case "A's transient failure cannot release B's generation and asks for no retry" proves it.
- **Commit:** 49df4cd (service), 0237233 (test)
