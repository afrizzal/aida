What holds up after tracing:

- **Tenancy.** Every statement in the reviewed services has an explicit organization term. That includes the two operations that `scopedDb` does not scope: `updateManyAndReturn` (restart, `proposal-review.ts:446-460`) and `createMany` (sources, `proposal-request.ts:111-118`). All raw SQL in `proposal-sources.ts` and `membership.ts` filters on `"organizationId"`. The composite foreign keys keep sources, the published article and audit rows inside their own organization in the database too.
- **Explicit publish.** `createKbArticleInTx` has exactly one caller, `publishAttempt` (`proposal-review.ts:357`). It runs only after the member-row share lock, `isAdminRole`, the conditional DRAFT claim and the validation of the stored fields. The only other article writers are the existing manual action and the demo seed.
- **Lock order.** Publish locks the member row (FOR SHARE), then the proposal row (UPDATE), then inserts the article (unique slug index), then updates its own proposal again. Save, reject and restart lock only the proposal. Retry indexing locks only the article. The embed job locks only the article and then the chunks. No reviewed path takes two of these in reverse order, so no cycle was found. Two publishes that pick the same slug wait on the unique index in one direction only, and the loser retries.
- **Conditional updates.** Each one carries id, organization, status and version (the job's updates add the epoch). The final PUBLISHED update is tied to the claimed version. The retry claim is a single status-conditional UPDATE.
- **bigint.** `seq` and `snapshotSeq` stay `bigint` end to end; there is no `Number()` on that path.
- **Migration.** `ADD VALUE` is its own statement and the new value is not used anywhere else in the file. The CHECK biconditionals match the writes the services make. The trigger allows exactly the four status transitions and freezes title, body and article on final rows. The hand-written FTS objects are kept.

The findings below are gaps in how much the phase's guarantees actually cover. None of them lets a proposal publish without the admin action or crosses organizations through the reviewed code.

## Warnings

### WR-01: The change warning (D-08) misses messages merged into a source ticket

**File:** `src/lib/kb/proposal-sources.ts:257-272`, `src/lib/kb/proposal-sources.ts:332-357` (also `:296-300`)
**Issue:** The snapshot marker and the change check both use `MAX(seq)` over the ticket's PUBLIC messages. A merge moves the source ticket's messages into the target and keeps their seq (`src/lib/tickets/merge.ts:301-305`, "createdAt and seq are left untouched"). Suppose a RESOLVED proposal source B becomes a merge target after generation. Merging A into B adds A's PUBLIC messages to B, but every moved message has a seq lower than B's stored `snapshotSeq`. B's `MAX(seq)` does not change, B stays RESOLVED (the merge does not change the target's state) and B is not MERGED. `findChangedSources` therefore reports nothing, and the reviewer gets no D-08 warning even though B's public thread changed. This is the one way a thread changes that the bigint seq comparison cannot see.
**Fix:** Make the marker the larger of the PUBLIC seq and the merge seq. `merge.ts` draws `mergeMessageSeq` from the same sequence after both row locks, so a later merge always produces a larger value. Use the same expression in `readLargestPublicSeqs`, and therefore in both the snapshot and the check:
```sql
SELECT t.id AS "ticketId",
       GREATEST(
         (SELECT MAX(m.seq) FROM "Message" m
           WHERE m."organizationId" = ${orgId} AND m."ticketId" = t.id AND m.visibility = 'PUBLIC'),
         (SELECT MAX(s."mergeMessageSeq") FROM "Ticket" s
           WHERE s."organizationId" = ${orgId} AND s."mergedIntoTicketId" = t.id)
       ) AS "maxSeq"
FROM "Ticket" t
WHERE t."organizationId" = ${orgId} AND t.id = ANY(${ids}::text[])
```
Drop rows where `maxSeq` is null, so the "absent" behaviour stays the same. Add a case where a ticket is merged into a stored source after generation and the source is reported as changed.

### WR-02: `scopedDb` passes several operations through with no organization filter, but the phase adds two models to its "scoped" list

**File:** `src/lib/scoped-db.ts:55-64`, `src/lib/scoped-db.ts:91-100` (models added at `:37-38`)
**Issue:** The docblock says the client "automatically injects `organizationId: orgId` into every DOMAIN_MODELS query". The hook only handles `create`, `upsert` and the eight operations in `WHERE_SCOPED_OPERATIONS`. These operations go through unscoped: `findUnique`, `findUniqueOrThrow`, `findFirstOrThrow`, `aggregate`, `groupBy`, `createMany`, `createManyAndReturn` and `updateManyAndReturn`. This phase already calls two of them on its new models through a scoped client: `tx.kbProposal.updateManyAndReturn` (`proposal-review.ts:446`) and `tx.kbProposalSource.createMany` (`proposal-request.ts:111`). Both are safe only because the author wrote `organizationId` by hand, and plan 05 only recorded that in a SUMMARY note. A later `db.kbProposal.findUnique({ where: { id } })` or `updateManyAndReturn` on a scoped client would quietly read or write another organization's proposal. This is the same silent tenancy failure `scopedDb` exists to prevent.
**Fix:** Close the gap in the hook rather than relying on each caller:
```ts
const WHERE_SCOPED_OPERATIONS = new Set([
  "findMany", "findFirst", "findFirstOrThrow", "findUnique", "findUniqueOrThrow",
  "count", "aggregate", "groupBy",
  "update", "updateMany", "updateManyAndReturn", "upsert", "delete", "deleteMany",
]);
// ...
if (operation === "create") {
  args.data = { ...args.data, organizationId: orgId };
} else if (operation === "createMany" || operation === "createManyAndReturn") {
  const rows = Array.isArray(args.data) ? args.data : [args.data];
  args.data = rows.map((row: object) => ({ ...row, organizationId: orgId }));
}
```
`findUnique` accepts non-unique filters in Prisma 5 and later, so adding `organizationId` to its `where` is valid. If any operation is meant to stay unscoped, throw for it on DOMAIN_MODELS instead of passing it through. Add a unit test that lists every Prisma operation name and asserts each one is scoped or refused.

### WR-03: The publish share lock locks one member row, but the table allows several rows per user and organization

**File:** `src/lib/membership.ts:67-75`; `prisma/schema.prisma:129-139` (no `@@unique([organizationId, userId])` on `member`)
**Issue:** Review C1's guarantee is that a demotion or removal waits for a publish that already passed its role check. `shareLockActiveMembership` runs `... LIMIT 1 FOR SHARE` with no `ORDER BY`, on a table that has no unique key on `(organizationId, userId)`. Duplicate rows can come from Better Auth's non-atomic check-then-insert on invitation accept or add-member. If a user has two rows, the publish locks and reads whichever row Postgres returns first, which may be the admin row. Demoting or deleting the other row is not blocked, and it does not change the read result. The C1 race tests only cover one row per user. `findActiveMembership` has the same ambiguity (a `findFirst` with no `orderBy`), so whether a request is allowed depends on physical row order.
**Fix:** Lock every row and decide on all of them:
```sql
SELECT "id", "role" FROM "member"
WHERE "userId" = ${userId} AND "organizationId" = ${orgId}
ORDER BY "id"
FOR SHARE
```
Return null when there is no row, and treat more than one row as not allowed (or require every row to be admin). The root fix is a migration that adds `CREATE UNIQUE INDEX "member_organizationId_userId_key" ON "member"("organizationId","userId")`. That needs an owner decision because the table belongs to Better Auth. Record it as a known limit if it is deferred.

### WR-04: The generation input keeps the start of each thread and drops the end, where the resolution usually is

**File:** `src/lib/kb/proposal-sources.ts:302-315` (`ORDER BY seq LIMIT ${limit}`); `src/lib/kb/proposal-prompt.ts:85-87` (`messages.slice(0, MAX_MESSAGES_PER_SOURCE)`)
**Issue:** The feature turns resolved work into knowledge. For a thread with more than 20 PUBLIC messages, the loader reads the first 21 and the prompt keeps the first 20. The messages that actually resolved the ticket (the final agent reply, the customer's confirmation) are dropped, while the opening complaint is kept. The model then writes an article with no fix, or invents one. The truncation notice tells the reviewer that something was cut, but not that the resolution is what was cut. The tests ("25 PUBLIC messages: 21 returned (messages 1 to 21)") lock this behaviour in.
**Fix:** Keep both the start and the end of the thread. For example, read the first K and the last M PUBLIC messages, with K + M = `MAX_MESSAGES_PER_SOURCE`, plus one more to detect truncation:
```sql
(SELECT seq, "bodyMarkdown" AS body FROM "Message"
  WHERE "organizationId" = ${orgId} AND "ticketId" = ${id} AND visibility = 'PUBLIC'
  ORDER BY seq ASC LIMIT ${head})
UNION
(SELECT seq, "bodyMarkdown" AS body FROM "Message"
  WHERE "organizationId" = ${orgId} AND "ticketId" = ${id} AND visibility = 'PUBLIC'
  ORDER BY seq DESC LIMIT ${tail})
ORDER BY seq
```
Set `truncated` from a count, and mark the gap in the prompt (for example "[... N messages omitted ...]"). Update the 25-message test so it asserts that the last message is included.

## Info

### IN-01: The final-row fence does not protect the reviewer and actor columns that D-12 relies on

**File:** `prisma/migrations/20261111100000_kb_proposals/migration.sql:169-175`
**Issue:** D-12 records human review actions only on the proposal columns, never in `AuditEvent`. The trigger freezes `title`, `bodyMarkdown` and `publishedArticleId` on REJECTED, PUBLISHED and FAILED rows. It does not freeze `publishedByUserId`, `publishedAt`, `rejectedByUserId`, `rejectedAt`, `failureCode`, `failedAt`, `requestedByUserId` or `version`. The CHECK only forces them to stay non-null, so an UPDATE can rewrite the only record of who published or rejected a proposal.
**Fix:** Add these columns to the `IS DISTINCT FROM` list for final rows, in a follow-up migration (this file is final once applied).

### IN-02: Body length is limited at generation (`BODY_MAX`) but not when a draft is saved

**File:** `src/lib/kb/proposal-schema.ts:311-333` (compare `:265`); `src/lib/kb/proposal-review.ts:248-252`
**Issue:** `validateDraftFields` has no body maximum, so a save stores whatever the server action accepts (about 1 MB under the default Next.js action body limit). Publish then renders and embeds that body, which can mean many chunks billed to the user's own embedding provider. The generation path refuses more than 20 000 code points.
**Fix:** Apply `BODY_MAX` in `validateDraftFields`, add a `BODY_TOO_LONG` review refusal code and a UI copy row, or document that the asymmetry is intended.

### IN-03: Some known outcomes reach the caller as raw errors, so the UI shows "outcome unknown"

**File:** `src/lib/kb/proposal-review.ts:397-406`; `src/lib/kb/proposal-request.ts:121-128`; `src/lib/kb/proposal-sources.ts:107-111`
**Issue:** If the slug retry fails on the third attempt, the P2002 error is rethrown even though the transaction rolled back and nothing was published. A text value containing `\u0000` (a ticket id in the request, or a title or body in a save) fails in Postgres with 22021 and is rethrown the same way. The actions map both to UNKNOWN, which shows "outcome unknown" when the outcome is actually known: nothing changed.
**Fix:** In `publishProposal`, return a typed CONFLICT (or a new code) once the attempts run out. Refuse strings containing `\u0000` in `asId`, `asText` and `isTicketId` (NOT_FOUND, or BODY_REQUIRED and the like).

### IN-04: Restart keeps the original requester, so a proposal whose requester lost the role can never recover

**File:** `src/lib/kb/proposal-review.ts:446-460` (with `src/lib/kb/generate-proposal.ts:311-313`)
**Issue:** The job checks the role of `requestedByUserId`, not the role of the admin who restarted the generation. If the original requester was demoted or removed, every restart by another admin ends as FAILED REQUESTER_NOT_ALLOWED, even though the UI still offers Restart.
**Fix:** Either refuse restart with a typed code when the requester is no longer an active admin, or have restart record the restarting admin as the new requester in the same conditional update. Decide which and document it.

### IN-05: The status machine in TypeScript is not used by any service

**File:** `src/lib/kb/proposal-contract.ts:98-116`
**Issue:** `canTransition` and `isFinalStatus` (and `TICKET_REFUSAL_REASONS` and `PROPOSAL_FAILURE_CODES`) are referenced only from tests. The services hard-code their status terms, so the frozen contract and the code can drift apart without any test failing.
**Fix:** Use them where the services choose an expected status (for example, assert `canTransition(expected, next)` next to each conditional update), or note in the contract that the list exists for the enum-equality test only.

### IN-06: The migration builds two unique indexes without CONCURRENTLY on existing tables

**File:** `prisma/migrations/20261111100000_kb_proposals/migration.sql:96`, `:99`
**Issue:** `CREATE UNIQUE INDEX` on `"Ticket"` and `"KbArticle"` holds a SHARE lock that blocks ticket and article writes while each index builds during `migrate deploy`. Neither index can fail (`id` is already the primary key), but on a large self-hosted ticket table this is a write outage during an upgrade.
**Fix:** No change to this applied file. Note it in the upgrade docs. A future migration of this kind can build the index with `CREATE UNIQUE INDEX CONCURRENTLY` in its own migration and then `ADD CONSTRAINT ... UNIQUE USING INDEX`.
