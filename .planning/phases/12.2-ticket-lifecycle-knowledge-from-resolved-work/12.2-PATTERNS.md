### `prisma/schema.prisma` and the migration (model + migration)

**Analogs:** `TicketState` (`schema.prisma:730-751`) for `@@unique([organizationId, id])`; `AuditEvent` (`schema.prisma:460-475`) for org relation; `AuditActionType` enum (`schema.prisma:239-245`).

```prisma
enum AuditActionType {
  TRIAGE
  DRAFT_GENERATED
  DRAFT_APPROVED
  INSIGHT_CLUSTER_LABELS
  INSIGHT_SUMMARY
}
...
  @@unique([organizationId, id])
  @@index([organizationId, group, sortOrder])
```

Hand-written composite FK and unique precedent (`migration.sql:62`, `:265`):
```sql
CREATE UNIQUE INDEX "TicketState_organizationId_id_key" ON "TicketState"("organizationId", "id");
ALTER TABLE "Ticket" ADD CONSTRAINT "Ticket_organizationId_stateId_fkey" FOREIGN KEY ("organizationId", "stateId") REFERENCES "TicketState"("organizationId", "id") ON DELETE RESTRICT ON UPDATE CASCADE;
```
The schema comment block above `model TicketState` (`schema.prisma:715-728`) is the convention for listing hand-written objects Prisma cannot express; add the same kind of comment for any trigger or CHECK. `migrate dev --create-only` then edit by hand; never `db push`. Adding a value to `AuditActionType` is `ALTER TYPE ... ADD VALUE` (cannot run inside the same transaction as its first use in a Testcontainers test: keep it in its own migration statement).
