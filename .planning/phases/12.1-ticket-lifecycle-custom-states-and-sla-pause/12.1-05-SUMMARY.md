## Lock order as built

- resolveReplyTicket: `readStateConfigForShare`, `shareLockActiveState(reopenStateId)`, then `SAVEPOINT reply_resolve`, then the observer hooks and the ticket lock. A ROLLBACK TO the savepoint never releases the two share locks.
- reopenOnCustomerReply: reads the config again FOR SHARE (already held, no wait), the re-entrant ticket FOR UPDATE, then `UPDATE ... SET "stateId" = reopenStateId, "resolvedAt" = NULL ... AND EXISTS (TicketState s, s."organizationId" = orgId, s."group" IN ('RESOLVED', 'CLOSED'))`. The snooze wake block and the return value are unchanged. When race case (a) calls it directly without resolveReplyTicket, the config read is the first share lock.
- closeResolvedTicketIfQuiet: Setting days row FOR SHARE (lockAutoCloseSettings), config FOR SHARE, autoClose state FOR SHARE, `lockTicketsInIdOrder([ticketId])`, readStateGroups on the locked stateId (closed false unless RESOLVED), then the conditional UPDATE re-checking the group by EXISTS, resolvedAt, snoozedUntil and the cutoff. AUTO_CLOSED is written only when a row changed: before `{ stateId: previous, stateGroup: RESOLVED }`, after `{ stateId: autoCloseStateId, stateGroup: CLOSED }`.
- autoCloseOrganization: count `where { organizationId, resolvedAt: null, state: { group: "RESOLVED" } }`; the candidate SELECT joins TicketState on id and organizationId, group RESOLVED, no row lock; order and limit unchanged.
