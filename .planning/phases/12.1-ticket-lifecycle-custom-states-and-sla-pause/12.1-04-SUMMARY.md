## Why runTicketMutation keeps its own lock statement

lockTicketsInIdOrder returns only the columns merge and snooze need. runTicketMutation also needs priority, assigneeId, createdAt, mergedIntoTicketId and the four SLA columns (`slaPausedAt`, `slaPausedMs`, `firstResponseDueAt`, `resolutionDueAt`). So it keeps one statement, `SELECT ... FROM "Ticket" WHERE "organizationId" = $org AND id = ANY($ids) ORDER BY id FOR UPDATE`. That is the same ascending-id order on the ticket table alone, with no join, so no state row is locked. The module header records that this statement waits for rows held by others, and that the sla-flag worker locks with SKIP LOCKED and never waits, so the two cannot form a deadlock cycle (review C6; plan 12.1-06 Task 3 proves it with the two-ticket races, which depend on this order). Order inside the transaction: membership, then the target state FOR SHARE (STATE_NOT_FOUND), then the ticket lock, then the MERGED_SOURCE refusal, then the current groups (readStateGroups), then `now`.

## Frozen ResolvedAtPolicy table

| From group to group | by-group (agent change) | merge (plan 12.1-07, target CLOSED) |
|---|---|---|
| same group | only stateId | only stateId |
| any other group into RESOLVED or CLOSED | resolvedAt = now, isAtRisk = false, isBreached = false | from OPEN or PENDING: resolvedAt = now, both flags false; from RESOLVED: nothing (keeps resolvedAt and flags) |
| any other group into OPEN or PENDING | resolvedAt = null | n/a |
| into PENDING from another group | slaPausedAt = now | n/a |
| out of PENDING into another group | closePause: both deadlines and slaPausedMs + delta, slaPausedAt = null (nothing when slaPausedAt is null) | same |

delta = max(0, now - slaPausedAt) in whole milliseconds. The priority change uses `pausedDueTimestamps(createdAt, slaPausedMs, targets)`. An open pause is counted only when it closes. Exceptions named in the module header: auto-close (12.1-05) does not call this module and keeps resolvedAt; merge uses policy merge.
