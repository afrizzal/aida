## Summary

Public side (D-13): clean. `loadStatusPageData` selects only `state.group` and returns `group`. The page renders `PublicGroupChip`, which takes only the group: its label comes from `PUBLIC_GROUP_LABELS` (Open / Pending / Resolved / Closed, matching the UI-SPEC row "Public group labels") and its colour from the fixed `PUBLIC_GROUP_COLOR` map. A merged source still shows "Combined". The CSAT route reads only `state.group` and never returns it. No state name, id or colour reaches a public payload.

Authenticated readers:
- `searchTickets` joins `TicketState` with the organization term on both sides.
- The picker's number lookup goes through the composite relation.
- `ticket-detail-data` resolves feed state ids through `scopedDb` (TicketState is in the scoped model list) after `findActiveMembership`.
- Saved views treat soft-deleted, unknown, cross-organization and sentinel ids as `MISSING_REFERENCE`.
- `list-query` filters only by `stateId IN (...)`, so a missing id matches nothing.
- A present but empty or malformed `state=` falls to the `LEGACY_UNMAPPED_STATE_ID` sentinel and never to an empty list.
- The settings actions delegate to `ticket-state-admin`, which calls `findActiveMembership` and then `isAdminRole` inside the transaction (lines 198-200).

The main defect: a URL that carries both `state=` and the legacy `status=` is redirected to the union of the two, which widens the list (WR-b1).

Known notes:
- **"1 ticket uses" in `state-copy.ts`:** refuted as a defect. UI-SPEC line 433 sets the count rule ("1 ticket" / "{n} tickets"), and the singular verb follows from it. Row 483 shows only the plural form (IN-b1).
- **Contact page loader without a membership check:** confirmed (WR-b2, AIDA-43).
- **Computed `LEGACY_FILTER_KEY`:** confirmed (IN-b2).

## Warnings

### WR-b1: Legacy `status=` redirect unions with `state=`, widening the list (D-09)

**File:** `src/lib/tickets/list-filters.ts:257-270`
**Issue:** `legacyRedirectSearch` builds `state` as `canonicalIds([...parseStateParam(state), ...mapLegacyStatusParam(status, legacy)])`. The state filter is an `IN` list (`list-query.ts`, `where.stateId = { in }`), so the redirected URL matches tickets in either set. Example: `/tickets?state=<pendingId>&status=CLOSED` redirects to `state=<closedId>,<pendingId>`, which shows more tickets than either parameter alone. D-09 says a URL is "never widened". The mixed URL can only be hand-made or come from a stale link with a parameter added, but the fail-closed contract should not depend on that. The unmapped sentinel does not help here: it only adds an id that matches nothing.
**Fix:** When both parameters are present, intersect them. The redirect keeps only ids that appear in both sets. If the intersection is empty, it uses `[LEGACY_UNMAPPED_STATE_ID]`.
```ts
const mapped = mapLegacyStatusParam(status, legacy);
const merged = state === undefined
  ? mapped
  : (() => {
      const own = new Set(parseStateParam(state));
      const both = mapped.filter((id) => own.has(id));
      return both.length > 0 ? canonicalIds(both) : [LEGACY_UNMAPPED_STATE_ID];
    })();
```
Then add a unit test for the mixed URL. Alternatively, record the union as an explicit decision in CONTEXT, since D-09 does not specify the mixed case.

### WR-b2: Contact page loader still has no membership check (AIDA-43, confirmed)

**File:** `src/app/(app)/contacts/[id]/page.tsx:26`
**Issue:** The page reads `getScopedDb()` and loads the contact's tickets, now with `state { name, colorToken }`, without calling `findActiveMembership`. `getScopedDb` does not check membership (CONTEXT line 14). A session whose member row was deleted can still read the contact and its tickets' state names and colours. This phase edited the select only, so under D-01 ("new or rewritten" paths) this is the known open AIDA-43 item, not a new regression. It is still a live authorization gap on a path this phase touched.
**Fix:** Before the query, add:
```ts
const actor = await getSessionActor();
if (!(await findActiveMembership(prisma, actor.userId, actor.orgId))) notFound();
```
This matches `loadTicketDetailData` (line 125). Otherwise keep AIDA-43 open and list this page by name in it.

## Info

### IN-b1: "1 ticket uses" matches the UI-SPEC count rule (known note refuted)

**File:** `src/lib/tickets/state-copy.ts:235-238`
**Issue:** UI-SPEC row 483 shows only "{n} tickets use this status now." UI-SPEC line 433 makes every `{n}` count follow "1 ticket" / "{n} tickets", so `deleteInUseDescription(1)` = "1 ticket uses this status now. …" is that rule with the matching verb. It is not a drift. `n = 0` would read "0 tickets use", but case A (zero tickets) uses `DELETE_UNUSED_DESCRIPTION`, so the dialog never calls it with 0.
**Fix:** None required. Optionally, write the singular form into UI-SPEC row 483 so a grep for the row matches both branches.

### IN-b2: Test uses a computed key to dodge the acceptance grep (known note confirmed)

**File:** `tests/integration/saved-views.test.ts:24`, `:391`
**Issue:** `const LEGACY_FILTER_KEY = "statuses"` and `{ [LEGACY_FILTER_KEY]: ["OPEN"] }` keep the literal `statuses:` key out of the source. That hides the one intended use from a "no `statuses` filter key left" grep. The test itself is correct: it asserts that the v1 key is refused. But the acceptance grep now proves less than it claims, because a real leftover `statuses` key built the same way would also pass it.
**Fix:** Use the literal key with a comment marking it as an intended negative case, and exclude this test (by path and line) from the acceptance grep explicitly. Do not hide the key from the grep.

### IN-b3: Feed state lookup relies only on `scopedDb` for the organization term

**File:** `src/lib/tickets/ticket-detail-data.ts` (refStates query, `db.ticketState.findMany({ where: { id: { in: refs.stateIds } } })`)
**Issue:** The query names no `organizationId`. It is safe today because `db = scopedDb(orgId)` and `TicketState` is in the scoped model list (`src/lib/scoped-db.ts:35`). However, the sibling query in `saved-views/service.ts` names the organization explicitly, and this one would leak another organization's state names into the feed if the client were ever switched to bare `client`.
**Fix:** Add `organizationId: orgId` to the `where`, as a second fence matching `saved-views/service.ts`.
