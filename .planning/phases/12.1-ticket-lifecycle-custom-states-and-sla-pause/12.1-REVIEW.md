# Phase 12.1: Code Review Report (part a, data and core)

**Reviewed:** 2026-11-09
**Depth:** standard (plus targeted cross-file lock-order tracing)
**Files Reviewed:** 16 (5 only partly, see frontmatter)
**Status:** partial (context ran short; the partly read files are listed above)

## Summary

The migration, the schema, the pure transition planner, the bulk mutation path, the
`sla-flag` worker, the reply/reopen path, merge, auto-close, create-ticket and the delete
path of the admin service were read and their lock order traced across files.

What holds:

- **Tenancy.** Every raw statement read carries an organization term. The `sla-flag` lock step
  selects `id` and `organizationId` together, and the UPDATE joins on both through `unnest`.
- **Lock order.** No cycle found. Role writers (create, merge, auto-close, reply) take
  config `FOR SHARE`, then the target state `FOR SHARE`, then tickets in ascending id.
  `runTicketMutation` takes the target state `FOR SHARE` before its ticket lock. Admin
  delete takes config `FOR UPDATE`, the state `FOR UPDATE`, the replacement `FOR SHARE`,
  then tickets. The worker locks only `FOR UPDATE OF t ... SKIP LOCKED`.
- **Delete with a moving ticket.** The delete loop re-checks `ticket.stateId !== state.id`
  after the lock, so a ticket a concurrent writer moved away is skipped.
- **Pause arithmetic.**
  - `closePause` clamps negative deltas to 0.
  - A pause without a start is a no-op.
  - A priority change uses `createdAt + slaPausedMs`.
  - A merge of a pending source closes the pause under the `merge` policy.
  - A move within one group changes only `stateId`.
- **Migration.**
  - Data is mapped per organization, with a RAISE on any unmapped ticket.
  - Saved views fail closed on bad input.
  - The FTS objects from earlier migrations are untouched.
  - No earlier partial index, CHECK or trigger depends on `Ticket.status` (grep), so the
    final `DROP COLUMN`/`DROP TYPE` loses nothing.
  - The organization trigger and the group-immutability trigger are present.
- **Audit.** Rows hold only `{ stateId, stateGroup }`.

No blocker found. Two warnings concern defence in depth around the tenancy and lock
protocol fences.

## Warnings

### WR-01: Composite state foreign keys use `ON UPDATE CASCADE`, so an update to `TicketState.organizationId` moves tickets and config into another tenant

**File:** `prisma/migrations/20261110100000_ticket_states/migration.sql:217`, `:226-238`; `prisma/schema.prisma` (`Ticket.state`, `TicketStateConfig.*State` relations)
**Issue:** D-04 adds the composite key `(organizationId, stateId) -> TicketState(organizationId, id)`
so that the database refuses cross-tenant state references. The generated `ON UPDATE CASCADE`
weakens that from the parent side. A single
`UPDATE "TicketState" SET "organizationId" = X` (a scoped-db `update` with `organizationId`
in `data`, a script, a later bug) is not refused. It rewrites `Ticket.organizationId` of
every ticket in that state, and the `organizationId` primary key of the config row that points
at it, into organization X. The result is a silent cross-tenant move of ticket data, not an error.
Nothing in the product needs to change a state's organization.
**Fix:** declare the composite relations with `onUpdate: Restrict` (or `NoAction`) in
`schema.prisma`. Then, in a new hand-checked migration (this one is final), drop and re-add the
six constraints with `ON UPDATE RESTRICT`. Optionally extend the group-immutability trigger to
`BEFORE UPDATE OF "group", "organizationId"`.
```sql
ALTER TABLE "Ticket" DROP CONSTRAINT "Ticket_organizationId_stateId_fkey",
  ADD CONSTRAINT "Ticket_organizationId_stateId_fkey" FOREIGN KEY ("organizationId", "stateId")
  REFERENCES "TicketState"("organizationId", "id") ON DELETE RESTRICT ON UPDATE RESTRICT;
-- same for the five TicketStateConfig_*StateId_fkey constraints
```

### WR-02: `reopenOnCustomerReply` writes a state without taking the target `FOR SHARE` (D-15 amended)

**File:** `src/lib/tickets/reopen-on-reply.ts:253-268`
**Issue:** D-15 amended says every writer that sets `stateId` reads the target state
`FOR SHARE` in its transaction and refuses a soft-deleted one. `reopenOnCustomerReply` is
exported. It reads `reopenStateId` from config and writes it without `shareLockActiveState`. It
is safe today only because both callers (`ingest-message.ts:204-212` and
`api/public/status/[token]/follow-up/route.ts:97-105`) first call `resolveReplyTicket`, which
takes that lock at `reopen-on-reply.ts:180-182` in the same transaction. The function's own
`observedBeforeLock` branch exists for calls without `resolveReplyTicket`, so it is designed
to be callable on its own. Any such caller writes the reopen state with no state lock and no
refusal of a soft-deleted state, which is the case the explicit lock exists for (a soft
delete's non-key update lock does not block the foreign key's key-share check).
**Fix:** after reading the config, lock the target. This costs nothing when the lock is
already held:
```ts
const { reopenStateId } = await readStateConfigForShare(tx, orgId);
const target = await shareLockActiveState(tx, orgId, reopenStateId);
if (!target) throw new ReopenStateUnavailableError(orgId, reopenStateId);
```

## Info

### IN-01: Entering PENDING overwrites an existing `slaPausedAt`

**File:** `src/lib/tickets/state-transition.ts` (`planStateTransition`, the `toGroup === "PENDING"` branch)
**Issue:** `data.slaPausedAt = now` is set without checking `row.slaPausedAt`. A row that is
already paused but not in PENDING can only come from an inconsistent write, for example the
demo finalize path that sets `slaPausedAt` directly. On such a row the earlier pause start
is lost, and its time is never added to the deadlines.
**Fix:** use `row.slaPausedAt ?? now`, or assert that `row.slaPausedAt === null` when
`fromGroup !== "PENDING"`.

### IN-02: `legacyStatus` stays on soft-deleted states and never passes to the replacement

**File:** `src/lib/tickets/ticket-state-admin.ts:272-380` (delete); `src/lib/tickets/ticket-states.ts:159-170` (`readLegacyStateIds` filters `deletedAt IS NULL`)
**Issue:** suppose the migrated "Open" state is deleted with a same-group replacement. Then
old `?status=OPEN` URLs get the missing-reference treatment, and
`finalizeDemoTicket` with `legacyStatus: "OPEN"` throws `DemoSeedStateUnavailableError`, even
though every ticket moved to a live OPEN-group state. This fails closed and is consistent with
D-09. It is recorded so that the behaviour is a deliberate choice, not an accident.
**Fix:** none required. If mapping to the replacement is wanted, move `legacyStatus` to the
replacement inside the delete transaction, after the replacement's `FOR SHARE`. The partial
unique index allows this once the deleted row's key is cleared.

### IN-03: `slaPausedAt` is `timestamptz`, the deadlines are `timestamp`

**File:** `prisma/migrations/20261110100000_ticket_states/migration.sql:140`; `prisma/schema.prisma` (`slaPausedAt @db.Timestamptz(3)`)
**Issue:** today all pause arithmetic runs in JavaScript, so this is harmless. Any future
raw SQL such as `"firstResponseDueAt" + (now() - "slaPausedAt")` would mix `timestamp` and
`timestamptz`, and Postgres would cast implicitly through the session `TimeZone`.
**Fix:** keep the pause arithmetic in `closePause`. Note the type mix in the
`state-transition.ts` header.

### IN-04: Redundant second config read in the reply path

**File:** `src/lib/tickets/reopen-on-reply.ts:253`
**Issue:** `readStateConfigForShare` runs a second time in the same transaction that
`resolveReplyTicket` already locked (`:180`). It is harmless, and it becomes useful if WR-02
is fixed. As written, it suggests a lock that the function does not complete.
**Fix:** fold it into the WR-02 change, or pass the config from `resolveReplyTicket`.
