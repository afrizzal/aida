### Data model (AIDA-56)

- **D-03:** New table `TicketState`: `id`, `organizationId`, `name`, `colorToken`, `group`, `sortOrder`, timestamps. `group` is a new Postgres enum `TicketStateGroup` with exactly `OPEN`, `PENDING`, `RESOLVED`, `CLOSED`. A state's group never changes after creation (no update path; the planner may add a trigger as a second fence). Names are unique per organization, case-insensitive. Unique `(organizationId, id)` serves the composite foreign keys. Source: SEED-004; Codex areas 1 and 5 (fase12); Codex area 1.
- **D-04:** `Ticket.stateId` is the single source of truth, `NOT NULL`, with a composite foreign key `(organizationId, stateId)` to `TicketState (organizationId, id)`, `ON DELETE RESTRICT`. No denormalised group column on `Ticket`: raw SQL joins `TicketState` (or uses `EXISTS`) with the organization term. The old `status` column, its index `@@index([organizationId, status])` (`prisma/schema.prisma:302`) and the `TicketStatus` enum are removed at the end of the migration, after the data moved; an equivalent index on `(organizationId, stateId)` replaces the old one. Source: Codex area 1.
- **D-05:** One configuration row per organization, `TicketStateConfig` (primary key `organizationId`), with five role references, each a composite foreign key to `TicketState (organizationId, id)`: `newStateId` (the default for new tickets, group OPEN), `reopenStateId` (customer reply on a resolved or closed ticket, group OPEN), `resolveStateId` (group RESOLVED), `autoCloseStateId` and `mergeCloseStateId` (group CLOSED). Roles may point at the same state. The group of each role is validated by the service under the config row lock and proven by tests; the migration sets them. Only the default (`newStateId`) is exposed in the admin UI (AIDA-97 "set the default"); the other roles move only through deletion with replacement (D-12). Source: Codex area 1; orchestrator.
- **D-06 (run decision K40):** The default state must be in the OPEN group. A new ticket that starts pending, resolved or closed contradicts SLA and reopen semantics. This narrows the choice to OPEN-group states but keeps "set the default" (AIDA-97). Source: Codex area 1 (flagged as a behaviour choice); orchestrator.
- **D-07:** Every organization always has a complete state set and configuration. `src/lib/bootstrap.ts` (`createFirstOrgAndAdmin`, the only organization creation path: setup action, env bootstrap and demo identities) calls one shared idempotent helper that creates the five default states and the configuration inside the same flow; test fixtures that create organizations use the same helper. Source: Codex area 7; code check (`bootstrap.ts:12-37`, `demo/identities.ts:60`).

### Migration (AIDA-56)

- **D-08:** One hand-checked migration, atomic, in this order: create `TicketStateGroup`, `TicketState`, `TicketStateConfig`; insert five states for **every** organization, including organizations without tickets ("New" OPEN, "Open" OPEN, "Pending" PENDING, "Resolved" RESOLVED, "Closed" CLOSED, sort order 0 to 4, colour tokens matching today's chips); insert the configuration (new = New, reopen = Open, resolve = Resolved, autoClose = Closed, mergeClose = Closed); add `Ticket.stateId` and the SLA pause columns (D-16); map each ticket's enum value to the matching state of its own organization (NEW and OPEN stay separate); set the pause start of every ticket that is PENDING at migration time to the migration transaction's time, without changing any deadline; convert saved views (D-09); add `NOT NULL`, the foreign keys and the new index; drop the old index, column and enum. Prisma's generated DROPs of hand-written objects (`searchVector` columns, GIN indexes, CHECKs, triggers from earlier migrations) are removed by hand, as in 11-01 and 12-01. The migration runs in `aida-dev-db` with a stop-and-report precondition, never `prisma db push`. Source: Codex area 2; 11-01 and 12-01 precedent.
- **D-09:** Saved-view filters `version: 1` (status values, 11 D-03) become `version: 2` with state ids of the same organization; every other filter key is kept unchanged. An unknown status value or malformed filter JSON makes the migration fail with a diagnostic (`RAISE EXCEPTION` naming the view id), never a silent drop or a widened filter. A saved view that later points at a deleted state keeps the id and shows a missing reference (11 D-05), never all tickets. Old URLs with enum status values are parsed by a compatibility mapper to the migrated state of the active organization; unknown values fail closed (ignored with the missing-reference treatment, never widened). Source: Codex area 2 (fase12 area 5); 11 D-03, D-05.
- **D-10:** A Testcontainers migration test applies every migration up to `20261109100000_ticket_lifecycle`, seeds several organizations (one empty) with tickets in every enum value, private and shared saved views (v1, with status and other filters), audit rows, deadlines and flags, then applies this phase's migration and asserts: per-organization counts and ids unchanged; each ticket in the state matching its old value; deadlines and flags unchanged; PENDING tickets with the pause start set and nothing else changed; saved views converted with other keys intact; audit rows untouched; earlier hand-written objects still present; a cross-organization `stateId` refused by the database; a malformed saved view rolls the whole migration back. A fresh install (empty database) migrates cleanly. Source: AIDA-56 accept; Codex area 2.

### Readers of status (AIDA-56)

- **D-11:** Reader matrix, each row with its own test:

| Reader | Decides by |
|---|---|
| Create ticket (`create-ticket.ts`, intake, email ingest) | `newStateId` |
| Customer reply (`reopen-on-reply.ts`) | group RESOLVED or CLOSED moves to `reopenStateId`, same conditional update and lock as today (11 D-17); wake unchanged (12 D-14) |
| Auto-close job | candidates in group RESOLVED with `resolvedAt` and not snoozed, as today; target `autoCloseStateId` |
| Merge | source to `mergeCloseStateId`; a pending source closes its pause first (D-16) |
| Snooze and wake | snooze refuses group CLOSED; wake changes only the snooze |
| Single and bulk state change (`runTicketMutation`) | the chosen state id, validated in the actor's organization; lifecycle effects (resolvedAt, flags, pause) fire only when the **group** changes, and are exactly today's per-status effects mapped to groups; a move within one group changes only `stateId` and writes the audit row; a merged source refuses every state change (`MERGED_SOURCE`) |
| `sla-flag` worker | only tickets in group OPEN and not paused; both UPDATEs |
| CSAT route | group RESOLVED or CLOSED |
| Public status page | a fixed public label per group, never the internal state name (D-13); a merged source keeps "Combined" |
| Filters, chips, palette, saved views, bulk bar | state ids; the chip shows the state name with its colour token |
| Inbox row emphasis (today bold for NEW, `ticket-list-row.tsx:91`) | bold when the ticket is in the default state (`newStateId`) |
| Triage AI (`ai-triage.ts`) | writes no status today (grep); stays that way |
| Demo fixtures and seed | the five migrated identities; the `ageHours` / SLA invariants still hold |
| Feed and audit | legacy rows (enum values) render through the existing copy; new rows store `{ stateId, group, name }` (name snapshot); the feed shows the current name while the state exists, else the snapshot with a "deleted state" marker |
| Insight | unchanged (`resolvedAt` and flags); aggregates tested equal before and after the migration |

Source: Codex area 3; orchestrator (row emphasis, audit shape).

- **D-12 (run decision K41):** Deleting a state is allowed only (a) when no ticket and no role uses it, or (b) with a replacement state of the **same group**, which receives every ticket and every role of the deleted state. Each of the OPEN, RESOLVED and CLOSED groups always keeps at least one state (the roles need them). Reason: same-group reassignment has no lifecycle side effects (resolvedAt, flags, SLA pause), so a bulk reassignment cannot silently reopen, resolve or pause tickets. AIDA-97 ("remove a state only after its tickets are reassigned") is met. Source: orchestrator; Codex area 4 (risk of cross-group effects).
- **D-13:** The public status page and anything a customer sees show only a fixed label per group (OPEN, PENDING, RESOLVED, CLOSED, with the existing public copy for those statuses), never an internal state name such as "Waiting on engineering". A ticket in the "New" state therefore shows the OPEN label publicly. Source: Codex area 3 (privacy, conservative); orchestrator.

### Managing states (AIDA-97)

- **D-14:** (admin surface) A settings page for ticket states, admin-only (D-01): create (name, group, colour), rename, recolour, reorder, set default (D-06), delete (D-12). Reorder uses accessible move-up / move-down controls, no drag-and-drop library and no new package. Colours come from a fixed palette of state colour tokens added to the design system (light and dark), with the name always visible so colour is never the only signal; contrast is covered by the existing `a11y-contrast` E2E. E2E covers each action. Source: AIDA-97 accept; Codex area 4; `.planning/DESIGN-SYSTEM.md` (token-only).
- **D-15:** (concurrency) Every admin state operation locks the organization's `TicketStateConfig` row `FOR UPDATE` first. Deletion then locks the deleted state's row `FOR UPDATE` (a concurrent writer that sets a ticket to that state needs the foreign key's key-share lock on it and waits), moves its tickets to the replacement with one audit row each, re-points roles, and deletes the state. A writer that waited and finds the state gone gets a refusal ("state no longer exists"), never a 500. The planner proves both orders with PID-bound race tests (`tests/support/lock-wait.ts`), including a ticket writer that already holds a ticket row lock, and shows there is no deadlock. Source: Codex area 4 (one lock protocol, fixed order); orchestrator (mechanism; *unverified until the race tests exist*).

### SLA pause (AIDA-57)

- **D-16:** Two new `Ticket` columns: `slaPausedAt` (timestamptz, null when not paused) and `slaPausedMs` (bigint, not null, default 0: the sum of closed pauses). All transitions take the ticket row lock **before** reading the effective time. Entering group PENDING from another group sets `slaPausedAt = now`. Moving between two PENDING states changes nothing. Leaving group PENDING computes `delta = now - slaPausedAt`, adds `delta` exactly once to `firstResponseDueAt`, `resolutionDueAt` and `slaPausedMs`, and clears `slaPausedAt`, in the same UPDATE as the state change. Both deadlines move even when the first response already happened (the acceptance says each timer's due time moves by the paused time; the first-response deadline is then a normalised deadline, not a historical snapshot). A priority change computes `createdAt + new target + slaPausedMs`; an open pause is added when it closes. A first response during a pause is recorded and clears flags as today. Flags already set when a pause starts stay set. Snooze does **not** pause SLA. A merge of a pending source closes its pause before closing it. Pause state lives in the database, so a worker restart changes nothing. Tickets pending at migration time start their pause at the migration time (D-08), with no retroactive deadline change. Source: AIDA-57 accept; Codex area 5.
- **D-17:** `sla-flag` (`src/lib/worker/jobs/sla-flag.ts`) excludes paused tickets and every group except OPEN in **both** UPDATEs, re-checks the condition on the current row, and keeps its one-directional semantics. The handler accepts an injected clock for tests (default `new Date()`); transitions accept one too. Tests drive the real handler and real transitions with controlled times, never sleeps: several pauses of controlled length move each deadline by exactly their sum; a first response inside a pause; a priority change inside and after a pause; a "restart" (new handler invocation and client) mid-pause; merge of a pending source; no flag while paused, correct flag after resume; the `<` / `=` boundary; and two PID-bound race orders between the worker and a resume. Source: AIDA-57 accept; Codex area 5.
- **D-18:** While a ticket is paused, the agent UI shows the SLA as paused (UI-SPEC copy), so a deadline that has not moved yet is not shown as running. Source: Codex area 5.

<specifics>
## Specific Ideas

- Today a status change into RESOLVED or CLOSED sets `resolvedAt = now` and clears flags; into any other status it clears `resolvedAt` (`src/lib/tickets/mutations.ts:331-346`). Mapped to groups this stays exactly the same for group changes (RESOLVED to CLOSED is a group change and still sets `resolvedAt`, as today); a move inside one group has no lifecycle effect.
- Reopen today: one conditional UPDATE from RESOLVED or CLOSED to OPEN with `resolvedAt` null (`reopen-on-reply.ts:203-225`). Auto-close today: RESOLVED to CLOSED (`auto-close.ts:77-94`, `:218-224`).
- The status chip today maps NEW, OPEN, PENDING, RESOLVED, CLOSED to token classes (`src/components/tickets/status-chip.tsx:6-13`).

## Instruction for the planner

Lessons from Phases 8 to 12, binding here:

- Few plans, few new mechanisms. Prefer what Testcontainers or unit tests can prove: row locks, conditional updates, unique and foreign-key constraints, one transaction. Testcontainers needs the Colima socket environment that the orchestrator supplies.
- Race tests are bound to backend PIDs (`waitForBlockedBy`), never to a sleep. Time-dependent tests use an injected clock.
- No test may run a real compose stack (O-1).
- E2E tests assert observed outcomes; every expectation matches the behaviour an earlier plan specifies.
- Acceptance criteria point at the file where the code actually lives, and never contradict the plan's own action.
- No edit after a review without a new review of that edit.
- One test process at a time; long commands write to a log, and exit codes are read without a pipe.
