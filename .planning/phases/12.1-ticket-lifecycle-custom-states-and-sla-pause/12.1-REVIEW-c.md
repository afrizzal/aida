# Phase 12.1: Code Review Report, part c (UI)

**Reviewed:** 2026-11-09
**Depth:** standard (with spot checks of called helpers: `state-copy.ts`, `state-colors.ts`, `list-filters.ts`, the Radix menu package)
**Files Reviewed:** 24
**Status:** issues_found

## Summary

I reviewed the UI half of 12.1 against 12.1-UI-SPEC (copy rows, focus table 1h, Surface 4c, palette and contrast rules) and DESIGN-SYSTEM.md. The main scans came back clean:

- **Colour tokens and type sizes:** no oklch or hex values and no Tailwind palette classes outside `globals.css`. Every new element uses an explicit `text-[Npx]` size, and no new code uses a named size (`text-sm` or `text-xs` appear only inside shipped shadcn internals). The ten `--state-*` tokens in `globals.css` match the spec values in `:root`, `.dark` and `@theme inline`.
- **Copy:** every copy string I checked against its UI-SPEC row matched word for word. The one deviation is IN-c4.
- **Colour as a signal:** colour is never the only signal. Chips show the name, dots sit next to the name, the checked colour option shows a `Check` icon, and the paused chip has an icon and text.
- **Public group chip:** `PublicGroupChip` receives only `group`. Its two callers (`status/[token]/page.tsx:75` and `status-form-dialog.tsx:310`) never pass an internal state name or colour.

The defects are mostly about accessibility and focus:

- Disabled menu items whose reason never reaches keyboard or screen-reader users.
- A scrolled-away focused item in the new scrolling status menu.
- A focus fallback when you uncheck a missing-status item.
- Missing pending guards and stale lists after some refusals.

**The known note about `delete-status-dialog.tsx` is confirmed:** see IN-c1.

## Warnings

### UI-WR-c1: Disabled-with-reason menu items: the reason is never announced on focus and is read twice in browse mode

**File:** `src/app/(app)/settings/statuses/status-manager.tsx:471-506`

**Issue:** "Use for new tickets" and "Delete status…" get Radix `disabled` plus `aria-describedby` pointing at the reason line (UI-SPEC 1c, 1h).

- **Unreachable by keyboard:** Radix Menu removes disabled items from keyboard navigation. `@radix-ui/react-menu` `dist/index.mjs:209` and `:320` filter `getItems()` by `!item.disabled`, and `:443` passes `focusable: !disabled` to RovingFocusGroup. Arrow keys skip these items, so a keyboard or screen-reader user never focuses them and never hears the `aria-describedby` reason.
- **Read twice:** the reason `<span>` sits inside the item, so it is also part of the item's accessible name. Browse-mode readers announce it twice: once in the name, once in the description.

This fails the UI-SPEC accessibility backstop ("disabled menu items read their reasons").

**Fix:** keep the item focusable and refuse the action yourself:
```tsx
<DropdownMenuItem
  aria-disabled={defaultReason ? true : undefined}
  data-disabled={defaultReason ? "" : undefined}
  className={cn("items-start text-[13px]", defaultReason && "opacity-50")}
  aria-describedby={defaultReason ? defaultReasonId : undefined}
  onSelect={(e) => { if (defaultReason) { e.preventDefault(); return; } onSetDefault(); }}
>
  <Star aria-hidden="true" />
  <span className="space-y-1">
    <span className="block">{ROW_MENU_SET_DEFAULT}</span>
    {defaultReason && <span id={defaultReasonId} aria-hidden="true" className="block text-[12px] text-muted-foreground">{defaultReason}</span>}
  </span>
</DropdownMenuItem>
```
Elements hidden with `aria-hidden` still work as `aria-describedby` targets. Do the same for the Delete item. Then record in the P12 D1 amendment notes that the shared pattern needs this change wherever it is reused.

### UI-WR-c2: The top-bar status menu now scrolls, but focusing the current value uses `preventScroll: true`

**File:** `src/components/tickets/ticket-meta-header.tsx:198-200` and `:402`

**Issue:** 12.1 adds `max-h-[320px] overflow-y-auto` to the status `DropdownMenuContent`. When the `s` key or the palette's "Change status" command opens the menu, `focusCurrentValue` runs `.focus({ preventScroll: true })` on the checked `menuitemradio`.

In a long list, the ticket's current state can sit below the fold, for example any Closed state when there are many states. It then gets focus without being scrolled into view, so the keyboard user sees no highlighted item. This was harmless with five fixed items. It became a defect once the menu could scroll.

**Fix:**
```ts
const item = content.querySelector<HTMLElement>('[role="menuitemradio"][aria-checked="true"]');
item?.focus({ preventScroll: true });
item?.scrollIntoView({ block: "nearest" });
```

### UI-WR-c3: Unchecking a "A deleted status" filter item removes the focused item; focus falls back to the menu container

**File:** `src/app/(app)/tickets/filter-chip-row.tsx` (missing-id `DropdownMenuCheckboxItem`s, the block under `{missingIds.length > 0 && …}`)

**Issue:** `onSelect={(e) => e.preventDefault()}` keeps the menu open. Unchecking a missing item removes that id from the URL, and the re-render unmounts the focused item. If it was the last missing id, the "No longer exists" label goes too.

Radix's FocusScope then moves focus to the content container: no item is highlighted and screen readers re-announce the menu. The missing-status notice under the row also disappears in the same navigation.

The 1h/4c focus rules cover the notice button but not this path. It is the same "focus after an async outcome" gap the Phase 12 review flagged.

**Fix:** before calling `toggleState`, focus a surviving item: the previous checkbox item, else the first state item. Alternatively, close the menu and focus the trigger, using `requestStatusFilterFocus(nextParam)` just as the notice does.

### UI-WR-c4: "Use for new tickets" has no pending guard

**File:** `src/app/(app)/settings/statuses/status-manager.tsx:208-222`

**Issue:** `handleSetDefault` has no pending state. An admin can start a second set-default from the same row or another row before the first call returns. Each success fires its own toast and calls `refreshThenFocus`.

`pendingFocusRef` is overwritten, so the first row's focus target is lost and the toasts can finish out of order. That can claim a default that the second call has already replaced: "New tickets now start as A", then B.

**Fix:** add a `defaultPending` state and return early while it is set. Show the items as `aria-disabled` while pending, as reorder does with `moveBusy`. Clear it in a `finally` block after the action settles.

### UI-WR-c5: After `REPLACEMENT_INVALID`, the delete dialog still offers the invalid replacement

**File:** `src/app/(app)/settings/statuses/delete-status-dialog.tsx:177-181` (with `status-manager.tsx:363-365`)

**Issue:** On `REPLACEMENT_INVALID` the dialog clears the Select and focuses it, as the spec asks. The options still come from the page snapshot (`replacements` is computed from `states`, and nothing refreshes it), so the deleted or moved state is still listed.

The admin can pick the same state again and get the same refusal indefinitely. The callout tells them to "Pick another one" without saying which.

**Fix:** keep a `rejectedIds` set in the dialog and filter the Select options with it. Also ask the parent to `router.refresh()`; the manager passes fresh `replacements` without remounting, because the key is `formKey`.

## Info

### UI-IN-c1: Confirmed: a comment repeats button labels only so an acceptance grep matches

**File:** `src/app/(app)/settings/statuses/delete-status-dialog.tsx:141`

**Issue:** The comment `// Case A "Delete status", case B "Move tickets and delete", case C "Replace and delete".` duplicates labels the code takes from `state-copy.ts` constants. Its only effect is to satisfy `12.1-12-PLAN.md:179`, which asserts that the file "contains … 'Move tickets and delete', 'Replace and delete'".

The grep would therefore pass even if the case-to-label mapping were wrong, for example B and C swapped. The note is confirmed; the acceptance check is vacuous.

**Fix:** delete the comment. Replace the grep with a test that renders the dialog for cases A, B and C and asserts the destructive button's text. Alternatively, assert on `MOVE_AND_DELETE_BUTTON` and `REPLACE_AND_DELETE_BUTTON` usage in the case expression.

### UI-IN-c2: The notice-to-trigger focus handoff uses a module-level mutable variable

**File:** `src/app/(app)/tickets/filter-chip-row.tsx:64-82`, `missing-status-notice.tsx:34`

**Issue:** `statusFocusTarget` is module state shared across the whole client session. If the `router.replace` started by "Remove deleted status" never commits (the user navigates elsewhere first), the target stays set. The next render whose `state` param equals it, often `null` (no param), then moves focus to the Status trigger without warning.

**Fix:** clear the target on `pathname` change or after a timeout. A cleaner option is a small context or ref owned by `TicketListPanel`'s client boundary.

### UI-IN-c3: The name length limit is counted two different ways

**File:** `src/app/(app)/settings/statuses/status-form-dialog.tsx:142` and `:250`

**Issue:** The client check counts code points (`[...trimmed].length`), but `maxLength={40}` on the input counts UTF-16 code units. A name containing emoji or other astral characters is cut silently below 40 characters, while the help text promises "Up to 40 characters".

**Fix:** drop `maxLength` and rely on the code-point check plus its field error. Alternatively, document that the input cap is stricter.

### UI-IN-c4: The "Delete in-use description" copy differs from the UI-SPEC row

**File:** `src/app/(app)/settings/statuses/delete-status-dialog.tsx:223` (renders `deleteInUseDescription` from `src/lib/tickets/state-copy.ts:235-238`)

**Issue:** The row reads "{n} tickets use this status now. …". The implementation renders "1 ticket uses this status now. …" for n = 1. The verb agreement is better English, but it is not the row text word for word, and the spec's copy contract says strings are used verbatim.

**Fix:** record the deviation as a copy amendment in 12.1-UI-SPEC (Copywriting table), or revert to the row text.
