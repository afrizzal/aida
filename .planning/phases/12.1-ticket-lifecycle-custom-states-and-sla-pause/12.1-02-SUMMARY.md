## Red-window checker contract (for plans 12.1-03 to 12.1-14)

```
node tests/support/red-window-tsc.mjs <plan-id> <log-path> [--through-task N] [--baseline PATH]
```

- Run from the repository root. Plans are read from `.planning/phases/12.1-ticket-lifecycle-custom-states-and-sla-pause`; a plan is completed when its SUMMARY exists. The baseline defaults to `tests/support/red-window-baseline.json`.
- The log: `pnpm exec tsc --noEmit --pretty false > LOG 2>&1; echo "TSC_EXIT=$?" >> LOG`, written by the same command, checked within 15 minutes.
- Exit 0: no violation. Exit 1: at least one violation, each printed as `VIOLATION <reason>: <line>`. Exit 2: the log does not exist, the baseline is missing or invalid, fewer than 15 plans parse, the plan id is unknown, or the arguments are malformed.
- Output: tsc exit, the diagnostic count, the ignored count per owning plan, every violation, then PASS or FAIL.
- Freshness: exactly one `TSC_EXIT=<int>` line, and it is the last non-empty line; mtime at most 15 minutes old.
- Form: every other line is `<path>(<l>,<c>): error TS<n>: <text>` (the path is everything before the first `(<digits>,<digits>): error TS`) or an indented continuation after a diagnostic.
- Exit agreement: 0 with diagnostics, non-zero without any, or a value outside 0, 1 and 2 fail.
- Ownership: the window is 12.1-15 and every plan not depending on it (12.1-01 to 12.1-15). A diagnostic fails when it sits in the plan's own file (tasks 1 to N with `--through-task N`), under `.next/` (the message says to run `pnpm exec next typegen`, never to delete `.next/`, and to stop and report if it persists), in a file no window plan owns, or in a file whose other owners are all dependencies or completed. A file the plan lists only in a later task is ignored and counted as `<plan> (later task)`.
- Baseline rule (review R2-2): with an unfinished other owner, the file is allowed when no owner is finished. It fails as "file already migrated by Q" when a finished owner Q other than `recordedBy` exists. When the only finished owner is the recorder (12.1-01, for example `merge.ts`), each signature (file, TS code, first-line message, no position) is allowed only when the baseline lists it and the log's count does not exceed the baseline count. Otherwise it fails as "new red-window diagnostic" or "increased red-window diagnostic (log count X, baseline count Y)".

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Scoped tsc could not see Node types**
- Found during: Task 3 verify (first run tsc=2, TS2591 for `node:fs`, `__dirname`, `process`).
- Issue: the verify's temporary tsconfig lives under `$TMPDIR`. Automatic `@types` inclusion resolves from the config's directory, so `@types/node` was not loaded for `design-tokens.test.ts` and `red-window-tsc.test.ts`.
- Fix: `/// <reference types="node" />` at the top of both test files. It resolves from the file's location and changes nothing in the repository's own program, which already loads `@types/node`.
- Commit: 4c5af0a

**2. [Rule 3 - Blocking] Implicit any from the JS checker**
- Issue: values returned by `windowPlans` and `loadPhasePlans` were untyped JS, which gave TS7006 in the test.
- Fix: a JSDoc `Plan` typedef plus `@param` and `@returns` on `parsePlanFile`, `loadPhasePlans`, `transitiveDeps` and `windowPlans`. With `allowJs`, TS uses them.
- Commit: 4c5af0a
