## Summary

This part reads in full the diff of the five files that part a read only partly. It does not
repeat WR-01, WR-02 or IN-01..04 of `12.1-REVIEW.md`.

What holds:

- **Membership first (D-01).** Every admin operation runs `runAdminOperation`. Inside the
  transaction it calls `findActiveMembership`, then the exact role check (`ADMIN_ROLES` is
  `{owner, admin}`), then takes the config `FOR UPDATE`, and only then parses input. A
  non-member therefore gets `MEMBERSHIP_ENDED` before any input refusal. `listStatesForSettings`
  checks membership before it reads anything.
- **Tenancy.** Every raw statement in the admin service, `ticket-states.ts`, snooze and
  auto-close carries an `organizationId` term. The Prisma `updateMany` calls include
  `organizationId`. The auto-close candidate join matches on both `id` and `organizationId`.
  One pre-existing statement in the seed lacks the term (IN-a2-5).
- **Lock order (D-15).** Admin operations take config `FOR UPDATE`, then the state(s)
  `FOR UPDATE`, then the replacement `FOR SHARE`, then tickets in ascending id. Because every
  admin operation takes the config row `FOR UPDATE` first, admin operations never interleave.
  Auto-close takes Setting, then config `FOR SHARE`, then the target `FOR SHARE`, then the
  ticket. Admin operations never touch Setting. The seed takes the state `FOR SHARE`, then the
  ticket. No cycle found.
- **Admin refusals.**
  - `LAST_IN_GROUP` exempts only PENDING (K41).
  - `REPLACEMENT_REQUIRED` covers both tickets and roles. It is re-checked after the ticket lock
    when no replacement was given.
  - The replacement must be active, in the same group and not the deleted state itself.
  - Set-default refuses a state outside the OPEN group (K40).
  - Re-pointing roles only ever targets a same-group replacement, so the config cannot leave its
    groups through the service.
- **Soft delete (K42).**
  - `lockStateForUpdate`, `shareLockActiveState`, `listActiveStates`, `readLegacyStateIds` and
    the reorder set all filter `deletedAt IS NULL`.
  - `readStateGroups` deliberately does not filter it, because it reads a ticket's current
    state, never a target.
  - Rename runs `updateMany` with `deletedAt: null`.
- **Name uniqueness.** The partial unique index on `(organizationId, lower(name)) WHERE
  "deletedAt" IS NULL` matches `parseName`. JS `trim()` strips a superset of what `btrim`
  strips, so the CHECK always holds. Both sides count code points. The service maps 23505/P2002
  to `DUPLICATE_NAME`.
- **Reorder.** The service sorts by `(sortOrder, id COLLATE "C")`, swaps the neighbours, and
  renumbers `0..n-1` with writes only where the value changes. A move at the boundary only
  normalises the order. `sortOrder` has no unique index, so the row-by-row rewrite cannot
  collide part way through.
- **Auto-close.** It keeps `resolvedAt` (Phase 11 D-16; the UPDATE does not touch it). It
  re-checks the RESOLVED group twice: once on the locked row through `readStateGroups`, and
  again in the UPDATE's `EXISTS`. The target is taken `FOR SHARE`, and a deleted target throws.
- **Snooze.** It refuses every CLOSED-group state through the group of the locked ticket. A
  missing group fails closed (`TICKET_UNAVAILABLE`). Snooze never touches the pause fields.
- **Demo seed.** It resolves the legacy key to an active state under `FOR SHARE` and throws
  `DemoSeedStateUnavailableError` otherwise. `stateId`, `slaPausedAt` and `slaPausedMs` are
  typed out of the free `data`, so a caller cannot write them directly.
- **Audit.** Admin ticket moves and auto-close write only `{ stateId, stateGroup }`.

No blocker. One warning concerns the size limit of the delete-with-replacement transaction.

## Warnings

### WR-a2-1: Deleting a state with many tickets runs one 30 s transaction while it holds the config row `FOR UPDATE`. A large state cannot be deleted, and new-ticket intake for the organization stalls

**File:** `src/lib/tickets/ticket-state-admin.ts:9`, `:322-366`
**Issue:**
- **The work is per ticket.** `deleteTicketState` moves every ticket of the deleted state inside
  one interactive transaction (`TRANSACTION_OPTIONS.timeout = 30_000`). It costs two round
  trips per ticket: `applyStateTransition`, an `updateMany`, then `recordTicketAudit`, an
  insert. On top of that come one statement that lists the ids and one that locks them all.
- **Large states fail.** A "Closed"-group state of a real helpdesk easily holds tens of
  thousands of tickets. Such a delete exceeds the timeout and rolls back every time, so the
  documented "delete with replacement" (K41, AIDA-97) is unusable for exactly the states that
  matter.
- **Writers stall meanwhile.** The transaction holds the organization's
  `TicketStateConfig` row `FOR UPDATE` for the whole run. Every role writer takes that row
  `FOR SHARE` first: create-ticket (email intake), merge, reply/reopen and auto-close. All of
  them block for up to 30 s, and those with a shorter `maxWait` fail. This fails closed (no data
  loss), but it is an organization-wide outage of ticket intake that any admin can trigger by
  clicking delete.

**Fix:** move the tickets with set-based statements in the same transaction. A same-group
move changes only `stateId` and `updatedAt` (D-12), so no per-row planning is needed:

```ts
const moved = await tx.$queryRaw<{ id: string }[]>`
  UPDATE "Ticket" SET "stateId" = ${replacement.id}, "updatedAt" = ${now}
  WHERE "organizationId" = ${orgId} AND "stateId" = ${state.id}
    AND id = ANY(${lockedIds}::text[])
  RETURNING id
`;
// one INSERT ... SELECT FROM unnest(...) for the STATUS_CHANGED audit rows, same batchId
```

Alternatively, cap the synchronous path, for example refuse with a new code above N tickets
and hand larger moves to a pg-boss job that works in batches. Add a test with a few thousand
tickets that asserts the delete finishes well inside the timeout.

## Info

### IN-a2-1: The delete loop skips a ticket whose update count is not 1 and soft-deletes the state anyway

**File:** `src/lib/tickets/ticket-state-admin.ts:355`, `:388-392`
**Issue:** `if (count !== 1) continue;` silently leaves a ticket in the state, and the state is
then marked deleted. Today the row is locked and in the organization, so the count is always
1. Still, this is the one path where a failure would leave a ticket pointing at a deleted state,
which K42 forbids. The `stateId !== state.id` skip above it is correct; this one is not
needed.
**Fix:** `if (count !== 1) throw new Error(\`state delete: ticket ${ticket.id} not moved\`);`.
The rollback then keeps the state active.

### IN-a2-2: Auto-close does not check that the auto-close role points at a CLOSED-group state

**File:** `src/lib/worker/jobs/auto-close.ts:110-112`, `:142`
**Issue:** the target is taken `FOR SHARE` and checked for `deletedAt`, but its `group` is only
copied into the audit row. The service keeps the role inside CLOSED, but nothing in the
database does: the migration has no trigger on `TicketStateConfig`. A hand edit or a later bug
would make the worker "close" RESOLVED tickets into another group without the effects of
`planStateTransition`.
**Fix:** `if (!target || target.group !== "CLOSED") throw new AutoCloseStateUnavailableError(orgId, autoCloseStateId);`

### IN-a2-3: State names accept control and zero-width characters

**File:** `src/lib/tickets/ticket-state-admin.ts` (`parseName`)
**Issue:** `"Open\u200B"`, `"Open\n"` with an inner newline, or a name with bidi controls passes
`parseName` and the CHECK. It does not collide with `"Open"` under `lower(name)`, so an admin
can create states that look identical in the chips, the filters and the feed.
**Fix:** refuse `\p{Cc}`, `\p{Cf}` and line separators with `INVALID_NAME`. Optionally
NFC-normalise before the length check.

### IN-a2-4: `listStatesForSettings` reads states, counts and config in three separate statements

**File:** `src/lib/tickets/ticket-state-admin.ts:652-670`
**Issue:** without a transaction, a delete that commits between the reads can produce a config
whose `defaultStateId` or role points at a state missing from `states`, or counts for a
deleted state. This affects the display only.
**Fix:** run the three reads in a `REPEATABLE READ` read-only `$transaction`, or join them into
one query.

### IN-a2-5: The demo finalize update has no organization term

**File:** `src/lib/demo/seed-demo-data.ts` (`finalizeDemoTicket`, `tx.ticket.update({ where: { id: ticketId } ... })`)
**Issue:** the statement is guarded by `lockDemoTicket`, which refuses a ticket outside the
organization, so nothing leaks. It is still the only write in the reviewed files without the
"tenancy on every statement" term.
**Fix:** `tx.ticket.updateMany({ where: { id: ticketId, organizationId: orgId }, data })` and
assert `count === 1`.
