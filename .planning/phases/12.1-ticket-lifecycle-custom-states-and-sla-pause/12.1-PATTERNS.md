## 0. Findings the planner must act on (not visible from CONTEXT.md alone)

1. **A second organization creation path exists.** CONTEXT D-07 says `createFirstOrgAndAdmin` (`src/lib/bootstrap.ts:12-50`) is the only creation path. It is not: `src/app/(auth)/setup/actions.ts:55-62` calls `auth.api.createOrganization` itself and never goes through `bootstrap.ts`. The default-state helper must be called there too (or the setup action must be refactored onto `createFirstOrgAndAdmin`). Better Auth has no organization hook configured (`src/lib/auth.ts:23`, only `allowUserToCreateOrganization: false`). Test fixtures also create organizations directly: `tests/support/inbox-fixtures.ts:25-27` and 14 integration test files (`audit-append-only`, `create-ticket`, `draft-generation`, `email-ingest`, `inbox-schema`, `insight-run`, `kb-embed`, `scoped-tx`, `search-isolation`, `sla-flag-handler`, `ticket-picker`, `triage-injection`, `workspace-isolation`). After `stateId` becomes `NOT NULL`, every one of them breaks unless it calls the helper.
2. **`FOR UPDATE` plus a join locks the joined row too.** `lockTicketsInIdOrder` (`src/lib/tickets/merge.ts:134-148`) returns `status::text AS status`. Once status is a `TicketState` join, `SELECT … FROM "Ticket" t JOIN "TicketState" s … FOR UPDATE` would also take `FOR UPDATE` on the state row and collide with the D-15 delete protocol (which relies on the FK key-share lock). Use `FOR UPDATE OF t` (or read the group in a second, unlocked statement after the lock). The same applies to the inline lock in `runTicketMutation` (`src/lib/tickets/mutations.ts:250-256`).
3. **`runTicketMutation` does not lock through the helper.** CONTEXT says every new ticket lock goes through `lockTicketsInIdOrder`, but `mutations.ts:250-256` has its own one-statement `ORDER BY id FOR UPDATE`. It has the same order, but it is a second copy. The rewritten state change either moves onto the helper or records why it keeps its own statement.
4. **The audit privacy contract forbids free text.** `src/lib/tickets/ticket-audit.ts:5-7` says "before and after hold ids, enum values and booleans only. Never pass … free text", and `prisma/schema.prisma:652` repeats it. D-11 stores a state **name snapshot** in `STATUS_CHANGED` rows. The type (`TicketAuditValue = string | boolean | null`, line 15) allows it, but both comments must be amended in the same plan, and the amendment must state that an admin-chosen state name is configuration, not ticket content.
5. **The integration harness can only migrate to head.** `tests/integration/global-setup.ts:15-37` starts one `pgvector/pgvector:pg16` container and runs `pnpm prisma migrate deploy` for **all** migrations. The D-10 migration test (apply up to `20261109100000_ticket_lifecycle`, seed, then apply this migration) has no precedent. It needs its own container (or its own database on the shared container) with the migrations directory copied minus the new one, then the new one applied. See "No Analog Found".
6. **No composite foreign key exists in the schema yet.** Every relation in `prisma/schema.prisma` is single-column. `Ticket(organizationId, stateId) → TicketState(organizationId, id)` and the five `TicketStateConfig` role FKs are the first. Prisma supports `@relation(fields: [organizationId, stateId], references: [organizationId, id])` with `@@unique([organizationId, id])` on the target; the planner must check the generated SQL by hand (D-08) because `organizationId` also takes part in `Ticket.organization`.
7. **Fixtures and tests set `status` directly.** `tests/support/inbox-fixtures.ts:51,74`, `tests/support/lifecycle-fixtures.ts:19,41`, and `tests/integration/sla-flag-handler.test.ts:22-52` (which calls `prisma.ticket.create` with `status`) all write the enum. 19 integration test files, the egress fixture `tests/integration/egress-fixtures/probe.ts`, `tests/unit/activity-feed.test.ts` and 9 E2E specs pass status literals (grep `status: "NEW|OPEN|PENDING|RESOLVED|CLOSED"` under `tests/`). A fixture helper that maps a group or a migrated name to a `stateId` is needed before wave 2.
8. **`TicketStatus` from the generated client is imported by 15 product files.** These are listed in the reader matrix (section 2). Removing the enum (D-04) breaks `tsc --noEmit` until every one is migrated, so the plans 1 to 3 "not independent deploys" note in D-19 is a hard compile-time fact.
