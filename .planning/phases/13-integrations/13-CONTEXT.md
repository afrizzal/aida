<domain>
## Phase Boundary

AIDA plugs into other tools through three things, and nothing else: (1) admin-created API tokens and a versioned REST API at `/api/v1/*` (AIDA-58, AIDA-59); (2) outbound webhooks signed with HMAC-SHA256, delivered through pg-boss with retry, a delivery log, auto-deactivation and an SSRF guard (AIDA-60); (3) an issue-tracker bridge: one adapter interface, a GitHub Issues adapter and a Plane adapter, an Escalate action on the ticket, and tracker status changes returning as an internal note (AIDA-61, AIDA-62). AIDA-63 (every new egress documented and tested) is worked on but cannot close in this phase (see Owner items).

Out of scope: the `internal` adapter (AIDA-91, Phase 17); any AI feature (nothing in this phase calls `lib/llm/`); writing back to a tracker; linking an existing issue; public replies through the API; CORS; more trackers (Linear, Jira). Adapters and webhooks are tested against fake servers only. No real credentials are used by the run.

Later phases build on this one: the adapter interface must not assume a network call (ROADMAP → Cross-phase risks, tracker adapter row), and every new data path must honour deactivation (same table, AIDA-43 row).

## Implementation Decisions

Format per decision: decision; Codex view; where Claude differs and why; source. Security, authorization, schema and tenancy choices take the most conservative option (Aturan keputusan 4); each difference from Codex is also reported to the owner through `LAPORAN.md`.

### API tokens and the public API (AIDA-58, AIDA-59)

- **D-01 (X-01) Token format and storage.** Format `aida_<prefix>_<secret>`: `prefix` is a random public identifier (stored in plain text, unique, shown in the UI), `secret` is 32 random bytes from `crypto.randomBytes`, base64url. The full token is shown once at creation and never again. Stored: SHA-256 of the full token string; lookup by prefix, then constant-time compare of the hash (`timingSafeEqual`). No pepper, no slow hash, no new package. Expiry is mandatory: default 90 days, maximum 365 days, no non-expiring token. Revocation is soft (`revokedAt`, plus a reason) so the audit trail and `lastUsedAt` stay. `lastUsedAt` is written at most once per 60 seconds per token (conditional update). The token value and the `Authorization` header never reach logs, error text, audit rows or the delivery log. *Codex:* SHA-256 is enough for a 256-bit random secret; a pepper only helps against a database-only leak and costs key management; argon2 brings no matching benefit; mandatory expiry, `revokedAt`, throttled `lastUsedAt`. *Difference:* none. *Source:* AIDA-58, SEED-002, Codex.
- **D-02 (X-02) Scopes and principal.** Two scopes only: `read` and `read_write` (AIDA-58). Only owners and admins create, list and revoke tokens. A token acts as its creator: on every request the creator's membership is re-read conservatively (`findConservativeMembership`, `src/lib/membership.ts:81`), and every mutation re-checks it inside its transaction (the `runTicketMutation` pattern, `src/lib/tickets/mutations.ts:300`, verified to call `findActiveMembership` inside the transaction). A token works only while its creator is still a member **with the owner or admin role** in that organization. Deactivation, or a role change that takes the creator below admin, revokes that user's tokens in the same transaction (`revokedAt`, reason `creator_deactivated` or `creator_demoted`), and the request-time check rejects them as well (defence in depth). Every API mutation records the creator as the actor plus the token id (D-17). *Codex:* token acts as creator, conservative membership check each request and in the transaction; after demotion the token stays only if the operation rights are still held; record user and token id. *Difference:* a demoted creator's tokens are revoked rather than kept. Reason: tokens are admin-minted credentials, AIDA-58 only creates them for admins, and keeping them after demotion leaves an admin-created credential with a non-admin; this is the conservative choice on authorization. *Source:* AIDA-58 ("a token whose creator is deactivated stops working"), Codex, Claude.
- **D-03 (X-03) Auth path and proxy.** `src/proxy.ts` gets a dedicated branch for the anchored prefix `/api/v1/` (with the slash, matched on the canonical pathname the proxy already computes for `BLOCKED_PUBLIC_ROUTES`): it forwards only when an `Authorization` header starts with `Bearer aida_`, and otherwise answers the same 401 JSON as today (`src/proxy.ts:163-171`). It is not added to `PUBLIC_PREFIXES`. Every route under `src/app/api/v1/` calls one gate, `requireApiToken(request, scope)`, and nothing else authenticates there: no `readFreshSession`, no `getScopedDb`, no cookie fallback. A session cookie may be present and is ignored. No CORS headers are emitted, so browsers on other origins cannot call the API. Tests cover path variants (`/api/v1x`, `/api/v1`, `/API/v1/`, encoded slashes, `..` segments) and a cookie-only request (401). *Codex:* the proxy forwards exactly `/api/v1/`; every route requires the bearer gate without a session fallback; a cookie may be present but is not used, so rejecting it is unnecessary; add a gate inventory and path-variant tests. *Difference:* the proxy also requires a bearer-shaped header before forwarding (more conservative: a route that forgot its gate is still not reachable by an anonymous request). *Source:* SEED-002, Codex (verified: raw `startsWith` at `src/proxy.ts:159`).
- **D-04 (X-04) Rate limits.** Per-token limit through a fixed-window counter on Postgres, one atomic `UPDATE ... RETURNING` per request (window start and count on the token row or a one-row-per-token table; the planner chooses). Default 60 requests per minute, settable by the admin per token up to 600. Over the limit: 429 with `Retry-After`. `consumeRateLimit` is **not** used for authenticated calls, because its admission control (`RATE_LIMIT_MAX_CONCURRENT = 3`, one in-flight call per identity, `src/lib/rate-limit/check-rate-limit.ts:197` and `:268`, verified) gives a false 429 to parallel calls from one token. Failed authentications (missing, malformed, unknown, expired or revoked token) are limited per client IP with `consumeRateLimit` under a new scope in `src/lib/rate-limit/public-limits.ts`; a false 429 on that path only slows failures. The fixed-window burst at a window edge is documented in the API docs. *Codex:* per-token window counter with an atomic Postgres update; separate quota 429 from overload 503; a coarse IP limit before the bearer lookup. *Difference:* the IP limit counts failures only, so legitimate parallel calls from one IP are never throttled by the admission pool; no 503 overload state, because the token path has no admission queue. *Source:* AIDA-58, Codex.
- **D-05 (X-05) Versioning and OpenAPI.** `/api/v1` is frozen once shipped; a breaking change goes to `/api/v2`. One static OpenAPI 3.1 document under `docs/` (the planner names the file) lists every operation with its required scope as `x-aida-scope`. A parity test walks `src/app/api/v1/**/route.ts`, collects every exported HTTP method, and fails in both directions: an operation in code missing from the document, and an operation in the document missing from code, plus a scope mismatch. No new package (no schema-to-OpenAPI generator). *Codex:* static OpenAPI with an operation and scope parity test that also detects new operations missing from the document. *Difference:* none. *Source:* AIDA-59, Codex.
- **D-06 (X-06) Tenant scoping and responses.** The organization comes only from the token row, never from the path, query or body. A foreign or unknown id answers 404, the same as a missing one. Routes reuse the existing ticket services with the creator as actor (status changes keep the Phase 12.1 custom-state and SLA-pause rules). Every response goes through an allowlist serializer; no Prisma row is spread. Never returned: encrypted settings, `AuditEvent.input`, `statusToken` (verified returned by `createTicket`, `src/lib/tickets/create-ticket.ts:155-160`), token hashes, webhook or tracker secrets. Lists use cursor pagination, default 25, maximum 100. Request bodies are size-limited and validated with zod (already pinned at 4.6.7). Operations (AIDA-59 minimum): read tickets (list, get), messages of a ticket, contacts, tags; create a ticket; update status, priority and assignee; add an internal note. No public-reply endpoint (anything customer-facing stays behind a human in the UI). Every operation has an authentication test and an unmocked cross-org test. *Codex:* same, plus the warning that `scopedDb` does not intercept `findUnique` or `createMany` (verified, `src/lib/scoped-db.ts:82-91` and `:119`). *Difference:* none; the planner uses only scoped operations on the new models (D-21). *Source:* AIDA-59, SEED-002, Codex.

### Outbound webhooks (AIDA-60)

- **D-07 (X-07) Signature.** Each delivery carries `X-Aida-Event`, `X-Aida-Delivery` (stable delivery id), `X-Aida-Timestamp` (Unix seconds) and `X-Aida-Signature: v1=<hex>`, where the HMAC-SHA256 is computed over `${timestamp}.${deliveryId}.${event}.${rawBody}`. The docs tell receivers to verify in constant time and reject a timestamp more than 300 seconds from their clock, and to deduplicate on the delivery id. The signing secret is 32 random bytes, encrypted at rest with `encryptSecret` (`src/lib/crypto/secret-box.ts:32`; it must be recoverable to sign, so it is encrypted, not hashed), shown once, and rotated by immediate replacement (no overlap window in this phase). *Codex:* sign timestamp, delivery id, event and body; encrypted secret; immediate rotation first. *Difference:* none. *Source:* AIDA-60, SEED-002, Codex.
- **D-08 (X-08) Delivery, retry and auto-deactivation.** Transactional outbox: the change that causes an event writes the `WebhookDelivery` row (status `PENDING`) inside its own Prisma transaction, through one helper, for app and worker paths alike (email ingest, auto-close, snooze wake included). pg-boss `send` never runs inside the transaction (the rule already stated at `src/lib/tickets/create-ticket.ts:163`); after commit a `webhook-deliver` job is enqueued, and a periodic sweeper job enqueues any `PENDING` row older than a minute, so a crash between commit and enqueue loses nothing. Delivery is at least once, with a stable delivery id. Per attempt: 10-second deadline, response body read capped (64 KiB) and discarded, 2xx is success, everything else (including any 3xx) is failure. Retry: 5 attempts, explicit `retryDelay` 30 seconds, `retryBackoff` true, ceiling 30 minutes (the K55 note at `src/lib/queue/boss-client.ts:20-24` says backoff does nothing without an explicit `retryDelay`; whether pg-boss 12.23.0 offers `retryDelayMax` is *unverified*, the planner checks the installed package). Auto-deactivation: after 5 consecutive **final** failed deliveries (not attempts), counted with an atomic update that also flips `enabled` to false at the threshold; any success resets the counter. On deactivation, every owner and admin of the organization gets one in-app notification (new `NotificationType` value, idempotent `eventKey` per deactivation) and, when SMTP is configured, one email through the existing sender with `Auto-Submitted` (`src/lib/notifications/digest-sender.ts`). *Codex:* outbox in the domain transaction including worker events, dispatcher recovers pending rows, at-least-once with stable ids; 10 s timeout, 5 attempts from 30 s with backoff and jitter, 30-minute cap; deactivate after 5 failed final deliveries; idempotent notification and email. *Difference:* none (jitter only if pg-boss offers it; no hand-rolled scheduler). *Source:* AIDA-60, SEED-002, Codex.
- **D-09 (X-09) SSRF guard.** One module (relative imports only, read by app and worker), used by webhook delivery, tracker adapters and every connection test. Steps: parse the URL; resolve the host once; classify **every** returned address and refuse if any is denied; connect to the validated address through `node:http`/`node:https` with a custom `lookup` that returns only that pinned address, keeping the hostname for SNI and certificate verification (no `undici` package: it is not a dependency, verified only `undici-types` in the lockfile); `redirect` is never followed; checked at registration and again on every attempt. Denied always, whatever any setting says: loopback (`127.0.0.0/8`, `::1`), unspecified (`0.0.0.0/8`, `::`), link-local (`169.254.0.0/16`, `fe80::/10`, which covers cloud metadata), multicast and broadcast, IPv4-mapped and IPv4-compatible IPv6 forms of any denied address, and NAT64 forms. Denied unless the operator allowlist covers them (D-10): RFC 1918, CGNAT `100.64.0.0/10`, ULA `fc00::/7`, and other reserved ranges. Public targets: `https` on port 443 only. The delivery log stores a category (`dns`, `denied_address`, `timeout`, `tls`, `redirect`, `http_status`, `connection`), the status code and the duration, never error text or response bodies (this closes the "SSRF error oracle" class noted in Phase 7). Tests: unit tests inject the resolver and the policy as constructor parameters, never through an environment variable or build flag; one real-socket test proves pinning (a resolver that answers differently on a second call cannot move the connection); and a test proves the production policy factory refuses loopback and link-local even when the operator allowlist lists them. *Codex:* HTTPS, validate every DNS answer, pin with SNI kept, refuse redirects, re-check each attempt, limit scheme, port, timeout and response size; inject resolver and transport in tests; no environment flag or CIDR bypass an operator can switch on in the production webhook path; a real-socket pinning test. *Difference:* the operator allowlist of D-10 also applies to webhooks (see D-10 for why); the test seam is a constructor parameter that neither the environment nor the UI can reach. *Source:* AIDA-60, SEED-002, Codex (verified: no SSRF guard, `safe-fetch` or DNS pinning in `src`; `src/lib/connection-test/errors.ts:18-21`).
- **D-10 (X-10) Private-network targets and tracker base URLs.** Private-network targets are denied unless the **operator** (whoever runs the server, through one deployment environment variable the planner names, read at startup; not a workspace-admin setting in the UI) lists explicit CIDRs. Default empty. Entries that overlap the always-denied set of D-09 are refused at startup with a clear log line. Only addresses covered by the allowlist may use `http`, and any port. The docs tell operators to list the narrowest range (a single `/32` host when possible) and state the residual risk: an allowlisted range that contains AIDA's own compose network exposes internal services to admin-configured URLs. GitHub: `https://api.github.com` by default, or a GitHub Enterprise Server base URL, subject to the same guard. Plane: any base URL under the same guard (Plane cloud is public; self-hosted Plane on a LAN needs the allowlist). *Codex:* Plane on a LAN makes this an owner decision on egress scope; no operator CIDR bypass on the webhook path. *Difference:* the run builds the allowlist, default off, for webhooks and trackers alike. Reasons: the run brief requires "private-network targets denied unless an operator setting allows them"; self-hosted Plane on a LAN is the main audience (SEED-001); the configured Ollama URL already reaches private addresses by operator choice; a documented deployment setting is not a test backdoor (the test seams of D-09 are separate and unreachable from configuration); and it lets the egress test prove the real production path (D-11). Because this widens egress to LAN targets, it is added to owner item 13-o1 as a sub-question, and the default stays "off". *Source:* run brief, SEED-001, Codex.
- **D-11 (X-11) Egress listing while 08-o4 is open.** `docs/SECURITY.md` is **not edited** in this phase. The text for its egress section (webhook destinations, tracker destinations, the operator allowlist, what each sends) is written into a phase document in this directory (the planner names it, for example `13-SECURITY-DRAFT.md`) for the owner to apply. AIDA-63 and success criterion 5 stay open. The egress test is still extended: `docker-compose.egress-test.yml` gains `stub-webhook` and `stub-tracker` on the `10.90.0.0/24` internal network (verified subnet at `docker-compose.egress-test.yml:35`), the app container there sets the operator allowlist to exactly those two `/32` addresses, and `tests/integration/egress-isolation.test.ts` widens the observed-destination set (verified today `{postgres, stub LLM, stub SMTP}`, `:365`) to add the two stubs, plus a flow proving that a destination outside the allowlist is refused. When the egress suite is blocked (space), it is recorded as blocked, never as passed. *Codex:* AIDA-63 and criterion 5 cannot close; prepare proposed text and test evidence for the owner; changing `PROJECT.md` wording is the owner's. *Difference:* none. *Source:* ANTREAN 08-o4 and 13-o1, charter "Aturan teknis AIDA", Codex.

### Issue-tracker bridge (AIDA-61, AIDA-62)

- **D-12 (X-12) Adapter interface and credentials.** `src/lib/integrations/issue-tracker/` (relative imports only), mirroring `src/lib/llm/` (a provider-name union like `LlmProviderName`, `src/lib/llm/types.ts:11`). Two layers: a domain port every adapter implements (`createIssue`, `getStatus`) that assumes no network call, so the Phase 17 `internal` adapter fits; and an optional HTTP capability (`testConnection`, `verifyInbound(rawBody, headers, secret)`, `parseInbound`) with the transport injected (the D-09 guarded transport in production, a test transport in tests). Credentials live in a new org-scoped `TrackerConnection` model (provider, display name, base URL, non-secret target config validated per provider such as GitHub owner and repo or Plane workspace and project, encrypted credential, encrypted inbound webhook secret, `enabled` default false, creator, timestamps), unique on (`organizationId`, `provider`) in this phase so there is one connection per provider; the model allows relaxing that later. Connection tests use a 10-second deadline like the LLM probe (`src/lib/llm/test-connection.ts:13`). Implemented from `research/plane-inspiration.md` and public provider documentation, never from Plane's AGPL source. *Codex:* separate the domain port from HTTP, webhook verification and connection tests; `internal` needs no transport; `TrackerConnection` is clearer, start with one connection per provider. *Difference:* none. *Source:* AIDA-61, SEED-001, ROADMAP cross-phase risk, Codex.
- **D-13 (X-13) Escalation content and idempotency.** Any current member with access to the ticket may escalate, but only to a connection an admin has enabled. A preview dialog shows exactly what leaves AIDA: a title (prefilled from the ticket subject) and a summary the agent writes, plus a backlink to the ticket built from the configured app URL. Not sent by default, and not offered in this phase: customer name or email, message bodies, internal notes, attachments. No AI writes the summary. Create a new issue only; linking an existing issue is deferred. `TicketExternalLink` (org-scoped: ticket, connection, provider, external id, URL, `lastState`, last event time, link status) is unique on (`ticketId`, `connectionId`). Flow: insert the link as `PENDING` in a transaction (a double click hits the unique constraint and gets the existing link), call the provider, then mark it `LINKED` with the external id. If the provider call times out or the answer is lost, the link becomes `UNCERTAIN`: the UI tells the agent to check the tracker, and a retry needs an explicit confirmation that a duplicate issue may result. *Codex:* agent-written preview with minimal data and no internal notes by default; lock double clicks locally; a timeout after the issue was created gives no remote idempotency; use an idempotency key if the provider supports one, otherwise mark the result for manual reconciliation (provider support *unverified*). *Difference:* the design does not rely on a provider idempotency key at all. *Source:* AIDA-61, CLAUDE.md privacy rule, Codex.
- **D-14 (X-14) Inbound sync, replay and loops.** Route `/api/integrations/<provider>/<connectionId>/webhook`. `src/proxy.ts` adds the anchored prefix `/api/integrations/` to `PUBLIC_PREFIXES`, and an inventory test asserts that the only route under `src/app/api/integrations/` is this webhook route (admin actions are server actions under Settings, not routes there). Order, all before `JSON.parse`: read the raw body with a 1 MiB cap; look up the connection by the path id (unscoped lookup by id on this one system path; the organization is taken from the connection row); refuse a disabled connection or a provider mismatch; verify the provider HMAC over the raw bytes in constant time; then insert an inbound receipt keyed on (connection, SHA-256 of the authenticated raw body) under a unique constraint, kept 30 days; a duplicate is answered 200 and does nothing. Unknown connection, disabled connection and bad signature all get the same 401 body. Only then parse, validate with zod, and map. Stale events are dropped as well: the adapter returns the event time carried inside the signed body (for GitHub the issue's `updated_at`, *unverified*), and an event not newer than the link's last applied event time changes nothing, so a replay after the 30-day retention is still harmless. Rate limit: a per-connection fixed-window counter (as D-04) for verified requests, and `consumeRateLimit` per IP for failed verifications, because a false 429 on a valid delivery may never be resent by the provider (*unverified*). The result is an internal note (`visibility = INTERNAL`, `direction = OUTBOUND`, as internal notes are stored today, verified `src/app/api/tickets/[id]/messages/route.ts:189`) with a fixed template, the external id and the status name sanitized (plain text, control characters removed, at most 64 characters), rendered through `renderMarkdown` like every message (`src/components/tickets/thread-message.tsx:30-32`). No issue title, body or comment text is copied. The AIDA ticket status does not change (a human decides). No write back to the tracker; a status equal to `lastState` writes nothing. The note is recorded with a `SYSTEM` actor. *Codex:* raw-size cap, HMAC before parsing, atomic dedupe on the hash of the authenticated body per connection with stated retention, result and note in one transaction; the delivery id is metadata only because it is not signed; without a signed timestamp or nonce, "every replay is rejected" is not proven. *Difference:* the stale-event rule closes the after-retention gap without a signed timestamp. Honest claim for the docs and the verification: a byte-identical authenticated delivery is rejected before parsing; an older state never overwrites a newer one. *Source:* AIDA-62, SEED-001, `research/plane-inspiration.md` (header facts at `:92`), Codex.
- **D-15 (X-15) Tests against fake servers.** `node:http` fake servers on `127.0.0.1` with a random port for the GitHub API, the Plane API and the webhook receiver, reached in tests through the injected transport and policy of D-09 (never through configuration). Fixtures are written from public documentation and marked *unverified* until the human test with real credentials. E2E goes through the real UI against a fake tracker. The egress compose stubs of D-11 cover the runtime path. No real credentials, no real tracker, no real receiver. *Codex:* same. *Difference:* none. *Source:* charter phase table, AIDA-60, AIDA-61, Codex.

### UI, audit and payload

- **D-16 (X-16) UI.** Settings → Developers (API tokens, webhooks, delivery log, rotate secret) and Settings → Integrations (GitHub and Plane connections, test connection, enable), owners and admins only, added to `src/app/(app)/settings/settings-nav.tsx` (verified: neither exists today) and behind the existing admin gates. A shown-once dialog for every secret. An Escalate action in `src/components/tickets/ticket-meta-header.tsx` with the D-13 preview dialog, and a link chip for each `TicketExternalLink` with its status (including `UNCERTAIN`). Every screen follows `.planning/DESIGN-SYSTEM.md` (tokens only, `text-[Npx]`, halo empty state, §9 checklist), and the UI-SPEC from `/gsd-ui-phase 13` comes before planning. *Codex:* none beyond the candidate. *Source:* SEED-001, SEED-002, CLAUDE.md, charter step 4.
- **D-17 (X-17) Audit.** A new append-only model `IntegrationAuditEvent` (organization, actor type `USER`, `API_TOKEN` or `SYSTEM`, actor user id, token id, action, target id, timestamp, small non-secret metadata), protected by a database trigger like `AuditEvent` (`prisma/migrations/20260707053633_ai_foundation/migration.sql:45-51`), covering: token created and revoked (including automatic revocation of D-02), webhook created, changed, secret rotated, auto-deactivated, tracker connection saved, enabled, disabled. Ticket-level events use `TicketAuditEvent`: new actions for escalation and for a tracker status note, and a nullable token id column so API mutations record creator and token. `AuditEvent` (AI-shaped, verified required `provider`, `model`, `input`, `output`) and `MemberAuditEvent` (verified required `actorUserId`) are not reused. No secret, hash or token value in any audit row. *Codex:* `TicketAuditEvent` for ticket events and a new append-only integration audit model with user, token and system actors and no secrets. *Difference:* none. *Source:* Codex, charter ("`AuditEvent` append-only di level database").
- **D-18 (X-18) Payload minimisation.** Thin, versioned payloads (`"version": 1`): event name, delivery id, timestamp, the organization id (org-bound: a webhook only ever receives events of its own organization, proven by an unmocked cross-org test), ids (ticket id and number, message id) and the changed fields with old and new values as ids or enum names. Events in this phase: `ticket.created`, `ticket.updated` (status, priority, assignee), `message.created` for **public** messages only (id, ticket id, direction; no body). Never included: message bodies, contact email or name, internal notes or their existence, attachments, settings, `statusToken`, `AuditEvent.input`, secrets. Receivers fetch details through the API with a `read` token. *Codex:* thin, versioned, ids and allowed changes only; ids are still tenant data, so authorization, retention and an event contract are still needed. *Difference:* internal-note events are not emitted at all in this phase. *Source:* AIDA-60, SEED-002, Codex.

### New decisions (not in X-01 to X-18)

- **D-19 Every egress off by default.** Run default of owner item 13-o1: no egress happens until an admin creates **and** enables a webhook or tracker connection; both are created disabled; the connection test is itself an explicit admin click; the demo seed creates none; the operator allowlist (D-10) is empty by default. `PROJECT.md` and `CLAUDE.md` are not changed. *Source:* ANTREAN 13-o1.
- **D-20 No AI, untrusted payloads.** Nothing in this phase calls `lib/llm/`. Tracker payloads, webhook responses and API request bodies are untrusted input. Tracker notes stay out of AI context by construction, and tests assert it: triage reads only the first message (verified `src/lib/triage/run-triage.ts:31-34`), drafts read only `INBOUND` (verified `src/lib/rag/generate-draft.ts:49-52`), KB proposals read only `PUBLIC` (verified `src/lib/kb/proposal-sources.ts:344-351`); the tracker note is `INTERNAL` and `OUTBOUND`. A sanitized status name is not proof against prompt injection, so a later phase that feeds internal notes to an LLM must fence them. *Source:* CLAUDE.md, Codex item 7.
- **D-21 Schema and migrations.** A schema change is expected: `ApiToken`, `Webhook`, `WebhookDelivery` (outbox and log), `TrackerConnection`, `TicketExternalLink`, an inbound receipt table, `IntegrationAuditEvent` with its append-only trigger, a new `NotificationType` value (D-08), new `TicketAuditAction` values and a nullable token id on `TicketAuditEvent` (D-17), and per-token and per-connection rate-window storage (D-04, D-14). Hand-written Prisma migrations only, created and checked against a disposable dev database under rule J (a new container with the `aida-test-` prefix and label `aida.test=1` on a free port, same image as the `db` service, `DATABASE_URL` passed on the command line, `.env` untouched, `aida-dev-db` never used), as plan 10-01 Task 1 did. Each new migration is appended to the pinned list in `tests/integration/auth-upgrade.test.ts` (verified last entry `20261115100000_team_foundation` at `:47`).
