## 0. Status and amendment rule

Frozen by plan 14-01 (D-17). Plans 14-02 to 14-13 implement exactly this. ## 1. Operation table (the access matrix as data, `PROJECT_OPERATIONS`)

Access levels:
- MEMBER: any active organization member (a `member` row exists, read conservatively, K59); no project involved.
- READ: MEMBER plus read access to the project (section 2); archived project or task allowed.
- CONTENT: READ plus the project, the task and the task's parent are not archived.
- CONTENT_ARCHIVED_TASK: CONTENT except that the task itself may be archived (restore).
- MANAGE: project manager; for a non-private project also an organization owner or admin (conservative: every member row owner or admin); the project must not be archived.
- MANAGE_ARCHIVED: MANAGE, archived project allowed (restore and delete of a project).
- ORG_ADMIN: organization owner or admin, conservative.
- AUTHOR: CONTENT and the actor wrote the comment.
- AUTHOR_OR_MANAGE: CONTENT and (the actor wrote the comment or has MANAGE).
- UPLOADER_OR_MANAGE: CONTENT and (the actor uploaded the file or has MANAGE).
- CREATOR_OR_MANAGE: CONTENT and (the actor created the task or has MANAGE). Chosen for hard delete of a task (charter rule 4: the irreversible action gets the narrower rule; archive stays CONTENT).
- SELF_OR_MANAGE: the actor removes their own membership (leave) or has MANAGE.

Lock modes (section 3 gives the order): NONE; PROJECT_SHARE (project FOR SHARE); PROJECT_UPDATE (project FOR UPDATE); PROJECTS_UPDATE (several projects FOR UPDATE, one statement, id order); ORG_PROJECTS_UPDATE (every project of the organization FOR UPDATE, one statement, id order); TEAM_UPDATE (team row FOR UPDATE only; addTeamMember and removeTeamMember, which change no project's access under K69, and renameTeam); TEAM_UPDATE_THEN_PROJECTS (team FOR UPDATE, then every project the team is assigned to FOR UPDATE in id order; deleteTeam only, because it removes those projects' team assignments); TEAM_SHARE_THEN_PROJECT (team FOR SHARE, then the project FOR UPDATE).

Isolation expectations (column Isolation, field `isolation` of PROJECT_OPERATIONS, member of ISOLATION_EXPECTATIONS; section 17 defines each; review C5): TARGET (the call names a project, task, comment, attachment, label or milestone; 61 operations), CREATE (createProject), LIST (listProjects, listWorkspaceTasks, listWorkspaceMilestones, listFavorites, getProjectsProgress), KEY (resolveTaskKey), TEAM (listTeams, getTeam, createTeam, renameTeam, deleteTeam, addTeamMember, removeTeamMember, listTeamActivity).

## 2. Access rules (D-04, D-15, K59, K62, K69, 14-o1 default)

Single-entity check, in this order, inside the transaction (`access.ts`):
1. A malformed id (not a string of 1 to 64 characters from A-Z, a-z, 0-9, underscore, hyphen) is NOT_FOUND, never a database error.
2. Read the actor's organization membership conservatively (`findConservativeMembership`, all rows in id order, admin only when every row is owner or admin). No row: MEMBERSHIP_ENDED. This runs before any project lookup, so a former member learns nothing about which ids exist.
3. Take the lock of the operation (section 3) on the project row with an explicit organization term. Missing or another organization's: NOT_FOUND.
4. Read the membership again after the lock (a removal committed meanwhile is seen). No row: MEMBERSHIP_ENDED.
5. Read access: the project is not private, or the actor has a ProjectMember row in it (read with explicit organization terms). A TeamMember row of a team assigned to the project through ProjectTeam grants nothing by itself (K69, amends D-04 and D-15; review C2). No read access: NOT_FOUND, identical to a missing id (same code, no field, nothing else in the result).
6. Archive state (CONTENT and MANAGE levels): project archived, task archived or the task's parent archived: ARCHIVED, except where the level allows it.
7. MANAGE: ProjectMember role MANAGER, or (project not private and the actor is owner or admin). Otherwise NOT_ALLOWED (the actor already has read access, so this leaks nothing). Team membership never grants MANAGE.
8. Row-level rules (AUTHOR, UPLOADER, CREATOR, SELF): otherwise NOT_ALLOWED.

Task resolution (writes; review C3): read the task's projectId and parentId (plain read, explicit organization term), run steps 2 to 8 on that project, then, when the task has a parent, lock the parent row FOR SHARE (explicit organization and project terms) and only then lock the task itself (FOR UPDATE for every write that changes the task row, including archiveTask and restoreTask; FOR SHARE for a write that only hangs a row off the task, such as a comment, an attachment or a favorite of favoriteTask and unfavoriteTask, review R2-2); if its projectId changed in between (a concurrent move), CONFLICT at once, because starting over would lock a second project while the first is still held, out of id order (review a-WR-01, b-IN-02, fix batch F1); if only its parentId changed (a concurrent reparent), start over once in the same project; if it changed again, CONFLICT. A task or parent that a locking read no longer finds (deleted meanwhile) is NOT_FOUND. The archive checks of step 6 for the task and for its parent use the rows returned by these locking reads, never the earlier plain read, so a parent archive committed before the lock is seen as ARCHIVED and a parent archive that starts later waits for the write. The favorite toggles run this resolution at READ level, so they take the same locks but skip the archive checks (the archive exception of sections 10 and 16, review R2-2). Reads take no task lock. A task id of another organization or of an unreadable project is NOT_FOUND.

List predicate (reads): a typed Prisma `where` fragment, always combined with `organizationId: actor.orgId`: `isPrivate = false` OR a ProjectMember row of the actor (K69: no TeamMember branch); every nested relation filter also carries the organization term. Lists of tasks, milestones, attachments, favorites and activity apply it through the task's or the row's project. The membership read of step 2 runs first; no row: MEMBERSHIP_ENDED.

Eligibility (C14): a user is an eligible project member, team member or assignee only while a `member` row exists for them in the organization. On a private project an assignee must also be a direct project member (K69). Every list of people (project members, team members, eligible assignees) joins or re-reads `member` and leaves out users without a row; their stale ProjectMember or TeamMember rows stay in the table and grant nothing.

Who manages what (open point 2):
- Creating a project: any active member; the creator becomes MANAGER.
- Project settings, status, privacy, prefix, position, labels, milestones, membership, team assignment, archive, restore, delete: MANAGE (D-04 groups team assignment with project membership, so a project manager assigns teams; for a non-private project an organization owner or admin may too).
- Teams themselves (create, rename, delete, add and remove members): ORG_ADMIN (D-15). None of these depends on which projects a team is assigned to: no refusal and no result differs because a team is linked to a private project the caller cannot read (review C2). The earlier refinement that refused addTeamMember for a team serving a private project is withdrawn, because that refusal itself revealed the hidden link.
- K69 (amends D-04 and D-15, charter rule 4): team membership never grants access to a private project. assignTeamToProject on a private project inserts the ProjectTeam row and, in the same transaction, copies the team's current active members (TeamMember rows whose user still has a `member` row) into direct ProjectMember rows with role MEMBER, skipping users who already have a row; it writes TEAM_ASSIGNED plus one MEMBER_ADDED per copied member. Assigning a team that is already assigned is a no-op `{ ok: true, changed: false }` and copies nothing (a manager who wants later team members adds them directly, or unassigns and assigns again). Later addTeamMember, removeTeamMember, unassignTeamFromProject and deleteTeam change no project's access: copied rows are ordinary direct members that managers keep or remove. On a non-private project a team assignment is informational (every active member already has access) and copies nothing. setProjectPrivacy(true) copies nothing either: after it, only direct members read the project. The result of assignTeamToProject lists the copied user ids (`copiedUserIds`), which the manager can already see through getTeam.
- Last manager (open point 8): removing, demoting or self-removing the last MANAGER is refused with LAST_MANAGER; only managers who still have a `member` row count. setProjectPrivacy(true) is refused with LAST_MANAGER when no MANAGER row of the project belongs to a user who still has a `member` row, because owners and admins do not bypass privacy and nobody could reach the project afterwards (review a-WR-04, fix batch F1). setProjectMemberRole to MANAGER is refused with NOT_ELIGIBLE for a user without a `member` row (C14, review a-IN-04, fix batch F1). An organization member removal written by Better Auth outside these services can still leave a private project with no reachable manager; no recovery is built (14-o1 default) and the risk is recorded in the gate.
- Module names (contract.ts): `isWellFormedId(value)` implements step 1 (pattern `^[A-Za-z0-9_-]{1,64}$`, `ID_MAX_LENGTH` 64); `ProjectActor` is `{ userId: string; orgId: string }`.

## 3. Global lock order (open point 1)

Every transaction takes locks in this order and never goes back to an earlier class:
1. Team rows, in id order.
2. Project rows, in id order (FOR SHARE for content writes, deleteTask and the four favorite toggles (review R2-2, review P4), FOR UPDATE for settings, membership, privacy, team assignment, archive, delete, reorder and status moves, bulk, move and the source of duplicateProject (review R3-2)).
3. Task rows: a parent before its own subtasks, otherwise in id order (FOR UPDATE for the tasks a write changes, FOR SHARE for a parent that a write to one of its subtasks or a new subtask depends on, review C3; FOR SHARE for the task a favorite toggle names, review R2-2).
4. ProjectTaskCounter row (`UPDATE ... RETURNING`).
5. TaskKey and ProjectKeyPrefix rows (insert or update).
6. ProjectFileCleanup inserts.
7. ProjectActivity inserts, last.

Rules:
- The `member` table is never locked by these services; organization membership is read in steps 2 and 4 of section 2. A plain read inside the transaction refuses a removal committed before it; nothing stronger is claimed (the `mutations.ts:34-37` wording). Stated limitation (review C8, tied to owner item 12.2-o4): a member delete written by Better Auth's organization plugin is not serialized against project writes; re-reading membership after the project lock narrows the window but does not close it, so a write authorized just before a concurrent member delete may still commit. No plan claims that every revocation race against a Better Auth member delete is closed.
- A content write never updates the project row (C6: two FOR SHARE holders that both update the project row deadlock). The project row changes only under FOR UPDATE.
- Task rows under the project's FOR SHARE lock (content writes run concurrently; review C3): a write to a subtask locks the parent FOR SHARE and then the subtask (section 2, task resolution); createTask with a parent locks the parent FOR SHARE and re-reads it under that lock; a tree lock (lockTaskTreeInTx, used by deleteTask and moveTask) locks the root FOR UPDATE first and then, in a second statement read after the root lock, its subtasks FOR UPDATE in id order, so a subtask committed meanwhile is included; archiveTask and restoreTask lock their task FOR UPDATE; favoriteTask and unfavoriteTask lock their task FOR SHARE, after the parent FOR SHARE for a subtask (review R2-2). Because every path takes a parent before its subtasks, a subtask write and an archive or delete of its parent wait for each other in either order and never deadlock, and a favorite toggle and a delete of its task or of that task's parent do the same. Under the project's FOR UPDATE lock (setTaskStatus, setTaskParent, reorderTask, duplicateTask, duplicateProject on its source, bulkUpdateTasks, moveTask, deleteProject) no other service transaction holds task locks in that project, and those operations lock tasks in id order (bulk and deleteProject in one statement), except that a tree lock always takes its root first. duplicateProject locks no task row (review R3-2): it only reads its source, and under the source's FOR UPDATE no content write of the source runs, so its read statements see one committed state. favoriteProject and unfavoriteProject hold the project FOR SHARE and lock no task row (review P4).
- Deletes (review R2-3): deleteTask and deleteProject take every lock first (section 12 step 1: deleteProject also locks its tasks and its ProjectTaskCounter row there), then tombstone TaskKey rows (class 5), then insert ProjectFileCleanup rows (class 6), then delete rows in FK order and write ProjectActivity last (class 7). The rows they delete in FK order were locked in step 1, so a delete never takes a lock of an earlier class after a later one.
- Team changes (K69): addTeamMember and removeTeamMember lock the team FOR UPDATE only, because a team membership change alters no project's access; renameTeam the same. deleteTeam locks the team FOR UPDATE, then locks the projects of its ProjectTeam rows FOR UPDATE in one statement in id order (a project deleted meanwhile is skipped, never refused), then reads its ProjectTeam rows again under those locks (review a-WR-03, fix batch F1), then removes the assignments (one TEAM_UNASSIGNED per project) and the team. Team assignment (assign and unassign): lock the team FOR SHARE, then the project FOR UPDATE; assignTeamToProject reads the team's TeamMember rows under that team lock, so a concurrent addTeamMember or removeTeamMember either commits before the copy (and is reflected in it) or waits until the assignment commits (and is not). Because the team lock always comes first, none of these deadlock.
- moveTask locks both projects FOR UPDATE in one statement ordered by id, then the moved tree with lockTaskTreeInTx (the root, then its subtasks in id order). bulkUpdateTasks locks every involved project FOR UPDATE in one statement ordered by id, then every task FOR UPDATE in one statement ordered by id. moveProjectPosition locks every project of the organization FOR UPDATE in one statement ordered by id (rare; makes the org-wide rebalance safe).
- Test seam (C17, one style for all services): `src/lib/projects/service.ts` exports `setProjectServiceObserverForTests(observer | null)`. Every service transaction awaits `observer.onTransactionStart(tx, operationName)` as its first statement and `observer.afterLock(tx, operationName)` right after its last lock and before its first write. Production never sets it.
- Transaction options: `{ maxWait: 10_000, timeout: 30_000 }`. Transactions run on `scopedDb(orgId).$transaction` and still write the organization term explicitly in every query (D-01).
- Module names (contract.ts): `TRANSACTION_OPTIONS` is the frozen `{ maxWait: 10000, timeout: 30000 }`.

## 4. Subtasks and the trigger lock protocol (D-03, C7, open point 3)

- One level: `Task.parentId` points to a top-level task of the same project and organization (composite foreign key `(organizationId, projectId, parentId)` to `Task(organizationId, projectId, id)`).
- CHECK `Task_no_self_parent_check`: `parentId IS NULL OR parentId <> id`.
- Trigger `aida_task_subtask_depth` BEFORE INSERT OR UPDATE OF "parentId" ON "Task", function `aida_task_subtask_depth_guard()` (VOLATILE plpgsql). When NEW.parentId is not null: (a) `SELECT "parentId" FROM "Task" WHERE id = NEW."parentId" AND "organizationId" = NEW."organizationId" FOR SHARE`; when that parent has a parent, RAISE 'Task subtask depth exceeded'; (b) on UPDATE, when a row with `parentId = NEW.id` and the same organization exists, RAISE 'Task with subtasks cannot become a subtask'. Updating a task's own parentId takes a no-key-update lock on it, which conflicts with another transaction's FOR SHARE on that row, so whichever transaction locks first makes the other wait, re-read the committed row and refuse. Both interleavings are proven by PID-bound tests (plan 14-06); two raw writers that each point at the other can still meet in a deadlock, and PostgreSQL then aborts one of them, which also refuses the second link.
- Service fence first: createTask with a parent and setTaskParent refuse a parent that has a parent, a task that has subtasks and a task that recurs with SUBTASK_DEPTH or RECURRENCE_ON_SUBTASK before writing; setTaskParent locks the project FOR UPDATE and then the task and the new parent FOR UPDATE in id order, so two service calls serialize without a deadlock. The two trigger messages map to SUBTASK_DEPTH. A parent in another project is NOT_FOUND.

## 5. Activity (D-05, C8, open points 4, 5 and 10)

TEAM_MEMBER_ADDED and TEAM_MEMBER_REMOVED rows have projectId null and carry no project information.

- Two-project rows (review C1): a row about two projects has projectId = the project the row belongs to and relatedProjectId = the other project; its `before` value describes the related project's side and holds that side's `projectId`, its `after` value describes the row project's side and holds that side's `projectId`. Single-project rows never put another project's id in before or after.
- Duplicates: PROJECT_DUPLICATED on the new project (relatedProjectId = source, before `{ projectId: source }`, after `{ projectId: copy, taskCount, labelCount, milestoneCount }`); TASK_DUPLICATED for each created task, before `{ projectId: source project, taskId: source task, taskKey: source key }` and after `{ projectId: copy's project, taskKey: new key }`; a project duplicate's TASK_DUPLICATED rows also set relatedProjectId = the source project (a task duplicate stays in one project, so its relatedProjectId is null).
- Move (open point 5): one TASK_MOVED row (D-13): projectId = target, relatedProjectId = source, entity = the root task, before `{ projectId, taskKey, milestoneId, labelNames, assigneeUserId }` of the source side, after `{ projectId, taskKey, milestoneId, labelNames, assigneeUserId, subtaskCount }` of the target side. Project feeds read `projectId = P OR relatedProjectId = P`, so the row shows in both projects.
- Read rules: a project feed needs current READ access to its project. Task history needs READ on the task's current project and returns the task's rows whose projectId the reader can currently read (rows written while the task lived in a project the reader cannot read stay hidden). A team feed (listTeamActivity) needs MEMBER and the team in the organization, returns the rows with teamId = the team and leaves out every row whose projectId names a project the reader cannot read now (review C5), so a hidden link between the team and a private project leaves no trace in it, also not in its paging (Feed pages, below).
- Feed pages (review R3-3): a feed that leaves rows out (task history: rows whose projectId the reader cannot read now; team feed: rows whose projectId is not null and names a project the reader cannot read now) applies that filter inside the paged query itself, in the WHERE clause of the same statement that applies the keyset cursor and the limit, never by dropping rows from a page already fetched. A page holds up to limit readable rows in (createdAt, id) descending order; hasMore is true only when a further readable row exists after the page; the next cursor is built from the last returned row (null when hasMore is false). Rows the reader cannot read therefore change no page, no hasMore and no cursor. A project feed leaves no row out (every row of P or related to P is returned, redacted where needed). Redaction replaces values inside a returned row and never drops a row.
- Redaction on read (review C1, amends D-05 and D-13): for every returned row, a before or after value whose `projectId` names a project the reader cannot read now is replaced as a whole by REDACTED_SIDE, exactly `{ redacted: true }` with no other key: no identifier, name, task key, label name, milestone, assignee or count of that side survives. The row's own projectId or relatedProjectId naming such a project is returned as null, and the row carries `redacted: true` (otherwise `redacted: false`); the rest of the row follows the redacted projection below. For TASK_MOVED the before side is the source and the after side the target; for duplicates the before side is the source. A reader of both projects sees both sides unchanged.
- Feed rows (review R2-1): listProjectActivity, listTaskActivity and listTeamActivity return rows with exactly the keys of ACTIVITY_FEED_ROW_KEYS, in this order: id, projectId, relatedProjectId, taskId, teamId, actorUserId, verb, entityType, entityId, before, after, batchId, createdAt, redacted (14 keys; organizationId is never returned, the reader's organization is implied).
- Redacted projection (review R2-1, completes review C1): when a two-project row has a side the reader cannot read now (a private project the reader is not a direct member of, or a project that no longer exists after a hard delete), the returned row keeps a value only in id (the activity row's own identifier: the same for every reader, it names no project, task or entity, and the keyset cursor needs it), verb, entityType, createdAt, actorUserId, redacted (true) and the readable side, which is the readable project's id column (projectId or relatedProjectId) and that side's before or after value. Every other key is null: the unreadable project's id column and every key of REDACTED_ROW_NULLED_KEYS, exactly entityId, taskId, teamId and batchId, whichever side the value belongs to (a move's entityId and taskId name the moved task, which now lives in the target; a project duplicate's name the copy, which lives in the new project); the unreadable side's before or after value is exactly REDACTED_SIDE. A row with no unreadable side is returned unchanged with redacted false. Every returned row has at least one readable side: a project feed needs READ on its project and its two-project rows name that project; task history returns only rows whose projectId the reader can read; two-project rows carry no teamId and never reach a team feed. redactActivityRow (plan 14-04) is the one function that builds this projection, for all three feeds.
- Scope of redaction (review R3-1): redaction applies to two-project rows only. Single-project rows a project wrote while a task lived in it (TASK_CREATED, TASK_UPDATED, COMMENT_ADDED and the rest of a moved task's history in its source) stay in that project's feed exactly as written, with that task's id, because they describe that project's own past, which its readers could already read before the move. The guarantee of the redacted projection is about the redacted row itself: it carries no identifier, name, key, label, milestone or assignee of the unreadable side, and not the moved task's or the copy's entityId or taskId; it is not a promise that the moved task's id is absent from the whole source feed.
- PROJECT_REORDERED (run decision K71, review a-CR-01, fix batch F1): before and after are null. A position or a neighbour id would depend on projects some reader of the feed cannot read (a stored position counts hidden private projects; a neighbour may be one of them), so the row records only that the project was reordered.
- Update verbs (`*_UPDATED`, `*_CHANGED`) carry only the keys whose value changed, in both before and after. Order: createdAt descending, then id descending (plain code-unit comparison, never localeCompare).
- Value bounds (open point 10): before and after are null or JSON objects of at most 16 keys; keys are camelCase identifiers matching ^[a-z][A-Za-z0-9]{0,39}$; the keys description, descriptionMarkdown, body, bodyMarkdown and content are refused; values are null, booleans, safe integers, strings of at most 200 code points (a longer short label is cut to 200 code points; titles are at most 200, so never cut) or arrays of at most 50 strings of at most 80 code points; the serialized object is at most 4096 bytes, measured as the database measures it ( of the jsonb, which prints a space after every colon and comma; review a-IN-03, fix batch F1). The writer throws (a programming error, rethrown) on a violation; CHECKs repeat the size limit. A description change is recorded as `descriptionChanged: true`; a comment row stores `commentId` only; a file name is an untrusted short label shown as text only.
- Module names (contract.ts): `ACTIVITY_VERBS` (`ActivityVerb`), `ACTIVITY_ENTITY_TYPES` (`ActivityEntityType`), `REDACTED_SIDE` (frozen `{ redacted: true }`), `ACTIVITY_FEED_ROW_KEYS` (`ActivityFeedRowKey`), `REDACTED_ROW_NULLED_KEYS`, `ActivityScalar` and `ActivityValue` (null or an object of scalars and string arrays). Value bounds: `ACTIVITY_VALUE_MAX_KEYS` 16, `ACTIVITY_VALUE_MAX_BYTES` 4096, `ACTIVITY_TEXT_MAX` 200, `ACTIVITY_ARRAY_MAX_ITEMS` 50, `ACTIVITY_ARRAY_TEXT_MAX` 80, `ACTIVITY_KEY_PATTERN` `^[a-z][A-Za-z0-9]{0,39}$`, `ACTIVITY_FORBIDDEN_KEYS` (description, descriptionMarkdown, body, bodyMarkdown, content). Feed page size: `ACTIVITY_LIST_DEFAULT` 50, `ACTIVITY_LIST_MAX` 100.

## 6. Keys and prefixes (D-08, C5, C6, open point 9)

- Prefix: after trim and uppercase, ^[A-Z][A-Z0-9]{1,9}$ (starts with a letter, so a key never reads as a bare number); else PREFIX_INVALID. Unique per organization among projects, and reserved forever in ProjectKeyPrefix (organizationId, prefix unique, projectId without foreign key). A project may return to a prefix it reserved itself; any other project gets PREFIX_TAKEN; reservations are never deleted, even by a project delete. createProject and changeProjectKeyPrefix both write the ProjectKeyPrefix reservation before the Project row that carries the prefix (createProject generates the project id first), so two writers of one prefix meet first on ProjectKeyPrefix and never deadlock (review a-WR-02, fix batch F1).
- Key: prefix, then "-", then the number (no padding). Numbers 1 to 999999999 (TASK_NUMBER_MAX). Parse after trim and uppercase with ^([A-Z][A-Z0-9]{1,9})-([1-9][0-9]{0,8})$.
- Counter: ProjectTaskCounter (organizationId, projectId primary key, lastNumber 0 to 999999999), inserted in the createProject transaction; incremented with `UPDATE ... SET "lastNumber" = "lastNumber" + 1 WHERE "projectId" = ... AND "organizationId" = ... AND "lastNumber" < 999999999 RETURNING "lastNumber"`; no row returned: KEY_SPACE_EXHAUSTED. Never a column on Project (C6).
- Namespace: TaskKey (organizationId, normalizedKey unique; taskId and projectId without foreign key; kind ACTIVE, ALIAS or TOMBSTONE). Create inserts ACTIVE. Move turns the old ACTIVE row into ALIAS and inserts the new ACTIVE row. Duplicate inserts ACTIVE for each copy. Delete turns every row of the deleted tasks into TOMBSTONE. A prefix change leaves existing keys as they are; new tasks use the new prefix and the counter continues. Task.key holds the current key (unique per organization).
- Resolver `resolveTaskKey(actor, key)`: parse; TOMBSTONE, missing or malformed: NOT_FOUND; otherwise read the task by (organizationId, taskId) through the read predicate; no access: NOT_FOUND; else `{ ok: true, taskId, key, projectId, isAlias }`.
- Module names (contract.ts): `PREFIX_PATTERN`, `TASK_KEY_PATTERN`, `TASK_KEY_SEPARATOR` ("-"), `TASK_NUMBER_MAX`, `TASK_KEY_KINDS` (`TaskKeyKind`). `normalizePrefix(raw)` returns the trimmed, uppercased prefix when it matches the pattern and null otherwise; `isValidPrefix(raw)` is `normalizePrefix(raw) !== null`. `formatTaskKey(prefix, number)`, `parseTaskKey(raw)` (`{ prefix, number }` or null) and `normalizeTaskKey(raw)` (the canonical key or null).

## 7. Dates, time zones and recurrence (D-09, D-10, C15, open point 6)

- Calendar dates cross every service boundary as CalendarDate strings `YYYY-MM-DD` (real dates from 1970-01-01 to 2999-12-31) and are stored as `@db.Date`. Prisma reads them as a Date at UTC midnight; `toCalendarDate` and `fromCalendarDate` in contract.ts convert; raw SQL selects them as `"col"::text`.
- startDate after dueDate: INVALID_DATE_RANGE in the service and CHECK `Task_dates_check` in the database.
- Time zone: an IANA name accepted by `Intl.DateTimeFormat`, at most 64 characters; default "UTC" until user preferences exist (AIDA-98). `todayInTimeZone(tz, now)` uses `Intl.DateTimeFormat(...).formatToParts`. No date package (Node 22 Intl).
- Rules: DAILY, WEEKLY, MONTHLY, interval 1, top-level tasks only (RECURRENCE_ON_SUBTASK; CHECK `Task_recurrence_top_level_check`). Task columns recurrenceRule, recurrenceAnchor (DATE), recurrenceTimeZone are all null or all set (CHECK `Task_recurrence_fields_check`).
- setTaskRecurrence anchor: the given anchorDate, else dueDate, else startDate, else `todayInTimeZone(tz, now)`.
- Sequence: the anchor, then +1 day (DAILY), +7 days (WEEKLY), or for MONTHLY the anchor's day of month in each following month, clamped to that month's last day and computed from the anchor each time, never chained from a clamped date (31 Jan, 28 or 29 Feb, 31 Mar, 30 Apr).
- Base date of an occurrence: dueDate, else startDate, else `todayInTimeZone(tz, now)` at completion (a task without dates, open point 6). Next occurrence: the first sequence date strictly after the base.
- Successor: dueDate = next when the predecessor had a dueDate; startDate shifted to keep the predecessor's (dueDate minus startDate) gap when both existed; startDate = next when only startDate existed; dueDate = next when neither existed (the successor carries its occurrence's date). It copies title, descriptionMarkdown, assignee (null when no longer eligible), priority, labels, estimateMinutes and the recurrence (rule, anchor, time zone); it does not copy subtasks, comments, attachments, milestone, favorites or archive state. Status TODO, rank appended to the TODO group, a new key, recurrencePredecessorId = the predecessor, version 0.
- Exactly once: the successor is created only in the transaction that moves the task into DONE from another status, under the task's row lock, and only when the predecessor's `recurrenceSpawned` is false (set true by a conditional update in the same transaction). The partial unique index `Task_recurrence_predecessor_key` on (organizationId, recurrencePredecessorId) WHERE recurrencePredecessorId IS NOT NULL is the database fence. Retrying, a second concurrent completion, or reopening and completing again creates nothing. bulkUpdateTasks writes the rest of its patch (fields, then label removals and additions) before the status change of the same task, so a successor created by that completion copies the patched dates, priority, assignee and labels (review b-WR-01, fix batch F1). Deleting the successor later does not allow a new one. recurrencePredecessorId has no foreign key, so deleting the predecessor keeps the successor.
- Changing the series time zone after creation changes only future `todayInTimeZone` computations (tasks without dates) and is copied forward; the anchor is a calendar date and is never converted. A move keeps the recurrence.
- Clock: services take `opts?: { now?: Date }` and read it once after their locks.
- Module names (contract.ts): `CalendarDate` (a string), `CALENDAR_DATE_MIN` "1970-01-01", `CALENDAR_DATE_MAX` "2999-12-31", `parseCalendarDate(raw)` (the date or null), `isCalendarDate(raw)`, `fromCalendarDate(date)` (Date at UTC midnight; throws RangeError on an invalid date, a programming error), `toCalendarDate(date)` (UTC calendar date of a Date), `isValidTimeZone(value)`, `todayInTimeZone(timeZone, now)` (formatToParts with the Gregorian calendar and Latin digits), `TIME_ZONE_MAX_LENGTH` 64, `DEFAULT_TIME_ZONE` "UTC", `RECURRENCE_RULES` (`RecurrenceRule`).

## 8. Ordering (D-10, open point 9)

- Rank: integer at least 0; RANK_GAP 1024; RANK_MAX 2147483647. Groups: top-level tasks by (projectId, status); subtasks by parentId. Order is (rank, id); ties are allowed (two concurrent appends may share a rank).
- Append: the group's largest rank plus RANK_GAP (RANK_GAP for an empty group). Between a and b: floor((a + b) / 2) when strictly between; otherwise, or when an append would pass RANK_MAX, rebalance the group to (i + 1) times RANK_GAP in (rank, id) order inside the same transaction under the project's FOR UPDATE lock, then compute again. An append that runs without the project's FOR UPDATE lock (createTask under FOR SHARE, createProject without a lock) never rebalances: when the append would pass RANK_MAX it uses min(largest + 1, RANK_MAX), a tie ordered by id (reached only after about two million appends in one group). A raw rank update sets `"updatedAt" = now()` itself. Rank changes do not increment `version` (section 14).
- Project order (AIDA-64): one organization-wide order, Project.position, same math over all projects of the organization (ties broken by id); moving a project is MANAGE on that project and takes ORG_PROJECTS_UPDATE because a rebalance renumbers other projects (internal values only, no visible change). Not per user. Run decision K71 (review a-CR-01, charter rule 4, fix batch F1): the stored position is never exposed. getProject and listProjects return no position; the listProjects cursor names the last returned project only, and the server re-reads that project's position under the read predicate (unreadable or gone: INVALID_INPUT field cursor). moveProjectPosition takes a readable anchor (null: first), decides its no-op (`changed: false`) from the order among the projects the caller can read, places the project directly after the anchor in the full order (hidden rows keep their places; a rebalance renumbers the whole organization internally) and writes PROJECT_REORDERED with before and after null (section 5). createProject still appends after the largest stored position, which is never returned. So two worlds that differ only by private projects the caller cannot read give identical results, cursors and activity.
- Module names (contract.ts): `RANK_GAP` 1024, `RANK_MAX` 2147483647.

## 9. Progress (D-11, open point 7)

- Project progress: top-level tasks with status DONE and archivedAt null, divided by top-level tasks with archivedAt null; 0 for an empty project. Task progress: its subtasks DONE and not archived, divided by its subtasks not archived; 0 without subtasks. Result `{ done, total, percent }` with percent = floor(done * 100 / total), or 0. Computed on read with explicit-organization count or groupBy, never stored.
- A parent DONE with open subtasks is shown as it is; nothing completes automatically.

## 10. Archive and favorites (D-12, open point 7)

- `archivedAt` on Project and Task. Default lists leave archived projects and tasks out; list options `archived: "exclude" | "only" | "include"` (default exclude) serve the later archive page.
- An archived project refuses every write (ARCHIVED) except restoreProject, deleteProject and favorites; its reads keep working. Allowing deleteProject and favorites deviates from D-12 ("read-only except for restore"); the deviation and its reason are recorded in section 16 (row D-12).
- Archiving a parent sets archivedAt on the parent only; its subtasks keep their own archivedAt but count as archived through the parent (left out of default lists, writes refused with ARCHIVED); restoring the parent brings them back exactly as they were. A subtask can be archived on its own and then leaves its parent's progress. restoreTask in an archived project is ARCHIVED (restore the project first).
- Locks (review C3): archiveTask and restoreTask lock their task FOR UPDATE (after the parent FOR SHARE when the task is a subtask). Every write to a subtask locks the parent FOR SHARE first; every such write except the favorite toggles (below) also checks the parent's archivedAt on the locked row (section 2, task resolution), so archiving a parent and writing to one of its subtasks serialize in either order: when the archive commits first the subtask write returns ARCHIVED and changes nothing; when the subtask write commits first the archive waits for it and then succeeds.
- Favorites: ProjectFavorite and TaskFavorite, unique per (organizationId, userId, entity); favoriting twice or unfavoriting a missing favorite is a no-op `{ ok: true, changed: false }`; listFavorites returns only entities the actor can read now, archived ones only with includeArchived.
- Favorite toggles are an explicit archive exception (review R2-2; section 16 row D-12): a favorite is a per-user preference that changes no project content and writes no activity (D-05), so the four toggles run at READ and are not refused by an archived project, an archived task or a task whose parent is archived. favoriteTask and unfavoriteTask take the project FOR SHARE and lock the task FOR SHARE through the task resolution of section 2 (a subtask's parent FOR SHARE first), so they serialize with deleteTask (its tree FOR UPDATE) and deleteProject (its project FOR UPDATE) in either order: when the delete commits first the toggle returns NOT_FOUND and writes nothing; when the toggle commits first the delete waits for it and then removes the task together with its TaskFavorite rows. favoriteProject and unfavoriteProject (review P4) take the project FOR SHARE through requireProject at READ (lock mode PROJECT_SHARE), so they serialize with deleteProject (project FOR UPDATE) in either order: when the delete commits first the toggle's locking read finds no project and returns NOT_FOUND with no row written; when the toggle commits first the delete waits for it and then removes the ProjectFavorite rows with the project (section 12 step 5), so no insert ever meets a missing project and fails on a foreign key. They stay allowed on an archived project and wait for a concurrent archiveProject or restoreProject the same way. A favorite toggle called after a committed delete is NOT_FOUND, deep-equal to the call with a missing id.

## 11. Duplicate and move (D-13)

- duplicateTask: same project; copies the task and its non-archived subtasks with title, descriptionMarkdown, status, priority, dates, estimateMinutes, assignee (when still eligible), labels and milestone; not comments, attachments, activity, favorites or recurrence (a copy never starts a second series). New keys. Placement (review C6): duplicateTask runs under PROJECT_UPDATE; the copy gets rankBetween(source rank, rank of the next task of the source's group in (rank, id) order), or appendRank when the source is last; when that is null (adjacent integers, a tie with the next task, or past RANK_MAX) the group is rebalanced inside the transaction (section 8) and the rank computed again, so the copy is always directly after the source; the copied subtasks form the copy's new group with ranks (i + 1) times RANK_GAP in the source subtasks' (rank, id) order.
- duplicateProject(actor, projectId, { name, keyPrefix, includeTasks }): copies description, color, icon, status, dueDate, isPrivate, labels and milestones; with includeTasks also every non-archived task and its non-archived subtasks with status, priority, dates, estimateMinutes, descriptionMarkdown, ranks, labels mapped to the copied labels, milestone mapped to the copied milestone, and the assignee when still eligible in the new project (for a private copy only the duplicating user is a member). Never comments, attachments, activity, favorites, team assignments or members other than the duplicating user, who becomes MANAGER. The new prefix must be free (PREFIX_TAKEN). Keys are numbered from 1 over the top-level tasks in (status order, rank, id), each followed by its copied subtasks in (rank, id). Locks (review R3-2): duplicateProject takes PROJECT_UPDATE on the source (access stays READ, so an archived source is allowed) and reads the source's labels, milestones, tasks and label links only after that lock and afterLock; every content write of the source (setTaskLabels, updateTask, deleteTask, createTask and the rest, all holding the source at least FOR SHARE) and every MANAGE write (updateLabel and the rest, FOR UPDATE) either commits before the lock, and is in the copy, or waits until the copy commits, and is not; the copy never mixes two states of the source.
- moveTask(actor, taskId, targetProjectId, expectedVersion): top-level tasks only (a subtask alone: SUBTASK_MOVE); target equal to source: INVALID_INPUT; CONTENT on both projects. The whole tree moves in one statement that also sets the new number, key, rank and mapped milestone of each task (C3: the self foreign key and the milestone foreign key are satisfied at the end of that statement). Label links of the tree are deleted before that statement and re-created afterwards for labels whose name (case-insensitive) exists in the target; other labels are dropped. Milestone by case-insensitive name, else cleared. Assignee kept when eligible in the target, else cleared. Comments, attachments and task favorites follow because they reference (organizationId, taskId) only (K67). New keys from the target counter (root first, then subtasks in rank order); old keys become ALIAS. One TASK_MOVED row (section 5). Private-project rules hold across the move: afterwards the old key resolves only for readers of the target project.

## 14. Refusal codes, result shape and errors (C13)

- Codes (`PROJECT_REFUSAL_CODES`): NOT_FOUND, MEMBERSHIP_ENDED, NOT_ALLOWED, ARCHIVED, CONFLICT, INVALID_INPUT, INVALID_DATE_RANGE, PREFIX_INVALID, PREFIX_TAKEN, KEY_SPACE_EXHAUSTED, NAME_TAKEN, NOT_ELIGIBLE, LAST_MANAGER, SUBTASK_DEPTH, SUBTASK_MOVE, RECURRENCE_ON_SUBTASK, TOO_MANY, CONFIRMATION_REQUIRED, FILE_TOO_LARGE, UNSUPPORTED_FILE_TYPE.
- Result: `{ ok: true, ... }` or `{ ok: false, code, field? }`; `field` only with INVALID_INPUT. A no-op is `{ ok: true, changed: false }`.
- A `ProjectRefusal` thrown inside a transaction rolls it back and is returned; any other error rolls back and is rethrown. Database errors are a second fence, classified only by SQLSTATE and the constraint or index name the server reports, never by searching free text (review a-IN-07, fix batch F1): the trigger messages of section 4 (P0001, exact message) map to SUBTASK_DEPTH; a unique violation (23505) maps by index name (ProjectKeyPrefix and Project prefix: PREFIX_TAKEN; label, milestone and team names: NAME_TAKEN); Task_dates_check (23514) maps to INVALID_DATE_RANGE and every text length CHECK (23514) to INVALID_INPUT with the service's field (name, description, title or body; review a-WR-05); a deadlock (40P01) maps to CONFLICT as a last resort (review a-WR-01, a-WR-02; the lock order of section 3 should make it unreachable); never check-then-insert without that mapping; idempotent inserts use `INSERT ... ON CONFLICT DO NOTHING` and re-read.
- Version: Project, Task, ProjectMilestone and TaskComment carry `version Int @default(0)`, incremented by every change of their content fields (not by rank, position or updatedAt). Edits take expectedVersion and run a conditional update on (id, organizationId, version); a count of 0 is classified by an explicit re-read through the read predicate: gone or unreadable NOT_FOUND, archived ARCHIVED, else CONFLICT (the missRefusal pattern). The project edits (updateProject, setProjectStatus, setProjectPrivacy, changeProjectKeyPrefix) hold the project FOR UPDATE and compare expectedVersion before the no-op test, so a stale version is CONFLICT even when every value equals the stored one (review a-IN-02, fix batch F1). bulkUpdateTasks and reorderTask take no version (they lock instead).
- Module names (contract.ts): `PROJECT_REFUSAL_CODES` (`ProjectRefusalCode`), `ProjectRefusal` (`{ ok: false; code; field? }`) and `ProjectResult<T>` (`({ ok: true } & T) | ProjectRefusal`).

## 17. Test protocol (binding for every later plan)

- Integration tests run against Testcontainers with no mocks of the database or of isolation, with `DOCKER_HOST=unix://$HOME/.colima/default/docker.sock TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`.
- Every case seeds fresh organizations (fixtures of plan 14-02). The privacy world has two organizations and these actors: manager (project MANAGER), member (project MEMBER), teamMember (TeamMember of a team linked to the project by a ProjectTeam row, with no ProjectMember row: under K69 a team alone grants nothing, so teamMember is refused on the private project exactly like nonMember), nonMember (plain member of the same organization), orgAdmin (owner of the same organization, not a project member) and outsider (member of the other organization).
- Every operation is called by each actor on a private project, with the expectation of its Isolation class (section 1; review C5):
  - TARGET: manager and member get their access level's result (member gets NOT_ALLOWED on MANAGE operations and on rows of others under AUTHOR, UPLOADER and CREATOR rules); teamMember, nonMember, orgAdmin and outsider (with their own organization) get a result deep-equal to the same call with missingId() (NOT_FOUND); the outsider with the victim's organization in the actor gets MEMBERSHIP_ENDED.
  - CREATE (createProject): every active member creates in the actor's organization (nonMember, teamMember and orgAdmin in A, the outsider in B); the outsider with organization A in the actor gets MEMBERSHIP_ENDED and nothing is written.
  - LIST (listProjects, listWorkspaceTasks, listWorkspaceMilestones, listFavorites, getProjectsProgress): every actor gets a successful result; for teamMember, nonMember, orgAdmin and outsider it contains no id of the private project or of anything in it, while the manager's result contains them; the outsider with organization A gets MEMBERSHIP_ENDED.
  - KEY (resolveTaskKey): refused actors get a result deep-equal to resolveTaskKey with a well-formed key that exists nowhere; the outsider with organization A gets MEMBERSHIP_ENDED.
  - TEAM (listTeams, getTeam, createTeam, renameTeam, deleteTeam, addTeamMember, removeTeamMember, listTeamActivity): decided by organization membership (MEMBER) or organization admin (ORG_ADMIN), never by a project link; private project information the caller cannot read is left out (getTeam's project list, listTeamActivity's rows); the outsider with their own organization gets a result deep-equal to the call with missingId() for organization A's team ids; the outsider with organization A gets MEMBERSHIP_ENDED.
