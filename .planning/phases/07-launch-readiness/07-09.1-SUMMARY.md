## Egress capture mechanism: what worked, what was rejected

**Worked (Task 1, prior session):** a logging DNS resolver set as the compose network's `dns:` override for every service. Any DNS lookup a service attempts is logged, giving an observable, assertable record of every *attempted* destination — regardless of whether the underlying connection then succeeds or fails. This was the plan's own D-1-predicted "least platform-sensitive" option, and it worked on the first attempt in this Docker Desktop on Windows environment.

**Rejected/not needed:** a `NET_ADMIN`-capability capture sidecar and a blackhole-gateway approach (both named as alternatives in the plan) were not required once the DNS-resolver approach proved sufficient — no platform-specific capability issue was hit that would have forced a fallback.

**Negative control result:** a deliberate, forced lookup to a known-external host from inside the `internal: true` network was captured by the DNS logger and asserted present — proving the harness can actually detect egress, not just fail to observe it. Without this, the deny-all-network test's "success" would be indistinguishable from a broken capture.

## The Prisma checkpoint.prisma.io leak — and a lesson about adversarial refutation's limits

**What it was:** Prisma's CLI phones home to `checkpoint.prisma.io` on every `migrate deploy` invocation — including inside a Docker network declared `internal: true`, with no route to the internet. This is a genuine, real egress attempt from a component (the `migrate` service in `docker-compose.yml`) that ships in AIDA's own production image.

**How it was found:** `tests/integration/egress-isolation.test.ts`'s DNS-logger capture recorded the lookup attempt during Task 1's first run — the test's own negative-control discipline (assert the OBSERVED set is a strict subset of the expected set) turned what would otherwise be silent noise into a hard, actionable failure.

**Fixed:** `CHECKPOINT_DISABLE=1` added to both `docker-compose.egress-test.yml` and the real, shipped `docker-compose.yml:35` — a genuine privacy improvement for every self-hosted AIDA deployment, not just a test-fixture patch.

**The lesson (explicitly requested for this record):** 07-09's own security-pass audit (`07-SECURITY-PASS.md`, Sweep 5, finding F-14) had ALREADY found and reported this exact issue — but that report was **STATIC ANALYSIS**, and F-14 was catalogued as a "known issue, not in approved-fixes scope" (build/deploy-time egress, no ticket/customer data in the payload). Crucially, 07-SECURITY-PASS.md's own "Not audited" scope note explicitly flagged that "third-party SDK internals" were "verified only via static call-site/source analysis, not a live network capture." This runtime test is exactly that live capture, and it found the SAME issue Sweep 5 had already named — but from a completely different angle (a real, running deny-all-network deployment, not a source-code grep) — and this time it got fixed as a direct, forcing consequence of the test failing. **The real lesson is not that static analysis was wrong** (it correctly identified the issue) **but that static analysis alone cannot establish severity or urgency the way a live, runtime failure can** — a sweep's "known issue, out of scope" disposition and a failing integration test asserting a specific security property are very different forcing functions, even when they point at the identical line of code. Adversarial refutation (07-09's own verifier-agent methodology, which refuted 13 of 17 raw claimed findings) is a check on FALSE POSITIVES; it does not, and cannot, substitute for a live runtime proof when the claim is fundamentally about runtime behavior. Static findings that get triaged as "known issue, low priority" deserve periodic re-examination once a cheap runtime test exists to actually settle the question — this is exactly that re-examination, run once, and the answer changed the disposition from "accepted risk" to "fixed."

## Contrast/token violations found and how each was resolved

**Fixed (4 real, isolated contrast bugs + 2 real token violations):**

1. Four `Badge` call sites (`triage-category-chip.tsx`, `ticket-meta-header.tsx`'s language badge, `priority-chip.tsx`'s LOW/NORMAL, `triage-sentiment-chip.tsx`'s NEUTRAL) omitted `variant="outline"`, so each silently inherited the `Badge` component's DEFAULT variant (`bg-primary text-primary-foreground`) while their own `classes`/`className` only overrode the TEXT color (to `text-foreground`/`text-muted-foreground`) — producing an unintended `bg-primary` fill paired with the wrong text color, measured at 2.9:1-3.86:1 against a 4.5:1 requirement. Fixed by adding the `variant="outline"` these components clearly intended (border + neutral text, no fill) — the correct, already-existing variant, not a new one.
2. Sidebar footer email text (`text-sidebar-foreground/60`) measured 3.76:1 in light mode. Bumped to `/70`, matching the value already documented for inactive nav items in DESIGN-SYSTEM.md §4.1 and already used one section up in the same file — empirically re-verified at >5:1 after the fix.
3. Two token violations in hand-authored (non-vendor) pages: the login/setup `CardTitle`'s `text-2xl` (fixed to `text-[18px] font-semibold tracking-tight`, matching DESIGN-SYSTEM.md §3's documented page-title size) and the login form's root-error `text-sm` (fixed to `text-[14px]`, matching the identical pattern already used in `request-form.tsx`).

**Found and reported, deliberately NOT fixed (a systemic brand/semantic-color VALUE gap, not a narrow bug):**

- `--success` (light mode, `oklch(0.58 0.14 155)`) as badge text on its own `/10` tint — 3.47:1. Affects `KbEmbeddingStatusChip`'s "Indexed" badge.
- `--primary` (dark mode, `oklch(0.585 0.215 278)` / `#6563f7`) used AS TEXT on dark surfaces — 3.86:1-4.1:1. Affects the sidebar avatar-initials fallback (every dark-theme page), the "AI Draft" label and KB citation links, and the `bg-primary/10 text-primary` filter-pill pattern ("All", "Public Reply").
- `--primary` as a solid button/badge background with near-white text — 3.98:1 (light, `#716ee4`) / 4.29:1 (dark, `#6563f7`). Affects every default-variant `Button` and `StatusChip`'s `NEW` state.

**Why these were not fixed:** `--primary` is DESIGN-SYSTEM.md §1's locked Brand Identity, and `--success` is one of four documented semantic status colors (§4.7); both are used identically across dozens of components in both themes. A large-enough numeric adjustment to clear 4.5:1 is a genuine, visible brand-color decision with wide blast radius (every existing screenshot, both themes, every primary CTA) — not a narrow, safe, single-component fix. Per this plan's own critical constraint ("FIX it when the fix is small and safe, or REPORT it as a finding... Report honestly if axe finds violations you could not fix"), this is reported, not allowlisted. **7 of `a11y-contrast.spec.ts`'s 8 tests remain honestly RED** as a direct, correct consequence — see `deferred-items.md`'s "From 07-09.1" section for the full writeup, reason, and owner (maintainer, no target date).
