# AIDA — Security & Privacy (reference)

AIDA's promise is **privacy-first, self-hosted AI**. These controls are product features, not afterthoughts. Phase plans must honor them; the Phase 7 security pass verifies them.

## Data residency & egress
- All ticket/customer data and KB content stay in the operator's PostgreSQL. **The only *application-runtime* outbound network egress is to the operator-configured LLM endpoint** (OpenAI/Anthropic, or nothing for local Ollama) plus the operator's own configured SMTP/IMAP host. No analytics or error-reporting SDK exists anywhere in the codebase (verified: zero call sites for Sentry/PostHog/Datadog/Segment/etc.).
- Local mode (Ollama) supports a fully air-gapped deployment — zero external API calls once built.
- **Known gap (not application runtime):** the *build/deploy* path currently makes three third-party calls the privacy-first posture should eventually close, none of which carry ticket/customer data: `next/font/google` fetches a font at `next build` time (self-hosted afterwards — zero egress once built); Next.js's own build/dev telemetry to `telemetry.nextjs.org` is on by default (off at runtime); and the Prisma CLI's checkpoint ping to `checkpoint.prisma.io` fires on every `docker compose up` via the one-shot `migrate` service. See the Phase 7 security pass for full detail — corrected here rather than silently left implied by "no telemetry ... by default" above.

## Secrets & keys
- LLM provider API keys and email (IMAP/SMTP) credentials are **encrypted at rest** (AES-256-GCM via `APP_ENCRYPTION_KEY`, the app's one secret-box primitive), never logged, never returned to the client in plaintext. Verified: every credential-bearing `Setting` key round-trips exclusively through `encryptSecret`/`decryptSecret`, and all 14 `console.*` call sites in `src/` were traced and none interpolates a decrypted secret.
- `.env.example` documents required secrets; real secrets are never committed (enforced by `.gitignore`).
- Public-endpoint rate-limiting stores `sha256(ip + RATE_LIMIT_PEPPER)`, never the raw IP. `RATE_LIMIT_PEPPER` is **mandatory** — the app throws a descriptive error rather than silently falling back to an unsalted or public-default hash if it is ever unset at the point a rate limit is actually checked (fixed in the Phase 7 security pass; previously it could silently degrade to an unsalted hash on the shipped Compose path — corrected, not merely documented).
- **Demo and seed output prints no password (F-09, fixed in Phase 9 plan 09-02):** `pnpm db:seed`, the `DEMO_MODE` boot, `bootstrapFromEnv` and `scripts/capture-demo-assets.ts` never print a demo or admin password; the seed names the admin email and points to `DEMO_ADMIN_PASSWORD`, and the capture script also redacts the password from the seed output it echoes. Verified: `tests/integration/seed-guard.test.ts` and `tests/integration/demo-boot.test.ts` scan the captured stdout and stderr of every seed, boot and bootstrap run for the configured (random) password and for the documented default.

## Untrusted input (prompt-injection)
- Ticket subjects, bodies, and email content are **untrusted**. They are passed to the LLM as *data to analyze*, never as instructions, using clear delimiting and a system prompt that refuses embedded instructions.
- The AI has **no autonomous action capability in v1** beyond producing drafts/classifications: it cannot send to customers, change ticket state destructively, or call tools without a human. This structurally neutralizes "injection → action."
- Drafted replies are **citation-grounded** and require human approval before send; an agent is the gate against a malicious/hallucinated draft.

## PII handling
- Obvious secrets (API keys, passwords, tokens, card-like numbers) are redacted before text reaches the LLM or the audit log, via a redaction pass.
- The KB ingestion path is for operator-curated content; it should not ingest customer PII by default.
- Default posture: "no training on your data" — adapters request no-retention/no-train options where the provider supports them; documented per provider.

## AuthZ & tenancy
- Server-side authorization on every mutating route (admin vs agent); UI hiding is never the only control. Verified across all 35 Server Actions and all 8 route handlers in the Phase 7 security pass — one gap was found (a single Settings action missing its admin gate) and fixed the same day; see the security pass report for the full per-action/per-route audit.
- All data access goes through `scopedDb(workspaceId)`; an integration test seeds two workspaces and asserts zero cross-tenant reads. `scopedDb` does **not** intercept raw SQL — every `$queryRaw`/`$executeRaw` call site in the codebase was individually audited and confirmed to filter `organizationId` explicitly (or an equivalent org-scoped join), except one system-cron job whose predicates are row-local and returns no rows to any tenant.
- **Seed and demo guard (F-10, Phase 9 plan 09-02):** `pnpm db:seed` and the `DEMO_MODE` boot write demo data only into an empty database (no organization and no user; migrations, the job queue, `SystemSetting` and `RateLimitHit` never count). One classifier, `src/lib/demo/tenant-guard.ts`, reads only organization ids, user emails and the completion marker (`Setting` key `demo:seed-complete`, written last): the complete marked demo (one organization with the marker, only configured demo accounts) is skipped, and an incomplete demo or anything else is refused with one log line and no write. Nothing is ever deleted, renamed or modified to recover; recovery is a documented manual step on a new database (`docs/OPERATIONS.md`, Demo mode). The organization slug decides nothing, because the real bootstrap and the demo share it. The seed CLI, the demo boot and `bootstrapFromEnv` take one Postgres transaction-level advisory lock (`src/lib/tenant-seed-lock.ts`), held in one open transaction from the classification until the marker commits; race-free is claimed only for these three paths. The lock is a mutex, not atomicity: the seed's other writes commit on their own, and a crash leaves an incomplete demo that both paths then refuse. **Known limit:** the `/setup` wizard and user sign-up do not take the lock, so a sign-up racing the very first demo boot is not excluded. Verified: `tests/integration/demo-boot.test.ts` (fresh, repeated after the heartbeat, a 2 x 2 refusal matrix, a crash after each of seven write stages refused by both paths, concurrent seed CLI and demo boot, `bootstrapFromEnv` before and racing the seed, a lock timeout) and `tests/integration/seed-guard.test.ts` (the real `pnpm db:seed`), comparing the exact row count of every table before and after every refusal.
- **Workspace logo (AIDA-34, Phase 9 plan 09-05):** only organization owners and admins can upload, replace or remove the logo (`POST` and `DELETE /api/settings/branding/logo`): the session is checked first, then the role, and only then is the body read, bounded to one part. The bytes are sniffed with `file-type`, and only PNG, JPEG and WebP are stored; SVG and every other type are refused, and the declared type and the file name are never used. A logo is at most 1 MiB and 1024 x 1024 pixels, read from the image header without decoding it. The file is immutable under the organization's upload directory. Replace and remove take a per-organization advisory lock and enqueue the previous file in the one deletion queue in the same transaction, so overlapping replaces never orphan a file; only the fenced queue sweep deletes it, never while a backup holds the fence. The public route `GET /api/public/logo/<orgId>/<version>` sits under the existing `/api/public` prefix (no new `src/proxy.ts` entry). It is throttled first, with the Phase 8 limiter under the scope `public-logo` (300 requests per 60 s per client identity). It serves only the organization's current version, with the stored MIME type, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline` and `Cache-Control: public, max-age=31536000, immutable`, and answers the same 404 for every miss (unknown organization, no logo, another version, malformed parameters). The CSP's existing `img-src 'self'` already allows the same-origin image. **Caching limit:** removing or replacing a logo does not revoke copies already cached by browsers or proxies, because the versioned URL is cached as immutable for a year; new requests for an old version get 404. Verified: `tests/unit/logo-validate.test.ts`, `tests/unit/logo-upload-route.test.ts`, `tests/integration/logo-store.test.ts` and `tests/integration/logo-routes.test.ts`.

## Settings connection tests
- The four "Test connection" actions (AI provider, embedding provider, IMAP, SMTP) are admin-only. A failure returns one of four fixed categories and a correlation ID, never the probe's error text. The server log line under that ID holds the probe, the category and the error's name, code and HTTP status, each from a fixed list; never a message, host, port, URL, header or stack.
- This removes the error-text oracle and puts every network and protocol failure into one category, `connection_failed`: a timeout, a refused or closed connection, a DNS or TLS failure, another service on the port, an unexpected HTTP status, or a reply without the protocol's response shape.
- `authentication_failed` is only given where AIDA sends a credential: the OpenAI and Anthropic API keys (their fixed vendor hosts) and the IMAP and SMTP logins. A credential rejection does not prove which service answered; any HTTP server can send a 401.
- The Ollama probes send no credential and take an admin-typed URL. There an HTTP 401 or 403 is `connection_failed`, and a 200 passes only with Ollama's response shape: a `models` array from `/api/tags`, and an `embeddings` array of non-empty number arrays from `/api/embed`. Any other 200 is `connection_failed`.
- **Residual:** a service at the typed address that imitates the protocol's replies (on the Ollama URL, Ollama's `/api/tags` or `/api/embed` shapes) still passes, so a pass proves only the shape, not the service; response timing still differs between outcomes; and the probe still connects to the address the admin typed, so SSRF itself is not removed, only narrowed to these signals.

## Auditability
- `AuditEvent` is **append-only** — AI triage decisions, generated drafts, and approved sends are recorded with the model used and references to inputs/outputs. Audit rows are never mutated or deleted.

## Self-host hardening & continuity (single server)
- Caddy provides TLS by default; the app binds behind it.
- Backup/restore via `pg_dump`/`pg_restore` documented (AIDA-24); the Postgres volume is the single source of truth, so a volume snapshot + dump is a complete backup.
- Healthcheck endpoint for the container; documented upgrade path (migrate on deploy).
- An `AI off` switch lets an operator disable all LLM calls instantly (kill switch).

## Honesty in claims
- AIDA **orchestrates** LLMs (hosted or local) — it does not train/fine-tune models. Marketing uses relative/measured claims, never fabricated resolution-rate statistics.

## Reporting a vulnerability

Found a security issue? Please do not open a public issue — see [`.github/SECURITY.md`](../.github/SECURITY.md) for the private disclosure process. That document is the disclosure *process*; this one is the *design*.
